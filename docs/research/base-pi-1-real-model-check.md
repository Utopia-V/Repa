# Pi 1.1.0 真实模型缓存、上下文与变更说明核实

2026-10-10 UTC，在 `pi-1-real-check` 分支核实 Pi 1.1.0。生产底座以 `e2d58bcff` 为基线，其中 Pi 升级提交为 `06d3e3358`；本轮修改核实脚本、辅助模块和测试，底座默认行为保持不变。[Codex 0.87.1 报告](base-real-model-check.md)与 [DeepSeek 0.87.1 报告](base-deepseek-cache-check.md)及其原始证据保持原貌。

本轮沿用 `openai-codex/gpt-6-luna`、`deepseek/deepseek-flash` 和 `deepseek/deepseek-v4-pro`，各跑原场景与一次有变更说明的对照。两组都先建立六轮使用旧后缀的历史，再覆盖同一个 `plugin:notes` 段。实验组只在覆盖后的第一轮附加一句说明，指出该段的后缀从 A 改为 B；此后恢复原问题。这样检验的是明确的规则变更能否打断旧回复的延续，而不是再次给出当前 view 的答案。

## 结果与建议

两个 DeepSeek 模型都重现了旧规则延续：不加说明时，覆盖后的八轮仍使用旧后缀，压缩后才恢复；加一条说明后，当轮就改用新后缀，接下来七轮也全部正确。两组都读对了 view 版本，因此改善集中在规则跟随，而不是状态是否送达。

| 原场景 | 0.87.1 总命中率 | 1.1.0 总命中率 | 1.1.0 回复与结构 |
| --- | ---: | ---: | --- |
| Codex | 46.04% | 36.87% | 17 / 17 回复正确；覆盖保留完整前缀，命中差异集中在服务缓存复用 |
| Flash | 78.06%（诊断复跑） | 77.97% | 8 / 16 回复正确；八次失败都是覆盖后沿用旧后缀，结构与旧轮一致 |
| Pro | 70.68% | 72.14% | 8 / 16 回复正确；八次失败同上，本轮压缩后恢复，结构与旧轮一致 |

**建议底座支持由覆盖入口提供的一次性变更说明，先作为显式可选能力。** 它在两种 DeepSeek 模型上解决了本次持续八轮的跟随失败，代价很小：扣除初始 token 差异后，每轮多携带 32 个输入 token；覆盖后的八轮配对目录费用分别增加 0.000072000、0.000685696 美元。后者还包含服务命中波动，不应全算成说明的固定成本。

Codex 有无说明都在覆盖当轮采用新规则，未观察到额外正确性收益。此次有效的说明明确指出段名、旧值和新值，尚未检验泛泛的“提示已更新”、复杂或相互冲突的规则。因此，不建议立即对所有模型、所有提示更新无条件添加说明；本轮保留实验选项，由维护者决定是否采用及其范围。

## 与 0.87.1 的原场景对照

### 请求结构、状态更新与压缩

三个模型的请求结构都沿用原来的 Pi 路径。Codex 覆盖时保留此前 14 个 input 项，Flash 因不支持中途 system 而把新段折叠到开头，Pro 则保留此前 15 条消息、在后面追加 system。覆盖时公开历史只新增 `plugin:notes`，八个工具声明不变。有无变更说明也不改变这三条路径：说明附在本轮用户消息的末尾，不改写更早的请求前缀。

view 未变化时追加 0 份，变化时追加 1 份；两次批清都删除三份旧 view，使下一请求中的副本数从 4 降为 1。清理前后的顶层提示和工具保持不变，没有重现 Codex 旧基线最初发现、随后修复的提示重排。

压缩事件中，送给两份摘要的 `messagesToSummarize` 与 `turnPrefixMessages` 均不含 view。压缩前已把实际状态改为历史里尚未出现的版本 7；压缩后的请求只有一份当前 view，三个模型的两次回复都读对版本和后缀。压缩输入的证据来自 Pi 的准备事件，后续补回的证据来自 `before_provider_request`；它们不是压缩 wire 请求的直接观测。

### 逐轮用量

Flash 以旧报告中有分项回复诊断的复跑为主基线；旧报告的首次 Flash 运行仍保留在原文件中。初始临时目录的随机名称会带来少量 token 差异，压缩后输入还受模型生成摘要长度影响。

## 变更说明实验

比较窗口是 `override` 至 `view-6-stable` 的八轮。说明只发送一次，之后作为历史继续被携带；模型若立即跟上，再观察七轮是否反复。两个 DeepSeek 模型的无说明组都在第 9 次覆盖后对话——压缩后的第一轮——才采用 B；有说明组在第 1 轮就采用 B。Codex 两组都从第 1 轮开始正确。

Flash 的实验组在覆盖前每轮比对照组少 2 个完整输入 token，覆盖后则每轮多 30；Pro 覆盖前每轮多 2，覆盖后多 34。扣除这两处起点差异，两者均为每轮新增 32 token、八轮累计 256 token。Codex 起点相同，每轮多 36、八轮累计多 288 token。

Flash 八轮的缓存读总量不变，Pro 净少 256，Codex 净多 1,536。请求事件显示说明没有额外改写旧前缀，因此这些配对差值应保留为实际测量值，而不作为说明必然增减缓存的定律。尤其是 Pro，少命中的部分来自 `view-4` 多命中 128、第二批清理后的稳定轮少命中 384，其它六轮相同。

按相同起点校正，Flash 窗口费用差为 0.000076800 美元；Pro 为 0.000664576 美元，其中新增 256 token 按全部未命中计算为 0.000337920 美元，净少 256 个缓存命中对应 0.000326656 美元。这里把额外文本的计数与服务命中差异分开，避免用全部费用差代替说明的独立成本。全流程的差额还包含不同摘要长度，因此费用比较以压缩前窗口为主。

每个模型各有一组完整对照，没有随机化运行顺序；缓存也需要时间落盘。当前结果足以支持采用这类低成本、明确的变更提示作为候选，但尚不是跨模型、跨规则类型的成功率估计。

## Pi、服务与 Repa 的责任

### 请求观察与用量解析

[新测量辅助模块](../../packages/base/scripts/real-model/request.ts)通过已有 `createAgentRuntimeForTest.extensionFactories` 装入 Pi 事件。普通对话使用 `before_provider_request` 比较结构，正文只留在内存，工件只保存计数和判断；原 DeepSeek fetch 探针已删除。DeepSeek 的 2,048 token 输出上限仍保留，与旧实验相同。Codex 的负载直接沿 Pi 原生路径发送。

对照发布包源码，Pi 1.1.0 与 0.87.1 的 `parseChunkUsage()` 相同：先取 `prompt_tokens_details.cached_tokens`，再回退到 `prompt_cache_hit_tokens` 和 `cached_tokens`；非缓存输入是总输入减去缓存读写。因此，旧轮 54/54 的原始响应核对仍支持这个解析口径。本轮直接采用 Pi 历史计数，并用本地真实适配器测试保护字段优先级，不再重复采集原始 SSE usage。[1.1.0 解析源码](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/ai/src/api/openai-completions.ts)、[0.87.1 解析源码](https://github.com/earendil-works/pi/blob/f07218c4d4bbc12bef056a7058c3dd49dfe41abe/packages/ai/src/api/openai-completions.ts)。

Pi 的摘要调用不带 Agent 的 `onPayload`，所以 `before_provider_request` 不覆盖压缩。测量器在 `session_before_compact` 中按准备内容预留输入费用，并为 DeepSeek 预留最多两个摘要请求。Codex 摘要采用默认 `auto` transport，每个摘要最多有三次 WebSocket 尝试和一次 SSE 回退，所以按八次网络尝试保守预留；这不是本轮观察到了八次请求。两种预留都在失败或未知用量时保留，并停止后续调用。[SDK 连线](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/src/core/sdk.ts)、[压缩调用](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/src/core/compaction/compaction.ts)、[Codex 适配器](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/ai/src/api/openai-codex-responses.ts)。

### OAuth 刷新与取消保存

Codex 原场景使用原有 OAuth 完成对话，再通过公开 `ModelRuntime.getAuth(minOAuthValidityMs)` 触发真实刷新。原 `auth.json` 中的 access、refresh 和 expires 都更新，刷新后一次模型调用成功。凭据只在 Pi 的原存储锁内更新，证据只记录布尔结果。

1.1.0 的修复改变了取消语义：caller signal 只取消等待凭据锁；刷新一旦开始，就与 caller 取消脱钩，使用独立的 15 秒网络超时，并在释放锁前保存返回的旋转凭据。0.87.1 把 caller signal 同时传给刷新和保存，因此取消可能丢掉服务已经返回的新 token。[1.1.0 修复源码](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/ai/src/auth/resolve.ts)、[0.87.1 原实现](https://github.com/earendil-works/pi/blob/f07218c4d4bbc12bef056a7058c3dd49dfe41abe/packages/ai/src/auth/resolve.ts)。

[本地确定性测试](../../packages/base/test/real-model-oauth.test.ts)分别在刷新已开始但服务尚未返回、以及刷新已返回但尚未落盘时取消 caller。两种情况下 caller 都立即结束等待，而 Pi 继续把新凭据写入临时文件；下一次认证使用新 token，不再刷新。这里使用真实 Pi `ModelRuntime`、本地 OAuth handler 和带保存屏障的文件 `CredentialStore`，覆盖的是取消与保存机制。真实服务测试覆盖正常刷新及刷新后的使用，两种证据分别承担各自的结论。

核实脚本也把强制刷新作为必须等候保存的短关键操作：开始后即使收到 SIGINT，也等 `getAuth()` 收尾，再阻止后续模型调用。Pi 的 15 秒限制适用于刷新网络，不包含等待文件锁的时间。

### 缓存波动与保温

本轮能明确归因于 Pi 版本变化的是 OAuth 刷新开始后继续保存的语义。三个模型的提示折叠、单段覆盖、工具声明与 view 清理结构则与旧轮相同；DeepSeek 的 usage 解析和目录 TTL 也相同，因此没有发现需要本轮修复的底座问题。

缓存计数发生了变化，但结构证据没有给出新的 Repa 原因：Codex 原场景总命中率从 46.04% 降到 36.87%，主要差在第二批清理后和压缩后的稳定轮各少一次 1,536 token 命中；Pro 从 70.68% 升到 72.14%，主要多了压缩摘要的 640 token 命中。Pro 旧轮压缩后仍答错后缀、最后一轮还答错版本，本轮压缩后两轮均正确。摘要内容、采样输出和服务缓存状态都会变化，这些单次差异应记为服务运行与模型表现的波动，尚不能进一步判成服务升级或 Pi 修复。

DeepSeek [Context Caching](https://api-docs.deepseek.com/guides/kv_cache/) 于 2026-10-10 核对时仍说明：前缀须先落盘，构建需要数秒，命中采用 best-effort。因此 Pro 保留前缀却在覆盖轮得到 0 命中，并不与其公开缓存语义冲突；Flash 则确实发生了开头 system 改写，两者原因需要区分。

三个模型的锁定目录仍都没有 `promptCache.short/long`。Pi 的 cache warmer 与旧版本相同，在 `cache lifetime unavailable` 分支停止；每次 idle 观察 2 秒，普通请求事件增量、模型操作增量及 `cache_warm` 条目均为 0。因此保温仍记为不适用，当前证据覆盖目录与停止路径，并非一次续期实验。[保温实现](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/src/core/cache-warmer.ts)。
