2026-10-10，在 `deepseek-cache-check` worktree 核实底座基线 `fe1d7bca3`，使用本地安装的 Pi 0.87.1、DeepSeek API key 和关闭推理的同一组场景。[上一轮 Codex 报告](base-real-model-check.md)及其冻结证据保持原貌。

两个模型各完成一次完整流程；Flash 首次出现回复判断失败后，补充只读诊断并再跑一次。三次合计 **54 个模型请求、51 次 Pi 模型操作，按目录价格为 0.026442300 美元**。其中每次压缩是一个 Pi 操作、两个实际请求。全部原始 usage 与 Pi 会话用量一致，三次均恢复设置；真实回复存在下文列出的负结果，运行因此返回退出码 1。

### 内容送达与回复正确性

Flash 首次运行有 10 次完整回复判断失败。原证据只记录整体判断，因此保留该文件，另加版本、后缀及格式三个布尔判断复跑，得到以下定位结果：

- **Flash 诊断复跑：** 16 次对话均读对版本、格式正确；覆盖后的八次回复继续使用旧后缀，压缩后的两次才使用新后缀。实际请求的 system 在覆盖后仅含新后缀说明，不含旧后缀说明。
- **Pro：** 16 次回复格式正确，15 次读对版本；覆盖后的 10 次均继续使用旧后缀，最后一次还答错了版本码。覆盖时新后缀已作为中途 system 送出；压缩后开头 system 仅含新后缀，两个请求均携带版本 7 的 view。

这些计数把“Repa 是否送出当前内容”与“服务是否据此作答”区分开了。本轮请求结构符合底座设计，改动集中在核实脚本和测试；模型对更新提示的跟随失败及 Pro 末轮的版本错误仍待定位。它们保留为基线负结果，不用调整夹具或修改底座来掩盖。

## Pi 与服务端的责任

### Pi 0.87.1 的发送与计数

锁定包 `@earendil-works/pi-ai` 的 `dist/utils/transcript.js` 中，`resolveTranscript()` 对不支持中途 system 的模型调用 `collapseSystemMessages()`：重放全部命名段落，生成一个当前 system，再移除中途 system。Flash 的目录没有声明 `supportsMidConvoSystemMessages`，因此走这条路径。Pro 声明为 `true`，保留中途更新的位置。两者均未声明 `supportsMidConvoToolAdditions`，本次八个工具一直放在顶层 `tools`，内容不变。

`dist/api/openai-completions.js` 的 `parseChunkUsage()` 优先读取 `prompt_tokens_details.cached_tokens`，其次读取 `prompt_cache_hit_tokens`，记入 `cacheRead`；`input` 则是总输入减去缓存读写。54 次原始响应中，`prompt_tokens_details.cached_tokens` 都等于 `prompt_cache_hit_tokens`，而 `prompt_cache_hit_tokens + prompt_cache_miss_tokens` 都等于 `prompt_tokens`。原始响应按阶段汇总后，输入、输出、命中、未命中四项均与 Pi 一致，包括每次压缩的两个子请求。

因此，本组合把 DeepSeek 的命中计为 `cacheRead` 是准确的，Pi 的 `input` 对应未命中输入。完整输入仍按 `input + cacheRead + cacheWrite` 计算，与 Codex 报告口径相同。DeepSeek 本次没有单独的缓存写入计数，Pi 的 `cacheWrite=0` 表示没有这项报告值；未命中输入不改称“缓存写入”。本次直接观察同一次 SSE 响应完成核对，无需另发原始请求。

### 当前官方说明

以下官方页面均于 **2026-10-10** 核对；页面未标发布日期或更新日期，日期指核对日。

[Context Caching](https://api-docs.deepseek.com/guides/kv_cache/) 说明，缓存默认开启，当前按已经落盘的完整前缀单元匹配；请求边界、跨请求发现的共同前缀及固定 token 间隔都会形成单元。共同前缀可能需要先被发现、落盘，后续请求才命中。构建需要数秒，服务采用 best-effort，闲置后通常在数小时至数天清除；当前页没有公布固定 token 间隔的数值。

因此，Pro 覆盖时保留消息前缀却得到 0 命中，与服务未保证即时命中的契约相容；usage 没有给出足够诊断来确定这一轮的具体服务端原因。Flash 的开头改写则已经由 Pi 发送结构解释。两者不应归为同一种 Repa 缓存故障。

[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) 将命中与未命中分别定义为 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`，并说明 `prompt_tokens_details.cached_tokens` 与前者同义。最后一个带 `finish_reason` 的流式 chunk 携带完整 usage，测量器在透传该 chunk 前记账。

DeepSeek 的概略闲置寿命不是 Pi 模型目录中的固定 TTL。两个模型的 `promptCache` 都为空，Pi `dist/core/cache-warmer.js` 因 `cache lifetime unavailable` 停止调度，所以本次保温记为不适用，而非一次续期实验。

## 清理代价与建议值

**对本次约 2,000～3,000 token、单来源小 view 的短对话，建议继续使用三份旧 view 清一次。** 批清后的下一请求净减少 149 个输入 token，稳定提示和工具没有变化；第二次批清在两个模型上都只多出 107 个未命中 token。第一次清理更靠前，实际损失明显较大，尤其是 Pro：

| 运行与清理位置 | 命中：清理前 → 后 | 未命中：清理前 → 后 | 未命中净增 | 完整输入净变 |
| --- | ---: | ---: | ---: | ---: |
| Flash，第一批 | 2,304 → 1,792 | 258 → 621 | +363 | −149 |
| Flash，第二批 | 2,560 → 2,304 | 150 → 257 | +107 | −149 |
| Pro，第一批 | 2,560 → 384 | 139 → 2,166 | +2,027 | −149 |
| Pro，第二批 | 2,688 → 2,432 | 159 → 266 | +107 | −149 |

Flash 诊断复跑的两次净增仍分别为 363、107。这里比较的是清理前后相邻请求，包含新增一轮对话与删除旧 view 的共同作用，不能把整个差值当作删除操作的独立成本。首次清理后，下一次状态变化轮的命中率已恢复到 Flash 91.7%、Pro 91.8%。

按目录价格，表中相邻请求的净成本增加分别约为 Flash 0.000106、0.000031 美元，Pro 0.002580、0.000130 美元。三份旧版已能限制旧状态堆积，且本次清理损失短暂、绝对金额较小。仅看缓存价格，减少清理频率有吸引力；但提高阈值会增加旧状态共存，还可能把更长的对话尾部一起重算。这组记录只测了阈值 3，因此建议把它保留为当前已测范围内的工程默认，而不是宣布它成本最优。长会话或明显更大的 view 需要相同轨迹的阈值对照，再决定是否调高。

## 复现与证据

在仓库根目录运行；输出文件必须不存在。默认仍走 Codex，选择 DeepSeek 时显式指定 provider 和 model：

```sh
npm run real-model-check --workspace=@repa/base -- \
  --provider deepseek --model deepseek-flash \
  --output /tmp/deepseek-flash.jsonl \
  --limit 30 --request-limit 50 --cost-limit 0.5

npm run real-model-check --workspace=@repa/base -- \
  --provider deepseek --model deepseek-v4-pro \
  --output /tmp/deepseek-v4-pro.jsonl \
  --limit 30 --request-limit 50 --cost-limit 0.5
```

`--limit` 继续按 Pi 模型操作计数。DeepSeek 另在发送前限制实际请求数与目录估价，压缩子请求也计入，输出最多 2,048 token；按文本请求字节数加消息与工具开销保守预留未命中成本，不预设缓存命中。出现失败或缺失用量时保留预留并阻止后续请求。默认两次各分配 50 请求、0.5 美元；追加运行须扣除已用额度。本次 Flash 诊断复跑使用其剩余的 `--request-limit 32 --cost-limit 0.496500044`。所有运行均关闭自动重试，单次操作限时 90 秒。

[核实脚本](../../packages/base/scripts/real-model-check.ts)沿用公开 Repa 入口；[DeepSeek 测量辅助模块](../../packages/base/scripts/real-model/deepseek.ts)只比较内存中的请求结构、读取原始 SSE usage，并收紧输出上限，不改变提示和 view。除本机协议外，仅放行官方 DeepSeek completion 入口。Codex 不安装这一测量器，原有认证、刷新与用量汇总行为保持不变。安装版本从实际 Pi 包读取，以便升级到 1.1.0 后用同一脚本对照。

三份 JSONL 均仅保存 token、费用、计数、布尔判断和安全状态；[校验值](results/base-deepseek-cache-check-20261010/SHA256SUMS)用于核对冻结文件。第一份 Flash 的整体失败判断保持原貌，诊断数据保存在新文件中。三次运行的临时空间与会话已清理，`~/.repa/agent/settings.json` 与运行前校验值一致。

本次环境为 Linux、Node.js 22.19.0、worktree 自有依赖；项目声明的正式 Node 下限仍为 22.22.2。代码检查全部通过：

- `npm run check --workspace=@repa/base`，含声明构建。
- `npm test --workspace=@repa/base`：72 项，包括真实 Pi 适配器、两种 system 路径、SSE 分块、计数冲突、额度、脱敏和设置恢复。
- 独立只读审阅覆盖认证分流、额度预留、请求透传、计数核对与清理路径。

真实运行完成了三个流程、48 次对话、6 个压缩请求；54 个请求均返回 HTTP 200，51 个阶段的原始与 Pi 用量全部一致。回复失败保留在“内容送达与回复正确性”中，保温因目录无 TTL 不适用。后续 Pi 1.1.0 对照应同时检查请求结构、原始命中和回复判断，避免只比较总命中率。
