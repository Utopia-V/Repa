# 底座真实模型缓存与上下文核实

2026-10-10，使用 `openai-codex/gpt-6-luna` 和 Repa 应用目录中的 OAuth，核实 `base-skeleton` 基线 `73041a8a9`。选择依据是 Pi 0.87.1 内置 Codex 目录中该模型的标示单价最低；目录价格不是订阅额度的结算规则。最终完整运行 [run-05](results/base-real-model-check-20261010/run-05.jsonl) 发出 **19 次模型请求和 1 次 OAuth 请求**，17 次对话回复均读对当前状态，原始 usage 与公开会话记录的合计全部一致。

### Repa 的问题与修复

首轮真实运行发现，底座在 `before_agent_start` 中立即保存 view，早于 Pi 保存原生 system 消息。Codex 只把 transcript 首项当作初始系统提示，因此最早 view 存在时，顶层 instructions 只有 28 个字符，提示与工具以中途更新发送。第一次清理删掉这份 view 后，system 升到首项，instructions 变为 893 个字符，工具也搬到顶层。这个额外的前缀重排属于 Repa 接入问题。

[修复](../../packages/base/src/agent/runtime.ts)使用 Pi 的公开 `deliverAs: "nextTurn"` 队列，让 Pi 先放 system，再放 user 和 view。原来的命名分段、工具声明与上下文编辑机制保持不变。缓存过期且 view 同时变化时，先移除该来源的旧版，再排入新版；普通批清交给原有回合结束钩子。真实复测中，两次清理的 instructions 和工具都未再改变。多来源、批清、TTL 与单段覆盖的回归分别位于 [agent 测试](../../packages/base/test/agent.test.ts)和[协议测试](../../packages/base/test/e2e.test.ts)。

### 服务端和 Pi 的限制

- 服务原始响应明确返回 `cached_tokens` 和 `cache_write_tokens`。本次后者每次都是 **0**，不是字段缺失。清理前后的报告值增量也是 0，但缓存随后能够被读取，因此这个字段不能告诉我们内部究竟重写了多少缓存；下面同时给出未命中输入的变化，不把它冒充缓存写入量。
- 稳定请求也出现 0 命中，服务没有提供足以归因到路由、缓存边界或淘汰的诊断。本次证明了前缀结构可以保留以及实际存在命中，不能据此保证每轮持续命中。
- Pi 0.87.1 的 `dist/core/cache-warmer.js` 依赖模型 TTL，还要求预计节省至少 0.05 美元。当前短会话按目录价格计算远低于门槛。`pi-ai/dist/api/openai-codex-responses.js` 又没有把保温的 `maxTokens: 1` 传成服务端输出上限，所以也不能假定一次保温只生成 1 token。[现有本地补丁](../../patches/@earendil-works+pi-coding-agent+0.87.1.patch)只修复 view 对象身份判断，不能补上这些条件。
- OpenAI 的[公开 API 缓存文档](https://developers.openai.com/api/docs/guides/prompt-caching)说明了 GPT-5.6 以后模型的 `prompt_cache_options.ttl`，但本次使用的是 Codex 订阅后端，锁定适配器没有发送这一选项。这里没有把 API 文档中的寿命直接填成 Codex 的已验证 TTL，也没有放大上下文或绕过收益门槛强行保温。

## 清理代价与建议值

**建议保留当前阈值 3，不在这次核实中调高或调低。** 两次清理都使下一请求的完整输入减少 165 token；这是删除旧 view 与新增一轮对话共同作用的净值，不是旧 view 的独立大小。

第一次清理的位置很靠前。[run-03](results/base-real-model-check-20261010/run-03.jsonl)与 [run-04](results/base-real-model-check-20261010/run-04.jsonl)中，清理前后缓存读取都从 1,536 降为 0，非缓存输入从 589 增至 1,960，即相邻请求增加 1,371 token。最终 run-05 在清理前一轮已经未命中，清理后仍未命中，因而不能把这一轮的全部 miss 归因于清理。

第二次清理时，可复用前缀更长。三次修复后运行均保持 1,536 token 缓存读，非缓存输入从 769 降到 604，没有观察到缓存读损失。两处清理的缓存写字段都保持 0，内部实际重写量无法由本服务的这项计数确定。

因此，3 份旧版已能限制状态堆积，又能避免每次状态变化都删除历史前缀；提高阈值则会延长旧状态滞留。目前没有相同对话轨迹下的阈值对照，3 仍是工程默认值，而非成本最优值。修复后的代价主要取决于删除位置与服务端实际命中，不能再用修复前的提示重排损失来论证增大阈值。

## 测量记录与勘误

五份[冻结 JSONL](results/base-real-model-check-20261010/)仅包含计数、布尔判断和安全状态，没有凭据、完整请求或模型回复正文。原文件保持原貌：

- `run-01`：基线观测。旧记录器遗漏了 SSE 原始 usage，并把 Pi 终态后的 reader 取消标成失败；公开会话的 token 计数和正确回复判断仍可用。压缩走了 WebSocket，未进入其 `totalRequests: 18`，因此该数字只计 HTTP，不能作为该轮总请求数。
- `run-02`：核实器最初也阻止了本机协议连接，启动阶段退出，真实服务请求为 0。随后改为只放行显式登记的本机协议 URL。
- `run-03`：完成模型与 OAuth 流程，共 20 个 HTTP 请求。`checksFailed: 1` 来自核实器把两个压缩请求误按一个条目逐项配对；原始合计 762 输入、336 输出与公开 usage 一致。最终脚本按合计核对，并已有回归测试。
- `run-04`：覆盖前已建立缓存命中，覆盖后保持命中；第二个压缩子请求收到 HTTP 503，停止于该阶段，共 16 个 HTTP 请求。失败请求没有 usage，其 token 数未知。
- `run-05`：最终完整流程，20 个 HTTP 请求，所有回复与用量核对通过，原 Agent 设置恢复成功。

全部记录合计 74 个 HTTP 请求。首轮压缩旁路缺少逐次 WebSocket 计数，按锁定 SDK 最多两个摘要、每个最多三次 WebSocket 尝试计算，**整项任务的请求数保守上界为 80，低于 100**。最终脚本在连接前阻止远端 WebSocket，让 Pi 沿原生回退路径使用 SSE，压缩也进入统一请求账本；run-05 的两次被阻止构造不产生网络请求。

## 复现与检查

在仓库根目录运行；输出文件必须不存在，脚本启动前会构建当前公开包入口：

```sh
npm run real-model-check --workspace=@repa/base -- \
  --output /tmp/repa-real-check.jsonl --limit 30
```

[脚本](../../packages/base/scripts/real-model-check.ts)通过 `@repa/base`、公开客户端协议和 `examples/notes-plugin.ts` 工作。示例原 view 是常量，核实夹具只在其后叠加可控版本，不改变示例工具和文件保存行为。默认运行通常是 20 个请求；覆盖前若尚未命中，至多补两个短请求。所有模型、压缩、OAuth 和失败尝试共用发送上限，单请求限时 90 秒，自动重试关闭。`--limit` 不能超过 100；`--skip-refresh` 可用于只复查上下文，但会跳过刷新核实。

默认凭据目录为 `~/.repa/agent`，可用 `--agent-dir` 指定。运行前关闭使用同一目录的 Repa 进程；脚本临时使用 SSE、关闭推理和自动压缩、设置较短的压缩保留量，结束后恢复原设置。凭据不复制，刷新结果由 Pi 持久化到原 `auth.json`。空间与会话在临时目录中收尾删除；设置恢复有冲突时，保留恢复副本并输出其本机位置。输出 JSONL 中的 `null` 表示不可观测或不适用，不按 0 计算。

本次环境为 Node.js 22.19.0、Linux、Pi 0.87.1 和 worktree 自有依赖；项目声明的正式 Node 下限仍为 22.22.2。以下检查全部通过：

- `npm run check --workspace=@repa/base`，含声明构建。
- `npm test --workspace=@repa/base`：75 项。
- `npm test --workspace=@repa/space-history`：47 项。
- 最终真实运行 `run-05`：17 次状态与提示判断正确，18 个会话用量条目与 19 次模型请求合计对应；无工具执行。

独立只读审阅覆盖了 view 顺序修复、TTL 清理、公开 API 使用与凭据保护。待补的真实证据是保温请求的续期效果，以及不同 view 大小、对话长度下的阈值成本对照；本次没有据此改变保温配置或默认批清阈值。
