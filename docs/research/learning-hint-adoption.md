# 提示内容与后续代码的对应

2026-10-10。[公开提示记录的结构核对](learning-hint-traces.md)已经确认，建议、按钮动作和代码快照可以连接，但这些对象还不能合成一个成功标签。本轮进一步核对六个按日志规则选出的真实场景：先从请求与建议固定具体变化，再查看同一对象的后续代码。结果显示，文字建议与生成代码可能冲突，已记录的修改也可能随后消失；缺少后续快照的场景则保持未判定。匿名结果与计数见[核对结果](results/learning-hint-adoption-20261010.json)。

## 来源与选取范围

原件仍是 Anastasiia Birillo、Aleksei Rostovskii、Yaroslav Golubev 和 Hieke Keuning 发布的 [Zenodo 17551130 v1](https://zenodo.org/records/17551130)，许可为 CC BY 4.0。本轮使用同一份已校验 ZIP，SHA-256 为 `5527127f0a3c939601b17ef207ef8b34df7cad9159c9617f879efbf4e989d499`。这里发表的是对原记录的新分析；原代码、提示全文、个体标识、文件路径及绝对时间保留在私有工作层。

选择只使用报告中的 Log。报告须恰好有一次代码请求和一次随后的代码生成；从生成记录之后到报告末尾，分为无 Show／Accept、有 Show 而无 Accept、有 Accept 三组。每组按请求 UTC 时间、原报告顺序排列，取前两个不同父目录的报告。目录表示发布分组，不作为已认证的不同参与者；组间可以重复，也不据六例估计总体采用率。

合计 734 份报告符合条件，其余 316 份保留排除原因。这里的组数按代码生成及其后窗口计算，因此与全包的按钮总数不同。六例中有一例曾在前一轮结构核对中读过，明确标记为已知样本；其余案例没有根据后续代码、执行次数或判断难度筛选。没有记录、没有实质建议和内容冲突都保留在原选择中。

## 先明确在判断哪一项建议

请求可能只提供一个函数，生成代码却包含整份文件。因而，整串不相同还不足以说明函数有新修改；包声明等范围外内容也不能被补成请求时不存在。本轮先读取原请求与生成内容，固定局部候选，再打开后续快照。

这一步发现一例渠道冲突：文字要求对字符构造频率表，使用 `groupingBy` 与 `eachCount`，代码却把目标函数的表达式留空。因此，统一以明确文字建议中的第一项实质要求为主候选，生成代码是否实现同一要求另外记录。这个解释在读取后续内容前固定，对全部六例一致使用。

这样的区分也影响 Accept 的解释。它是接受代码提示的动作，不是承诺实现文字说明。假如后续代码对应了一个与文字冲突的 payload，就应分别说明两种对应，而不是用文字未满足来否认代码曾被应用。相反，文字明确表示无需修改、对应函数也保持原样时，本轮记为“无新候选”，不另造一个“成功保持”的采用结果。

## 六例实际记录了什么

每例都从 non-Log 的实际研究 ID 取得文件视图，而不是用报告目录数字连接原表。共 436 条报告代码快照在原 CSV 中找到唯一键，原字段、带时区日期和代码正文一致。原表还为每例提供了 11 个文件名的请求前最近快照；文件枚举本身不决定哪个文件属于本次建议。

两个有 Accept 的案例，在唯一一份请求前文件快照中找到了完整请求函数，后续记录也保持同一文件身份。另两例只能通过局部内容比较或首份后续快照中的完整请求片段支持对应；它们最近的请求前快照并非逐字相同，不能据此倒填请求时状态。其余两例没有窗口内代码快照。下面的结果始终限定在已定位的目标函数，不把其他课程文件中已有的相似实现算进去。

| 案例 | 日志条件 | 固定的局部对象 | 后续代码记录 | 判断 |
| --- | --- | --- | ---: | --- |
| G1 | 无 Show／Accept | 请求与建议中的函数相同，没有新修改要求 | 127 | 无新候选；后续编辑不被统称为采用提示 |
| G2 | 无 Show／Accept | 替换一条输出语句的字符串 | 0 | 未判定；请求前旧快照与请求片段不同，不能用旧快照代替后续回答 |
| S1 | Show、无 Accept | 请求与建议中的函数相同，包括字符串内部末尾空格 | 0 | 无新候选；另无后续代码可供比较 |
| S2 | Show、无 Accept | 用指定分组与计数操作建立字符频率表 | 115 | 未观察到完整文字要求；后续出现的是 `groupBy` 与 `eachCount`，不是冻结的 `groupingBy` 要求 |
| A1 | Show、Accept | 在指定输出前声明类型明确的局部 Boolean 变量 | 100 | 一份快照符合，下一份删除了相应函数体；最后快照也没有该声明 |
| A2 | Show、Accept | 将目标函数改为使用过滤与长度的单表达式函数体 | 94 | 前六份未符合，之后 88 份保留了所指局部表达式 |

S2 的后续代码与建议主题有关，但部分 API 名称相近不足以满足执行前固定的要求。这里评价的是明确的局部谓词，不是完整任务能否通过。A2 同样只确认目标表达式；其他函数仍在编辑，局部相符不会把整份文件自动变成正确答案。

这六例没有形成“有 Accept，却从未记录到主候选”或“无 Accept，却记录到完整主候选”的明确反例。因此，当前结果不用于推翻所有“接受后曾出现建议修改”的解释。它已经说明的是：曾经记录到相符内容，不保证窗口末仍然保留；无后续记录也不能按未采用处理。

## 快照时间与真实修改时刻

两个 Accept 案例的首次相符快照都在按钮记录之后，但最后一份不相符快照又略早于按钮。两份状态记录之间的间隔分别为 162.233 秒和 152.439 秒，Accept 都落在其中。因此，可以描述首次记录的先后，却不能由这些记录确定代码实际何时被修改、按钮是否造成修改，或学习者何时理解了建议。

A1 的相符快照与下一份已删除快照只相隔 0.012 秒。这个数字描述两个记录时间，不是该代码只保留了 0.012 秒的证明。当前尚未核定采集器在编辑前后哪一刻保存正文，也没有连续观测所有真实状态，实际首次变化时刻保持未知。

六例在请求与生成之间均没有代码快照。请求片段仍提供一份明确基准，但这个空段不能被解释成学习者当时没有修改。观察窗口也都止于报告末尾；“后续保留”仅指窗口内已保存的快照，不延伸为之后继续保持或已经掌握。

## 对后续实现的影响

当前[作答与判断入口](../development/learning-attempts.md)已经可以表达这些区别。固定资源与定位保存文字、代码和快照各自的对象；同一份事实可以有不同的 `criterion`，分别评价文字要求、指定代码对应或最后一份记录中的保留情况。按钮动作与帮助条件仍按原来源保存，不能替代这些内容判断。

因此，本轮没有新增“采用成功”字段，也没有把六个手工判读案例包装成通用 Kotlin 判分器。程序适合承担固定资源、版本与引用校验；文件绑定、局部内容含义及记录的解释范围则需要足够依据。已有接口能够保存判断，不等于这些语义已经被程序自动识别。

这轮少量内容核对到此收束，不在同一批案例里更换谓词或延长窗口寻找更有利的结果。学习状态与任务选择仍需要具体要求、实际帮助条件及后续独立表现；本轮为它们确定了哪些记录可以消费、哪些关系还需要保留未知，而没有提供教学率或学习收益估计。

## 验证范围

选择实现的六项合成测试、后续视图提取的七项合成测试通过。独立选择核对逐项比较全部 1,050 份候选状态与 734 份符合条件的记录，并重新核对选中六份报告中的十二个请求／生成事件；选择顺序与原事件一致。

后续视图一次读取六份 HTML，共 6,410,996 字节，以及 document CSV 的 119,214 行、258,869,032 字节，总展开读取量为 265,280,028 字节。独立实现另从原件复算六例的身份、436 条代码连接、66 份请求前最近快照及全部区间选择，结果一致；所有区间原表行也有对应报告快照。原件与冻结候选的摘要前后相同。六例的内容解释由独立审阅核对；这里的读取与判读都不执行学生程序，也不作为产品学习效果验收。
