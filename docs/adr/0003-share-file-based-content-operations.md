# 以文件保存正文并共享内容操作

本记录约定目标设计；当前实现范围与运行方式见 [README](../../README.md#运行现有-tui)。

## 文件与内容组成

学习空间以文件形式保存文档正文，程序维护长期引用所需的身份、位置和修订。文档读者可以是用户、Agent 或两者，共用相同的内容能力；来源材料按其来源与原件生命周期管理。文件能直接供用户、Pi 通用工具和扩展读取，也方便兼容外部编辑。将结构化存储作为正文权威、再提供文件视图，会增加投影、导入和冲突处理成本；当前选择文件正文，并由 Repa 承担跨文件变更与恢复。索引、操作历史和能力自身的结构化业务数据按各自责任选择存储方式。

新建文本类文档默认采用 Markdown。编辑器可以提供源码、富文本或其他视图，各视图共用实际保存的源内容；已有材料保持原格式。代码、交互产物及其他内容形式通过相应能力使用共同的身份、修订与内容操作。

一份文档可以由单个文件或具有明确组成关系的多个文件承载。整体与成员按实际引用和编辑需要取得身份，成员可以独立读取与局部修改；保存、移动、复制与撤回按操作涉及的组成和依赖关系处理，必须共同完成的变化才协调提交。内容组成、使用方式及具体格式通过相应能力的契约表达，产物形态随能力组合扩展。

## 能力数据与数据库

复习项、实际复习记录、调度状态和算法参数等结构化数据由对应能力拥有，可以使用数据库作为权威存储。数据库承载需要查询、事务更新和持续演化的实体；文档正文沿用文件存储，两者通过稳定内容引用及需要保留的来源修订关联。能力定义自身的数据模型和学习方法，核心提供存储所属空间与生命周期的接入约定。

插件可以随包引入兼容宿主的数据库依赖，SQLite 等嵌入式数据库可作为本地能力的实现选择。插件的数据服务拥有 schema、事务、数据版本与迁移，前端和 Agent 工具通过相应能力的查询与操作使用数据。算法库的选择和调用留在对应插件或其依赖中。多个插件实际需要相同的存储辅助操作时，可以共享可选适配库；基座不统一管理业务实体、算法类别或数据库表。

复用现成调度算法时，实际复习记录和所用算法版本、参数分别保存，便于更正反馈及重新计算。用户记录与不能重建的状态属于持久数据；索引和能够依据保留记录重新生成的计算结果才可按缓存处理。仅提供工具或提示的插件无需声明数据库、迁移或快照接口，使用持久数据的能力再接入所需生命周期。

空间协调备份、搬移与独立复制，向持有数据的能力取得可保存的一致快照；能力解释自己的数据版本、恢复与必要引用映射，基座不扫描数据库表来推断业务关系。活跃数据库通过其已有快照机制参加，例如 [SQLite Online Backup API](https://www.sqlite.org/backup.html)。数据库内事务由所属数据服务负责，确需共同完成的文件与数据变更按实际操作接入保存和恢复；引入数据库不自动要求全局跨插件事务。禁用或卸载插件时关闭相应运行资源并保留数据，重新启用或兼容实现接续时核对数据版本。

## 材料与资源生命周期

持续维护的产物连同必要源内容、数据与资源一起保存，生成能力交付其所需依赖。会话、文档及保留的历史分别记录必要资源的保留关系，保存为长期文档时建立文档自己的关联，其可用性独立于原会话清理。相同资源字节可以复用存储，保留关系仍分别成立。普通内容引用用于解析目标，引用外部材料本身不产生原件的历史副本。

已受理请求保留继续执行所需的输入资源，包括尚未开始的排队请求；输入进入会话、会话建立分支或产物保存为文档时，相应记录各自保留所需资源。回收同时考虑仍需保留的请求、会话、文档、历史关联和活跃使用，清理原会话不破坏分支、文档或仍有效实例中的资源。

活跃展示对实际使用的受管理内容版本与资源建立临时持有，资源取得与释放由宿主统一处理。清理旧历史可以移除历史入口，仍被实例使用的字节在使用结束前保留；相同字节继续共用存储。保存结果或提交后台处理时，为相应文档或请求建立独立的必要资源保留关系；仍在使用的资源继续由展示实例持有，在实例关闭或不再使用时释放。临时持有属于宿主生命周期，不另建内容历史记录，也不自动保存外部原件的历史副本。

空间外材料默认引用原文件。加入材料时可以先登记身份、位置和基本说明，再按需进行文本提取、转写、索引或其他处理；处理任务拥有自己的进度与结果，缺少某种格式的处理能力不影响材料关联本身。材料读取以关联目标的实际可用状态为准。

重新定位同一原件或更新同一材料保留身份，更新记录实际观察到的新修订；加入另一份材料或独立复制建立新身份。将已有外部关联材料收进空间，属于同一材料保存方式的变化，保留身份并改为读取空间内副本，同时保留来源说明。操作意图由用户或 Agent 决定，文件名不单独决定是否是同一材料。

材料当前不可用时保留其身份、引用说明以及相关笔记和批注，重新找到原件后可以恢复关联。移除关联保留外部原件与已有文档，来源不可用和删除学习产物分别处理。引用可以携带页码、时间点、标题或文本片段等定位信息，并按需保留引用时所见的修订或摘录；材料变化后按实际使用需要核对，能够确定的定位可以更新，无法确定时保留原说明并返回待核对信息。

可重建的提取文本和临时索引作为缓存管理，校订稿、批注与整理说明作为文档维护，拥有自己的修订。重新处理原件可以生成新的处理结果，已有长期文档通过比较、合并或明确替换更新。缓存重建不覆盖这些文档，引用时的修订信息也不自动保存整份历史原件。

## 空间身份与内容引用

空间以独立的内容清单保存身份与位置关联，默认放在 `.repa/` 的可读结构化文件中。清单的基本记录包括标识、文档或材料角色，以及空间内相对位置或外部位置；来源信息按实际需要补充，多文件内容的组成与必要资源关系随相应持久记录保存。正文、派生索引和操作历史分别保存。清单属于不可仅从正文重建的持久数据，搜索索引和反向引用属于可重建数据。独立身份在实际操作或长期引用需要时建立，无须在首次读取每个文件时分配，也不要求每份文档写入管理用 front matter。

搬移学习空间时，空间内文档、材料副本与必要元数据一并保留，内部位置使用相对关系，内容引用继续在所属空间内解析。完整备份包含希望保留的历史，派生缓存可重建；外部原件仍是空间依赖，搬移后检查关联并支持重新定位。需要空间自包含时显式收进选定材料，目录整体换位置时可以检查对应文件并批量重新关联。

搬移或恢复学习空间保持空间身份；需要独立演变时，复制建立新的空间身份，并保留副本内内容引用的对应关系。同一空间身份的两个目录不能同时作为独立空间打开。空间内副本不自动复制应用侧模型连接、凭据或本机授权。

Repa 创建的内容引用使用稳定身份，在所属学习空间内解析。Markdown 保留普通链接语法，链接目标的语义形式为 `repa:document/<id>` 或 `repa:material/<id>`，可附加页码、标题等来源定位信息；标识编码和各类定位信息的细节随接口定义。程序生成引用，前端显示正常的链接文字。普通路径链接继续按路径解析，不自动获得身份引用的移动与重新关联语义。

外部 Markdown 编辑器可以读取和编辑这些文档，跳转 Repa 引用需要 Repa 支持。面向外部的导出可以将身份引用转换为当时的相对路径或来源位置；这种转换的结果遵循导出目标的链接语义。引用默认解析当前内容，固定历史内容需要显式副本或版本记录，单靠身份引用不保存材料的历史正文。

## 共同内容操作

前端与 Agent 的内容工具共用程序入口。一次内容操作维护其确定的修改与引用关系，统一处理冲突、失败和恢复。文档改名、移动以及材料重新关联位置保持身份；独立复制产生新身份，旧引用仍指向原内容。删除内容或移除材料关联后，身份引用返回目标不可用，不绑定同一路径下的新文件；恢复原对象时恢复其身份关联。拆分通常让保留的原文档沿用原身份，拆出的文档获得新身份；拆分、合并所需的组织方式与引用迁移由用户或 Agent 决定，程序执行确定的变化。

Agent 工具与前端按各自使用者提供调用形式。模型日常沿用适合当前能力的 `read`、`edit`、`write` 等工具，通过适配层进入共同内容操作；修改基准、冲突和实际结果按工具契约表达。直接将完整应用协议作为模型工具，可以省去一层映射，却会把空间标识、操作记录等程序职责带入模型参数。保留工具适配的取舍，是用一层集中的映射维护常用工具的使用方式，并让匹配、提交和恢复始终由共同内容模块负责。

内容操作的标识由工具执行适配层或前端客户端在提交前产生，并与实际调用来源关联。同一次提交的重传复用标识，以查询或返回原操作的结果；新发起的修改使用新的标识，即使参数相同也不自动合并。模型日常编辑无需生成或管理操作标识，需要查询或撤回时可以使用工具提供的标识。

一次 Agent 请求可以产生多次陆续保存的内容操作。普通内容修改工具以一次实际提交形成自然的保存边界；读取、搜索及随后对下一步修改的判断不需要预先纳入这项操作。需要共同完成的确定变化才组成同一项操作，例如拆分文档涉及的原文档、新文档、内容清单与已经确定的引用迁移，以及相应的组成和资源保留关系。取消 Agent 时保留已完成的操作，进行中的操作按自身恢复规则收尾。历史分组用于呈现和选择撤回，可以包含多项已经分别提交的操作；分组不改变原有提交与恢复边界。这样既能按一次工作查看修改，也允许 Agent 边探索边保存。

同一空间内经 Repa 入口提交的修改共用提交协调，条件检查与实际保存处于同一协调范围。空间内单一提交队列作为简单的实现方式，Agent 的阅读、模型生成和资源准备可以并行；内容读取与订阅在完整提交边界衔接。判断围绕本次涉及的内容及其匹配、修订和位置条件，不比较各 Agent 的全部历史或判断内容分歧的对错。更细的并发机制以实际瓶颈为依据，外部程序直接写入仍按外部变化处理。

学习语境的组成关系可以复用同一套内容引用。文档移动后仍可解析，从语境中移除成员只改变组成关系，不删除所引用的文档或材料。

## 编辑与保存

日常交互沿用阅读、搜索、局部编辑和写入，由 Agent 根据当前任务选择所需工具与阅读范围。局部编辑直接针对当前内容的明确文本或选区应用，保留其他位置的内容，并返回实际 diff；匹配失败或有歧义时提供相关片段或匹配位置，供补读和重试。字符、标点与空白变化按实际请求处理。

文本定位与实际写回分别处理。宽松比较可以帮助确定位置，不能将比较时规范化的正文或上下文整体写回。Pi 0.87.1 的编辑实现仍存在扩大同一行字符变化和统一换行的行为；Repa 复用工具参数与差异展示，定位和保存由内容模块完成。补丁定位借鉴 Codex，但未修改原文的保留规则由 Repa 的内容契约持有。当前核验见 [Pi 0.87.1](../research/pi-ecosystem-compatibility.md#12-pi-0871-的接入与升级)，最初比较及固定 Codex 源码见 [编辑行为比较](../research/pi-ecosystem-compatibility.md#10-pi-0843-的工具与服务复用边界)。

这些约定来自共同编辑与长期内容的需要。数学笔记、代码和数据中的字符可能具有实际含义：在 `公式 x²；标记：ＡＢＣ` 中替换标记，不应顺带把 `x²` 改成 `x2`。前端打开旧版本后继续输入，也不能在保存时无意覆盖 Agent 已完成的修改。局部编辑、整篇保存和共同提交分别处理这些问题。

| 当前选择 | 解决的问题 | 代价与可调整部分 |
| --- | --- | --- |
| 局部编辑按当前内容匹配，保留范围外的字符与换行 | 修改一个片段的影响可预测，数学符号、代码和已有排版不会附带改变 | Repa 维护匹配与补丁逻辑。宽松定位的具体规则可调整；显式格式化可以修改更大范围 |
| 整篇覆盖检查实际观察过的修订 | 较早打开的编辑器、其他会话和外部编辑不会被无声覆盖 | 冲突时需要补读或合并。Agent 读取相关片段即可取得版本基准，不要求为小改动阅读全文 |
| 前端与工具共用保存入口 | 身份、正文、组成和恢复记录在确定的操作边界一起成立 | 需要工具适配和文件恢复实现。只替换 Pi 的写文件回调不能覆盖匹配到保存之间的变化 |
| 一次确定修改形成一次操作，按空间协调提交 | 重传可查结果，多文件修改能够恢复，取消运行保留已完成内容 | 大型操作会占用提交队列；是否细分并发应由实际等待情况决定，模型的整个探索过程不进入一个大事务 |

这里保留的是修改意图、并发保护与长期内容的语义。匹配策略、并发粒度和上游适配方式可以继续评估；当上游实现能够满足相同行为时，应收缩自有实现。修改这些选择时同步更新接口与对应行为测试，不将当前代码或某个 SDK 版本的限制当作永久需求。

官方编辑器默认自动保存，其他前端可以选择自己的提交时机。后端完成写入后才返回新修订与实际 diff，前端据此显示已保存。连续输入可以在历史界面归为一组，Agent 修改或外部编辑介入后形成新边界。匹配、修订记录与恢复准备属于内容模块内部职责。

内容操作的提交指将一次确定的修改交给后端保存。是否向会话发送请求或要求 Agent 读取内容，由相应会话行为决定；普通文件如何告知 Agent 按[变化告知策略](0002-progressively-load-learning-context.md#普通文件的变化告知)处理。

整篇覆盖、前端保存较早打开的文档，以及需要绑定版本的结构性修改，使用修改基准（base）检查期间的变化。程序负责匹配、写入和明确的冲突反馈；模型通过必要的阅读与重试处理语义和定位问题。历史、撤回与中断恢复共用变更记录，保存实际涉及的内容身份、位置变化、修改前后修订及恢复所需的正文，相同正文可以去重复用。文档历史属于学习空间，独立于产生修改的会话；外部来源材料的历史原件仍只通过显式副本或版本记录保留。

## 恢复、撤回与外部变化

跨文件操作先准备可恢复的记录，再应用修改，确认完成后发布完整结果。写入失败或重启发现未完成操作时，检查相关文件的实际状态；仍处于预期状态时恢复到操作开始前，发现后续变化时保留当前内容并报告具体冲突。Repa 的正常内容结果在完整操作边界发布；恢复未完成时的现场读取明确携带问题状态，不作为已经确认的完整结构。外部文件访问者不参与同样的提交协调，可能观察到中间状态。

恢复冲突沿用已有记录保存未解决操作及其影响范围。实际文件查看、搜索、差异比较和修复所需编辑继续可用；依赖尚未确认的身份、位置或组成关系进行查询与修改时，返回可解释的待恢复结果。需要展开这些未确认内容的语境准备同样返回原因，已确认不依赖这些关系的内容与会话正常使用，不把不确定关系伪装成正常修订。

能够机械确认的恢复自动完成，需要理解内容的部分由用户或 Agent 判断，并通过已有内容操作修复。内容模块核对身份、位置与组成已经能够准确反映当前文件，保存修复结果后解除相应状态，原中断事实继续保留。修复既可以安全恢复到修改前，也可以保留后续内容并补齐当前关系；明确的来源缺失或目标已删除仍是可表达的领域状态，不要求所有引用都能打开。

这项取舍参考 [Git 的冲突检查、编辑与完成流程](https://git-scm.com/docs/git-merge)，以及 [SQLite 在恢复一致状态后提供正常读取的原则](https://www.sqlite.org/lockingv3.html)。外部文件的恢复仍由 Repa 的内容操作负责，SQLite 本身不替这些文件完成事务。

**实践观察点：** 通过真实外部编辑、中断恢复和日常使用反馈，观察影响范围是否误伤无关操作、现有文件与内容操作是否足以完成修复，以及是否反复出现难以结束的待恢复状态。出现这些反馈时，再调整保护范围或修复入口。

撤回作为新的内容操作记录。程序利用修改前、修改后与当前内容，合并能够明确区分的变化；重叠或含糊时保留当前内容并提供相关差异。结构撤回同样检查后续编辑、内容身份和位置占用，原修改与实际交流继续保留为历史。学习判断的语义影响由用户或 Agent 理解相关内容后修正。

内容能力适配 Pi 的通用读写工具，复用适合文档契约的调用方式与实现，在需要版本保护的操作中接入修改基准。执行修改时的当前内容读取、匹配检查和实际保存一起进入共同内容操作的协调范围，仅替换工具的写文件函数不足以形成该保证；Pi 的单文件修改队列也不替代空间内共同提交与跨文件恢复。通用 shell、第三方代码及应用外编辑直接修改文件时，按外部编辑重新读取、更新修订与视图并检查引用，保留前端已有草稿。Repa 只能记录实际观察到的版本，应用关闭期间未观察到的中间编辑不作为可恢复历史承诺。外部改名、移动或拆分后，确定的身份与位置关系可以更新，无法确定时提供重新关联与归属处理入口。

这些长期责任属于学习空间，独立于 Pi 会话。规划、整理、练习等能力共享内容引用、修订和操作支持，各自定义所需的内容约定与学习方法；Pi 继续承担 Agent 扩展的加载与运行。
