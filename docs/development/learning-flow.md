# 教学流程与判分

学习插件通过 `menu.select`、`task.advance` 和提交方法组织上课与复习。每个方法读取从[学习记录](learning-records.md)里的事实重放出的当前状态，核对守卫，再追加学习者行为的事实；界面读取[学习契约](learning-protocol.md)恢复画面。

## 设计思路

一道练习答对以后，程序需要知道它是否独立完成，以及它改变了哪个 KP 的进度。因此，判分先回答作答是否正确，教学流程再看作答之前有没有求助的事实，判断它能否作为独立完成的证据。求助后的正确答案仍保留正确反馈，但不会计入连对；聊天、讲解和例题也不建立已学状态。

每个 KP 先展示讲解和例题，再进行练习。两次连续独立正确后进入下一 KP，每个 KP 最多尝试五次；第五次先检查两连对，全部 KP 通过才完成 lesson。这部分沿 MA 公开的课内规则，见[官网课内流程](https://www.mathacademy.com/how-it-works)和 [The Math Academy Way，第 397 页](https://www.justinmath.com/files/the-math-academy-way.pdf#page=397)。重试没有进一步推进时才补关键先修，也沿[公开的补救方向](https://www.mathacademy.com/how-our-ai-works)。

以下数值和完整调度策略属于 Repa 假设：失败后冷却 48 小时，重试保留已过 KP；复习最多五题、至少三对且最后两题连续对，限时 10 分钟；菜单最多三项，避免相近项，并在连续三个 reviews 后提供合法新课。复习期间关闭辅导和参考读取是维护者决定，与 MA 可查 lesson 的做法不同。

没有证据就既不算对也不算错。判分途中关掉窗口、判分服务失败、模型表示没有把握时，这份作答只有作答事实、没有判分事实：它不计入尝试次数、连对和复习结果，也不阻塞任务，学习者可以继续下一题、中止任务或交卷。任务结束时若还有这样的作答，而它们判出来可能改变结论，结论就先待定（`unresolved`）：任务照样结束、菜单照常提供，但不因它们记失败、做失败更新或强制补救。条件具备时程序自动补判，追加的判分让任务结论和学生状态随之重算。

## 实现细节

### 任务、菜单与重算

`flow.ts` 装配插件方法，`session.ts` 提供方法与辅导共用的当前状态、判分和写入，`replay.ts` 按事实重放学习状态，`flow-state.ts` 从一项任务的事实得出证据与结论，`flow-menu.ts` 对学生模型库的完整候选应用教学资格。新课要求直接先修已学；到期本身不撤销资格。相同 topic、直接依赖或共享直接先修的候选不同列。菜单每次读取时按学习状态、当前时间和调用方能否运行 Python 当场算出：候选的编号由类型和 topic 得出（如 `lesson-t01`），菜单编号随任务数变化，所以刷新和重开不重抽候选，也不写任何事实。失败冷却且没有其他任务时，菜单提供原因和最早恢复时间。

任务的阶段同样从事实得出：课从第一个未过 KP 的讲解开始，`viewed` 事实记下翻到哪一页讲解或例题，`delivered` 事实记下出了哪道题；作答之后按判分事实显示反馈。任务的结论先看作答（课的两连对与五次失败、复习的通过与失败），再看学习者主动结束（`ended`）、截止时间和是否已被后来的任务取代。

默认插件通过 `connectLearning` 的 `hooks.beforeRestricted()` 接入[辅导中止](learning-tutor.md)：程序先写下任务事实，任务停在 `preparing` 并关闭辅导与参考读取，再等待底座中止路径完成，随后交付第一道题，从这一刻开始计时。准备失败后，`task.resume` 沿原任务继续。

复习按任务事实序号得出的 seed 打散 KP 顺序，先轮流覆盖 KP，再补余题。交付优先未见题，耗尽时重复并标记。每次交付从系统熵取一个 seed 记进交付事实；选项、排列块和选择格的顺序与不透明编号由它确定，所以重开时按同一个 seed 重建同样的画面，不重新洗牌。数据行顺序保持原样。

首次进入一轮强制重教时清除上一轮的 KP 进度和失败位置；这一轮失败后的重试保留已通过 KP，只重置未通过 KP 的尝试数和连对数。进行中的课按重算后的学习状态继承 KP 进度，所以更早任务的重判也反映到当前的课上：例如第一轮通过 KP1、在 KP2 失败，冷却后的重试继承 KP1；这时申诉把第一轮 KP1 的关键答案改判为错，重试的课就不再继承 KP1，即使已经通过 KP2 也回到进行中，与学生模型和菜单一致。课开始时继承的进度另外冻结一份，只用于结算这节课的 XP，已经给出的 XP 不因此收回。

初学只在整节通过后调用 topic 级模型更新。lesson 首次通过质量取 1；review 通过取独立正确数除以有证据的题数，失败取 `max(0.2, 1 - 独立正确数/有证据的题数)`，无作答超时取 1。它们都是 Repa 假设。正式作答引起的更新以最后一份有证据的作答的接受时间为锚点，判分服务延迟不把旧表现当成新的表现。更新和预演都沿模型库默认配置，关闭隐式传播。严重逾期时，一次通过后仍到期就继续按实际状态调度。

关闭空间不暂停计时。截止时间过后读取状态或请求中止，先按截止时刻结束任务，旧守卫收到携带终态的 `stale_state`；超时的模型更新时刻取原截止时间，使关闭后延迟打开不改变这次更新的锚点。截止时还没判出结果的作答不阻塞：任务按时结束，这份作答暂无证据。复习里这些作答都判对就能通过时，结论待定（`unresolved`），不做失败更新，也不把强制复习转为重教；它们怎样判都不能让复习通过时，已有失败的证据，照常按超时结束。补判出结果以后结论随之重算，先看通过，再看五次失败，最后才算超时。测验的结论见[测验与进度说明](learning-quiz-xp.md)。

### 判分、补判与重判

规则题复用 `gradeSlot`；开放题经 `completeStructured`，只发送本题、作答、参考解与 rubric；代码题经前端的 `python.run`，见下一节。判分按当前课程里的题目定义进行，结果作为 `graded` 事实追加，记下所依据的题目版本、各作答位的结论、测试结果和模型理由。

判不出结果时什么也不写，只在内存里记下原因，界面看到 `interrupted` 和 `service_failure` 或 `uncertain_grade`；重开以后原因显示为 `restart`。这份作答尚无证据，课和复习可以从 `recovery` 阶段用 `task.advance` 继续下一题，`task.abort` 与 `quiz.finish` 也不再等待判分。补判有三个时机：

| 时机 | 补判哪些作答 |
| --- | --- |
| 打开空间 | 规则题当场判完：崩溃时没来得及判的作答，以及按改正后的答案要重判的作答 |
| 每次方法调用 | 本次会话还没试过的作答在后台补判；代码题只在调用方声明 `python.run` 时补判，开放题在第一次调用时调用模型 |
| `submission.resume` 或同载荷的重交 | 学习者显式要求，立即再判一次 |

每份作答每次会话最多自动尝试一次，所以服务一直不可用时不会反复调用；判分结果落盘后发出 `learning.changed`。学习者的值太大（`too_large`）、期望值算不出来等测试没有结论的情形也按尚无证据处理，下一次会话会再试一次。

题目的答案改正后，过去的作答按新答案重判。打开空间时，程序对每份作答比较两件事：学习者当时看到的题面版本与现在的是否相同，最新判分所依据的题目版本与现在的是否相同。题面相同而题目版本不同（改了答案、判分方式，或代码题判分用到的课程运行前导），就按新定义重判；对错两个方向都生效，新判分追加在后面并取代旧判分，旧判分保留。XP 只增不减，不因重判收回，见[测验与进度说明](learning-quiz-xp.md)。题面已经变了的作答不再重判。知识点归属（`measures`、`uses`）不进题目版本，改归属不会触发重判，重算学习状态时直接按新归属算。

申诉先追加 `appealed` 事实，再按当前题目定义重判；新判分追加，作答、旧判分、已选任务和交付保留。已选任务若失去先修资格，后续推进和新提交会报告 `stale_state`，学习者可以中止后重新选择。反馈页通过作答定位已交付的 KP；重判使它之前的 KP 重新未通过时，同样阻止推进，而当前 KP 正常通过后仍可进入下一 KP。当前任务是已完成的课时，重判使它不再通过，这节课就回到进行中。

历史重判也会改变补救路径：仍有已学状态的 topic 强制 review，失去已学状态的 topic 则转入 lesson；lesson 所需但尚未学会的先修一起进入补救。重放负责形成这份可执行要求，菜单与已选任务的开始检查共用 `topicEligible`，避免菜单提供自身资格检查必然拒绝的唯一任务。

### Python 内部执行边界

代码题和带测试的 Parsons 题经前端服务 `python.run` 判分，协议是 `@repa/python-runner/protocol` 的 `repa-python-batch-v2`（[protocol.ts](../../packages/python-runner/src/protocol.ts)），Web 与 Desktop 用运行器包提供这项服务。能否运行 Python 只看前端连接时是否在 `capabilities.services` 里声明了 `python.run`：菜单、交付和补判都按发起调用的前端当场判断，不调用服务探测；没有声明时，选题跳过代码题与带测试的 Parsons，某个 lesson 的未过 KP 没有可用题时不提供该 lesson。

判分（`judge.ts`）调用检查工具也用的入口 `runCodeTests`（[code-tests.ts](../../packages/learning/src/code-tests.ts)），用法见[学习插件说明](../../packages/learning/README.md#代码题的测试)。一次提交只调用一次 `python.run`：

- 请求只有协议名和有序的 `tests`，不带提交编号、判分版本、运行环境或 runner 摘要；后端在等这次调用的结果时就知道它属于哪份提交。前面是每个带 `expect` 的测试的期望任务（程序为空串，对期望表达式求值），后面是学习者程序的各个测试（program、prelude、setup、夹具、captures 和 doctest 输入）。参考解、`verify` 和 doctest、`stdout` 的期望输出不发给前端。
- 结果按同样顺序给出每项的 `completed`、`timeout`、`failed` 或 `not_run`，并记下实际加载的版本，后端不拿它比较。超时和失败带 `prepare`、`program`、`capture`、`doctest` 或 `cleanup` 阶段；某项超时或失败后整批停下，余下的只能是 `not_run`。`completed` 带 `restoreError` 时结果照样有效，前端已经换了新的 Worker 运行余下的测试。
- 后端核对结果与请求一一对应、顺序相同、停下前后的状态合乎约定，不合时按服务失败处理。比较在后端完成：学习者的程序、capture 求值或 doctest 超时，以及比较不符，形成判分；准备与收尾超时、`failed`、期望值算不出来、学习者的值太大或结果缺项都没有结论，这份作答尚无证据，不记为学习失败。已有测试判错时整题照样判错。
- 判分事实只记每个测试的结论，原始执行结果不进学习记录。

课程核对用同一个入口，执行方换成 Node 沙箱，整门课一个解释器；核对不生成任何产物。

## 验证入口

在仓库根目录运行学习包的 `check`、`test`、`build` 和完整 `npm run course:check`。课程核对及依赖 Python 的测试可通过 `REPA_PYODIDE_PACKAGES` 指向已有离线 wheel 目录。

`learning-flow.test.ts` 通过真实空间宿主和日志验证 py01、隔天复习、冷却、补救、菜单、独立资格、申诉、判不出结果时不阻塞、复习截止时结论待定与重开后的自动补判，以及代码题只在前端声明 `python.run` 时出现、一次提交只调用一次服务。`learning-facts.test.ts` 验证答案或运行前导改正后的重判与 XP、更早一轮课的重判反映到正在进行的重试、复习截止时已有失败证据照常超时、归属改变不换版本、只搬事实文件后重算出相同状态。`code-tests.test.ts` 验证共用入口的调用顺序、超时归因、没有结论的情形和执行方守约检查；`grading.test.ts` 比对检查与判分对同一份作答的结论。真实杀进程与残缺日志恢复由 `learning-records.test.ts` 覆盖。

运行测试时设置 `REPA_LEARNING_EVIDENCE=/absolute/directory`，会在新的 `counterfactual-*` 子目录保留反事实用例的原始 JSONL、去掉关键作答的事实副本和同一决策时刻的菜单对照，供抽样复核。
