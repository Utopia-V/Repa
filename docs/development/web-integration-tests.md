# Web 集成测试

编写 Web 功能的集成测试时，你可以用这套夹具启动 Repa，提交一条输入，再检查流式回复、工具结果和运行状态。测试中的模型服务会按预设返回内容，因此，同一个用例可以重复运行，也不需要模型账号。

## 设计思路

以“把这段内容保存为笔记”为例，用例既要检查文件里是否写入了指定内容，也要检查客户端是否收到了保存后的回复。要检查这两个结果，就需要让输入实际经过提交、工具执行和消息订阅。因此，用例直接启动现有后端，通过 `RepaClient` 提交输入并订阅消息，再由 Pi 调用工具完成保存。

不过，要反复检查同一段过程，还需要让模型每次都作出相同的回应。例如，前面的笔记用例需要模型先调用写入工具，随后再回复保存结果。因此，我们把外部模型服务换成一个本地 HTTP 服务，由用例预先指定每次请求的回复，而后端和 Pi 仍然按原来的方式处理这些回复。

本地服务使用兼容 OpenAI 的接口，所以后端也可以把它当作普通模型连接来配置：先通过 `connection.create` 建立无密钥连接，再用 `settings.set` 把它设为默认模型。配置好以后，Pi 发出的模型请求就会送到这个服务，用例也就能控制接下来发生什么。

现在可以为笔记用例排入两份回复。第一份返回 `write` 调用，Pi 收到后会执行现有的写入工具；等文件保存好，工具结果就会进入下一次模型请求。这时，本地服务再返回第二份回复“笔记已保存”，客户端随后便能收到这条消息。到这里，我们就可以分别检查文件内容和回复，确认前面要求的两个结果都已经取得。

## 实现细节

### 启动、隔离与清理

用例从 [web-backend.ts](../../apps/web/test/helpers/web-backend.ts) 的 `withWebBackend` 开始。它先创建一个临时目录，并在启动 Vite 之前，把应用配置、Pi 配置、用户主目录和临时目录都指向其中。这样，这次测试创建的模型连接、空间、会话和连接文件就会与本机日常使用的数据分开；官方能力包则使用当前工作区的实现。

环境准备好以后，Vite 开发宿主就会通过 `repa-learning serve` 启动官方学习后端，并通过 `/__repa/connection` 提供连接。夹具先从这个 HTTP 端点取得地址和令牌，再建立 `RepaClient`，随后配置本地模型并打开临时空间。等这些步骤都完成以后，才会进入你传入的回调。因此，回调开始执行时，客户端和空间就已经可以使用了。

默认配置关闭运行重试，因此一次预设错误对应一次模型请求。如果要专门验证重试，可以在用例中通过 `setRuntime` 调整这项设置，再排入相应数量的回复。

回调结束以后，无论断言是否通过，夹具都会关闭自己创建的客户端和 Vite。如果此时后端尚未退出，就向本次启动的进程发送 `SIGTERM`。等进程退出、连接文件删除以后，再关闭模型服务，恢复原环境变量，并删除临时目录。

不过，如果你要验证的是后端能否自行退出，就应该先在回调中关闭最后一个客户端，然后等待进程结束。现有的正常退出用例正是这样处理的：先检查后端已经自行退出，再让夹具完成其余清理。

由于环境变量会影响当前测试进程，同一文件中使用夹具的用例应按 Vitest 默认方式顺序运行，不使用 `it.concurrent`。不同测试文件则由 Vitest 的独立进程隔离。

### 预设模型回复

本地模型服务位于 [local-model.ts](../../apps/web/test/helpers/local-model.ts)，只监听 `127.0.0.1` 的动态端口。你可以通过 `f.model.enqueue(...)` 排入下面三种回复；每收到一次模型请求，服务就取出下一份预设：

| 预设 | 行为 |
| --- | --- |
| `text` | 把 `chunks` 逐项发送为文本增量；每项可以是字符串或等待测试释放的 Promise |
| `tool` | 返回工具名与 JSON 参数；真实 Agent 执行工具后，会再次请求模型 |
| `error` | 返回指定的 HTTP 状态码与错误内容 |

比如，要验证前面提到的文件写入，就先排入一次 `write`，然后再排入普通文本。Pi 收到第一份回复后会先执行工具，所以，等第二次模型请求到来时，其中就应该已经包含工具结果。服务随后返回普通文本，这次运行才会完成。你还可以查看 `requests` 中收到的 JSON，进一步确认工具结果确实进入了后续请求。

如果要检查回复中途的状态，可以把 `deferredText` 返回的 Promise 放进后续片段中。服务会先发送前面的文字，再停在这个 Promise 上。等你从订阅中看见首段、完成中间状态的断言以后，调用 `resolve`，剩余内容才会发出。这样就能明确控制先后顺序，不必用固定延时猜测回复进度。

取消用例可以让这个 Promise 一直等待。当后端取消模型请求、关闭 HTTP 连接时，服务会结束等待中的响应；夹具清理时也采用同样的处理。

如果后端发出了比预设更多的请求，或者请求了其他路由，服务会记录错误，并在夹具清理时使测试失败。你可以据此检查回复数量与实际工具循环是否一致。

### 会话订阅与提交

在用例中，你可以先调用 `observeSession` 创建并订阅会话。因为它使用的是 `RepaClient.watch`，所以 `view()` 读到的也就是公开客户端维护的当前状态。如果除了最终状态，还想检查中间发生过哪些变化，就可以再查看 `changes` 中保存的增量。准备好以后，调用 `submit()`，便会通过 `session.submit` 发起一次运行。

下面是一个完整的文本回复用例，可以放在 `apps/web/test/` 下：

```ts
// @vitest-environment node
import { expect, it } from "vitest";
import { assistantText, observeSession, withWebBackend } from "./helpers/web-backend";

it("提交后收到预设回复与完成状态", async () => {
  await withWebBackend(async f => {
    const session = await observeSession(f.client, f.space.id);
    f.model.enqueue({ kind: "text", chunks: ["先看定义，再看例子。"] });
    const request = await session.submit("请解释集合");
    await expect.poll(
      () => session.view().runs.find(run => run.id === request.runId)?.status,
      { timeout: 8000 },
    ).toBe("completed");
    expect(assistantText(session.view())).toBe("先看定义，再看例子。");
  });
}, 30_000);
```

### 连接中断与恢复

要验证断线重连，可以让客户端通过 [connection-proxy.ts](../../apps/web/test/helpers/connection-proxy.ts) 连接后端。这个 TCP 转发器负责接通或断开连接，应用协议仍在原来的客户端与后端之间传递。

现有用例会先等到客户端收到部分回复，然后再断开转发连接。虽然这时客户端暂时收不到消息，后端仍然会继续完成剩余回复。等后端完成以后，用例再恢复转发，客户端也就会按已有逻辑自动重连并恢复订阅。随后，我们再等它取得完成状态，检查文本是否完整、消息是否重复，以及连接身份是否保持。

这里另外保留了一条直连，用来查询断线期间后端是否已经完成任务。因此，这个用例专门检查连接恢复；最后一个客户端离开以后后端怎样退出，则由前面的正常退出用例检查。
