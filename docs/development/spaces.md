# 空间备份、恢复与独立复制

空间备份把内容、会话历史和插件数据保存在一起，恢复后则可以接续使用。当前通过公开接口创建和恢复快照，图形界面的相关操作仍待接入。

## 设计思路

完成一次练习后，你（或者 Agent）可能会在笔记里补充新的理解，再保存作答和评分，供后续复习使用。下次打开空间时，我们需要让笔记保留修改后的内容，而复习安排也需要包含这次反馈。

这些数据虽然属于同一个空间，却有各自的保存方式：笔记主要是文件，会话历史由 Pi 管理，复习记录则保存在插件的数据库里。因此，备份整个空间时，我们需要把它们一起保存下来，同时维持好内容之间的引用。假如只保存笔记正文，即使以后能重新打开文件，也无法接上原来的讨论和复习安排。

要把这些不同形式的数据收进同一份备份，空间模块应当负责整体协调，各模块则提供自己需要保留的数据。对于复习数据库，插件可以使用 SQLite 已有的快照能力生成一致副本，再交给空间模块保存。这样既能把数据收进同一份快照，也让熟悉数据格式的模块负责处理它。以后即使修改复习算法或数据库结构，相应的保存与迁移仍由复习插件承担，空间模块也就不必跟着了解这些业务细节。

有了完整的快照，恢复时我们就可以重新建立一个可用的空间目录了！为了保留出问题的原目录，我们选择恢复到新目录，这样也方便后续核对和处理。不过，恢复得到的是快照保存时的内容；快照之后新增的笔记、对话和反馈，则需要另外从原目录中找回。

## 实现细节

[SpaceOperations](../../packages/repa/src/spaces/store.ts) 负责空间目录的准备、校验、发布和操作结果恢复。应用协调层确保空间没有正在运行的任务或尚未完成的内容、配置操作，并在快照期间阻止新操作进入该空间；其他空间继续使用。

### 持久数据与所属模块

| 数据 | 保存位置与责任 |
| --- | --- |
| 文档、材料及其修改记录 | 正文保存在普通文件中，内容模块管理 `.repa/content/` 下的身份、历史与资源保留关系 |
| 会话历史 | Pi 管理 `.repa/sessions/` 下的 Session JSONL，Repa 通过会话适配层读取和接续 |
| 复习记录 | 复习插件管理 `.repa/plugins/<pluginId>/reviews.sqlite`，保存反馈、更正、当前调度和参数版本 |

这些数据都有各自的读取和保存入口，因此，空间模块在备份时直接复用它们。至于插件的数据格式，仍然由插件解释；空间备份只记录参与者及其版本，不需要再建立一份复习数据模型。

这里保存的是空间数据，应用侧的模型连接、凭据和外部文件授权则不属于这份快照。对于关联的外部材料，备份也可能只保留引用，读取时仍然依赖原文件。因此，如果你需要一份可以独立使用的副本，应先将材料收进空间。具体范围见[身份与格式责任](#身份与格式责任)。

### 公开接口

| 调用 | 输入 | 结果 |
| --- | --- | --- |
| `space.backup` | `spaceId`、`destination`、`operationId` | 创建包含当前内容、所保留历史和已声明数据的备份目录 |
| `space.restore` | 备份目录 `source`、`destination`、`operationId` | 将备份恢复到新的工作目录，保持空间身份 |
| `space.copy` | `spaceId`、`destination`、`operationId` | 创建拥有新空间身份、可以独立演变的工作目录 |
| `space.operation.get` | `operationId` | 查询 `unknown`、`prepared`、`completed` 或 `failed` |

目标必须是尚不存在的目录，父目录已经存在，并位于源目录之外。调用成功发布后返回实际目标、空间身份、参与数据 owner 的版本与外部依赖；调用方按需要使用 `space.open` 打开。备份目录直接打开会返回 `snapshot_requires_restore`。同一空间身份的两个目录不能在一个后端中作为独立空间同时打开。

```ts
const operationId = crypto.randomUUID();
const result = await client.call("space.copy", {
  spaceId,
  destination: "/path/to/independent-space",
  operationId,
});
if (result.status === "completed") {
  const copy = await client.call("space.open", { path: result.destination });
}
```

长操作超出客户端请求期限时，后端仍会完成已受理工作。保留原 `operationId` 并查询结果；相同输入的重传返回原结果，失败操作也不自动重做。准备前的参数、空间忙碌和目标占用等错误直接返回 RPC 错误；已经写入操作记录后的失败保存在结果的 `error` 中。

### 创建空间快照

要创建快照，通过 `space.backup` 指定源空间、目标目录和 `operationId`。这里的目标目录必须尚不存在，并且位于源空间之外。如果空间里还有运行中的 Agent，调用会返回 `space_busy`，这时需要等任务结束后再发起备份。

备份开始后，应用会阻止新的操作进入这个空间，其他空间则可以继续使用。在这个期间，内容模块提供需要保留的内容和历史，有持久数据的插件则通过 `SpaceSnapshotParticipant.capture` 生成自己的快照。空间模块再收集这些文件，记录参与者和格式版本，并保存文件清单及校验值。

以复习插件为例，它的快照入口先检查数据库版本，再通过 SQLite 的 `VACUUM INTO` 生成一致副本。因为这个入口可以独立于插件后台加载，所以即使关闭了复习能力，我们仍然能够备份已有记录。快照入口的声明与加载方式见[插件说明](plugins.md#禁用后的持久数据快照)。

等全部数据在临时目录中准备好并完成校验，空间模块才通过目录重命名发布备份。如果请求超时或连接中断，调用方可以通过 `space.operation.get` 查询原来的 `operationId`，先确认备份是否已经完成，再决定后续操作。

### 插件持久数据的参与点

`ApplicationOptions.snapshotParticipants` 接受 `SpaceSnapshotParticipant`，声明 `id`、数据 `version`、空间内持久目录和 `capture`。目录位于 `.repa/` 下，不能与基座数据或其他参与者重叠。简单工具和提示无需注册参与者。

```ts
const participant: SpaceSnapshotParticipant = {
  id: "review",
  version: "1",
  directory: ".repa/plugins/review",
  async capture({ sourceDirectory, destinationDirectory,
                  sourceSpaceId, targetSpaceId, mode }) {
    // 使用所属数据库的快照接口，将一致数据写入 destinationDirectory。
    // 独立复制时由此能力将业务引用映射到 targetSpaceId。
  },
};
```

参与者负责自己数据的一致性、待完成写入的协调和独立副本中的业务引用。基座复制其产出的文件，记录 owner 和格式版本，并做完整性校验；基座不理解数据库表、算法状态或业务事务。普通文件的外部变化通过复制前后校验发现，任意应用外写入不参与应用内的提交协调。

`.repa/` 中出现未声明 owner 的持久目录时，操作返回 `snapshot_owner_unavailable`，由对应能力补上快照接入。已建立的备份可以原样恢复其不透明数据，结果继续列出参与者和版本；是否支持该数据版本以及迁移方法，在加载所属能力时处理。

### 恢复与失败处理

恢复时，通过 `space.restore` 指定快照来源、新目标目录和操作标识。空间模块会先检查快照格式、文件校验值和空间身份，检查通过后再发布恢复后的目录。接下来，你就可以用 `space.open` 打开它。不过，恢复得到的空间保留原来的身份，因此同一个后端不能同时打开它和原目录。

假如文件与快照清单不一致，恢复操作就会返回失败，不发布目标目录。这次失败的结果也会保存，所以修复来源后，需要用新的 `operationId` 发起恢复。如果只是重传原操作，得到的仍然是原来的失败结果，不会重新执行。

对插件数据来说，恢复目录只完成了原始文件的恢复，具体格式还要在使用相应能力时由插件判断。例如，复习插件遇到不支持的数据库版本或损坏文件时，会报告错误并保留原文件，而不会把它当成空库重新初始化。遇到这种情况，可以选择先前可用的空间快照再作恢复。

### 身份与格式责任

独立空间复制改变 `spaceId`，保留空间内的内容 `id`。完整身份是 `{ spaceId, id }`，因此两份内容互相独立，同时空间相对的 `repa:document/<id>` 链接继续成立。这与空间内 `content.copy` 分配新内容 `id` 的情况不同。

[内容快照适配](../../packages/repa/src/content/snapshot.ts) 映射内容清单、明确成员、资源引用、当前和历史学习语境组成格式，以及对应操作前后版本。历史操作继续支持在副本中查询与撤回。只有格式 owner 能确定的字段才映射，普通代码、任意 JSON 和 Markdown 正文中的历史陈述按原字节保留。

运行日志由原有 `run-journal` 读取并映射请求所属空间。Pi 会话保留原 JSONL 与真实历史文字，使用 Pi 的 `listAll(sessionDirectory)` 从所属空间目录列举，打开时通过 `cwdOverride` 指向新目录。`list(cwd, sessionDirectory)` 会按历史 cwd 过滤，因此不适用于空间搬移与恢复。消息媒体投影为副本的资源引用。复制不会根据对话中的路径文字去读取或改写原空间。

外部材料仍指向原件，并作为 `externalDependencies` 返回；副本不会复制应用侧的模型连接、凭据或外部文件授权。需要自包含时先显式 `material.collect`；重新授权和重定位使用已有内容关联入口。普通文件树中的符号链接原样保存，不跟随链接收进外部字节；相应目标仍依赖其实际文件环境。

未确认的内容恢复状态可随备份保留，以便继续处理；独立复制会返回 `recovery_required`。备份包含保留关系需要的 blob，不携带无引用缓存，也不恢复前端的旧连接租约。

### 发布与中断恢复

```text
<backup>/
  .repa-snapshot.json        # repa.space-snapshot v1；身份、owner、文件清单与校验值
  .repa-space-operation.json # 发布回执
  data/                     # 普通内容、.repa 持久数据；不含运行锁和活连接租约

<application-directory>/
  space-operations/<id>.json # repa.space-operation v1；输入摘要、源、目标和实际结果
```

空间操作先记录 `prepared`，在目标的同级临时目录中准备全部内容，校验与落盘后通过目录重命名发布。操作记录和目标位置复用 `proper-lockfile` 做独占协调；当前源空间继续由 `RuntimeStore` 持有。已有目标不会作为恢复覆盖对象。

发布目录内的回执使“目录已经发布、应用回执尚未写完”的中断可被确认。重新查询发现匹配的完成回执时补齐结果；尚未发布的准备目录只有在归属标记匹配时才清理，操作标记为 `interrupted`，不自动再执行。复制和恢复后的工作目录保留这份发布回执，后续使用不更新它。

恢复前检查快照格式、文件哈希、路径层级和空间身份。管理目录禁止符号链接，文件不能借清单路径写到目标之外。

## 验证入口

[space-lifecycle.test.ts](../../packages/repa/test/space-lifecycle.test.ts) 覆盖独立复制、身份与资源映射、发布中断及结果恢复。数据接续与插件库恢复使用下面的固定样本验证。

在仓库根目录运行 `npm run build:backend`，然后在 `packages/repa` 目录运行：

```sh
node --import tsx --import ./test/environment.ts --test test/upgrade-recovery.test.ts
```

根目录的 `npm test` 也会发现这些测试。[upgrade-recovery.test.ts](../../packages/repa/test/upgrade-recovery.test.ts) 使用真实客户端、Pi SDK 和 SQLite，覆盖以下行为：

- 从固定快照恢复后，内容、附件、会话、反馈、更正和参数保持；重传旧反馈不重复记录。继续交流、追加评分和撤回旧编辑后，再次重开仍保留结果。
- 复习库版本不受支持或文件损坏时，调用失败且原文件保持。从可用快照恢复后，可以接着记录反馈。
- 快照校验失败时不发布目标；修复来源后，新操作可以完成恢复，原失败回执保持不变。
