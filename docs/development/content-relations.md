# 内容引用与组成关系查询

通过 `content.relations`，你可以查到一篇 Markdown 笔记引用了哪些内容，也可以查到一个多文件对象由哪些成员组成。结果会说明关系来自哪里、依据哪个修订，以及目标目前是否可用。前端和其他能力可以据此浏览、导航或进一步处理相关内容。

## 设计思路

一篇潮汐笔记引用了观测记录，关系浏览组件就需要知道这条引用来自哪篇笔记、指向哪份记录。链接已经写在正文中，因此查询可以直接从正文提取，再解析它的目的地。以后修改链接时，变化也就保留在原来的笔记里，下一次查询会按新的正文取得关系。

正文中的引用之外，组件还需要展示一个多文件产物由哪些成员组成。组成关系已经明确保存在内容清单的 `members` 中，所以这部分直接读取清单。两类关系分别来自正文和清单，查询也应当保留这个区别，界面才能说明一条连线表示引用，还是表示组成。

保留来源以后，还需要说明关系依据的是哪个修订。引用随正文变化，因此使用文件字节的 `bodyRevision`；组成随清单变化，因此使用结构 `revision`。这样，即使正文和清单分别更新，调用方也能知道每条关系实际依据了哪一份数据。

来源确定以后，查询还要找到关系指向的目标。这里沿用链接本身的含义：`notes/summary.md` 中的 `tides.md` 相对于来源笔记的位置解析，而 `repa:document/<id>` 则通过内容身份查找。如果移动来源笔记，普通路径就会从新目录开始解释；如果移动的是身份引用的目标，引用仍然指向原来的对象。查询返回这些引用当前的解析结果。

为了取得这些结果，我们复用搜索模块发现来源文件，再通过 `ContentStore` 检查位置、权限并读取内容。正文交给基于 micromark 的 `mdast-util-from-markdown` 解析，由它区分实际链接、转义和代码中的示例；Repa 再解析目的地，并把引用与清单中的组成合在查询结果中。

关系的原始依据已经保存在正文和清单里，所以当前先在查询时读取、解析，不另外保存关系索引。同一次查询中的重复目标会共用元信息，下一次查询则重新读取当前内容。这省去了随编辑同步索引的工作，但每次查询仍有读取和解析成本；现阶段通过查询范围控制这些工作，后续再根据实际浏览的测量结果决定是否增加可重建索引。

## 实现细节

### 公开调用与范围

前端通过现有客户端调用：

```ts
const result = await client.call("content.relations", {
  spaceId,
  path: "notes",
  limit: 1000,
});
```

示例查询指定空间中的 `notes` 目录。你也可以把 `path` 换成某个来源文件，或者使用已有的 `repa:document/<id>`、`repa:material/<id>` 身份入口。

如果省略 `path`，后端会查找空间内的 Markdown 来源、已登记且带有明确组成的对象，以及已经关联的外部 Markdown 文件。目录查询只在空间内递归；读取单个外部文件时，则沿用原有的精确读取授权。

查找来源时，后端先筛选 `.md` 文件，扩展名不区分大小写，再从内容清单中补上其他后缀但仍登记为 Markdown 的对象，以及具有 `members` 的对象。因此，目录中即使放了许多普通图片、PDF 或代码文件，也不会先用完 Markdown 的来源配额。

如果你明确选择一个尚不支持引用提取的非 Markdown 文件，结果会报告 `unsupported_format`。不过，这个对象如果已有明确组成，查询仍会返回清单中的成员关系。

返回值由三部分组成：

| 字段 | 含义 |
| --- | --- |
| `relations` | 本次取得的引用与组成关系 |
| `unavailable` | 未能读取或确认的来源，包含目标、错误代码和说明 |
| `truncated` | 本次查询受到关系条数、候选数量或读取字节上限的限制 |

这些结果受本次查询的范围和读取预算限制。默认最多返回 1,000 条关系，可以通过 `limit` 调整条数；一次查询还最多处理 500 个来源候选，单个正文最多读取 8 MiB，总读取预算为 32 MiB。

如果这些上限使本次查询无法返回完整结果，`truncated` 就会为 `true`。这时应缩小 `path`，单独查询正在浏览的部分。因为接口没有保存翻页快照，新的调用仍然会根据当前内容重新取得结果。

### 关系与端点

查询中的每条关系都包含来源和目标。对于来源与本地目标，接口提供 `target`、可选的 `ref`、`location`、`role`、`mediaType` 和 `status`，用于显示与导航。这里没有重复附带整份组成清单或资源列表；需要这些详细信息时，可以拿返回的目标再调用内容接口。

关系的字段由 [content/schema.ts](../../packages/repa/src/content/schema.ts) 定义，查询方法在 [content/protocol.ts](../../packages/repa/src/content/protocol.ts) 中登记。两种关系分别带有以下信息：

| 种类 | 来源与附加字段 |
| --- | --- |
| `reference` | 来自 Markdown 实际使用的链接或图片语法；`revision` 为来源字节的 `bodyRevision`，另有 `href`、`syntax`、`line` 和 `range` |
| `composition` | 来自清单的 `members`；`revision` 为来源对象的结构修订，另有成员的 `index` 与可选 `name` |

当 `target.kind` 为 `local` 时，结果沿用 `ContentTarget`，可以交给已有的内容打开和导航入口。如果链接指向 URL，返回的就是 `kind: "url"`、状态为 `unverified` 的目标，因为关系查询本身不会访问网络。

目的地本身无法解析时，这一条链接会以 `kind: "unresolved"`、`status: "invalid"` 和相应代码返回，供调用方显示问题；同篇正文中的其他关系仍然保留。

如果链接能够解析成内容身份，只是暂时找不到对应内容，结果就会保留原来的 `ContentTarget`，以 `missing` 说明状态，并省略未知的文件位置。对于已经解除关联的材料，则返回原身份的 `detached` 状态。即使后来同一路径出现了新文件，那也是另一个对象，所以原身份引用仍然显示解除关联。

### 正文引用与定位

当前支持 CommonMark 的行内链接、参考式链接、自动链接和图片语法。图片的 `syntax` 为 `image`，普通链接为 `link`。提取依据的是正文中实际使用的语法，因此仅有定义、没有使用的参考式链接，以及代码中的示例链接，都不会形成关系。如果同一个链接使用了多次，每次使用的位置都会保留，便于分别导航。

要打开链接，可以读取 `href`。它已经按 CommonMark 解释了反斜线转义和字符引用，URL 本身则保留解码后的形式，不再规范化。

如果要在编辑器中定位这条引用，可以使用从 1 开始的 `line`，或者正文中的 UTF-16 半开区间 `range`。用 `text.slice(start, end)` 就能取出那次引用的原始书写。对于参考式链接，这个位置对应正文中的使用处，而不是后面的定义行。

解析 Repa 身份引用时，只使用其中的 ID，`?` 或 `#` 后缀仍保留在 `href` 中。普通路径则先分离后缀并作百分号解码，再相对于来源文件当前所在的目录查找；仅含片段的链接指向来源自身。

找到路径以后，后端还会通过内容模块检查权限和管理目录边界。正文中存在链接，只提供了要查找的位置，读取目标仍需已有授权。

### 正文不可用与组成仍然有效

假设你为 `course.md` 登记了几个组成成员，后来又通过外部程序暂时移走了这份文件。此时正文无法读取，正文中的引用也就无法提取；不过，清单里已经确认的成员关系仍然存在。因此，查询会返回这些组成关系，把来源标记为 `missing`，并在 `unavailable` 中说明正文不可读的原因。缺少正文读取权限时也按同样方式处理。

这里保留组成的前提是清单结构已经确认。如果来源的位置或结构本身还有待恢复，查询就会在 `unavailable` 中保留 `needs_recovery`，暂不返回依赖这份结构的关系。等恢复完成以后，再次查询即可取得已确认的结果，相关入口见[内容说明](content.md)。

### 查询责任与更新

[relations.ts](../../packages/repa/src/content/relations.ts) 负责选择来源、提取 Markdown 引用并组合结果。查询通过 [ContentStore.observe](../../packages/repa/src/content/store.ts) 进入内容队列，在同一次观察中列举身份、读取元信息和正文。

维护这段代码时，应使用 `observe` 回调提供的读取方法，避免再次进入同一个队列。这样，Repa 自己的内容提交就不会穿插进这次查询。外部程序仍可能修改文件，因此每份正文都会记录实际读到的字节修订。

这里读取正文只是为了提取关系，所以使用 `FileJournal.snapshot` 的不保留模式；读取外部原件时，也只计算字节对应的内容摘要。因此，一次查询不会新增 blob、资源持有、操作历史或普通文件身份，关系仍然由正文和原有清单决定。

由于关系来自正文和清单，这两种数据的变化都需要刷新查询结果。前端收到 `content` 变化事件后，可以按正在浏览的范围重新查询；如果只是清单发生修改，即使事件中的正文路径列表为空，也仍然需要更新组成关系。空间外原件目前没有主动 watcher，因此界面还需要在自己的刷新时机发起查询，后端届时会读取当前内容。

## 未完成项与待验证项

后端正文引用与组成查询已经接通，布局、展开、导航及多窗口刷新由 [#7](https://github.com/Utopia-V/repa/issues/7) 接入。当前没有提取 HTML、PDF 等格式内部的引用，也没有解释分类或先修关系；这些关系由拥有其含义的能力按实际需要提供。

当前采用受限范围内的按需查询，已完成下述小文件规模检查。大体量正文和持续浏览仍需结合实际使用测量，再决定索引或更细的分区查询。
