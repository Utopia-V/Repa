# 文档纪律：规则、检查与面向编码模型的线索

状态：已落地

## 问题

dsh（DeepSeek Harness，tag `dsh-v0.2.1-alpha.2`）的文档能跟上代码，并不依赖成员记得修改。起作用的有三项：

- 每层 AGENTS.md 中每条一至三行的常设规则；
- 二十多个随测试和 CI 运行的文档检查；
- 由脚本生成、再用 `--check` 核对的目录表。

我们依靠人的记忆，因此屡有遗漏：

- 第 1 步删除保温补丁后，学习插件的 README 和注释仍写着运行时的 idle 默认值。
- 底座说明有四成是升级日志，同一个状态抄写在多处，一个概念有四个名称。
- 编写代码的模型接到局部任务即动手，不了解上下层已有什么，于是确认、提问、代做服务三件事各写了一套"向前端发请求、等回复"。

这些问题无法靠一次重构清理干净；只要仍依靠人的记忆，下一次改动还会遗漏。维护者需要的是此后每次改动都遵守的纪律；dsh 为管理大团队所设的规矩不借鉴。

## 决定

做法分三个方面：文档纪律、仓库结构的约定、给编码模型的线索。每个方面均分为两部分。

- **规则**：写入相应层级的 AGENTS.md，每条一至三行，并链接到说明理由之处。
- **检查**：可以机械检查的写成检查，随根目录的 `npm test` 运行，数秒内完成，CI 的 Linux 任务也运行它。编写代码的人和模型每次运行测试都会遇到它。

无法检查的规则，例如"改代码时在同一个提交中更新文档"，dsh 也没有自动检查，依靠审阅把关。

### 文档纪律

规则：

- 文档随代码一并修改：行为变化时，在同一提交中更新受影响的 README 和接口注释。
- 每件事只在一处记录，别处链接过去。做法的理由与放弃的方案写入设计记录；包的用法和约定写在包的 README；待办事项放在 Issue；常设规则写在 AGENTS.md。
- 只写现状。历史留在提交、PR 和设计记录中，README 不记录升级过程，也不记录测试数量和运行结果。
- 可以机械检查的规则即写成检查。例外放入带理由的名单 `scripts/docs/exceptions.json`，只豁免一个文件或目录的一项检查，不整条关闭；名单中的条目过时后，检查同样报错。

这些规则由 `docs/AGENTS.md` 持有；根目录 AGENTS.md 另有"修改代码时，在同一提交中更新受影响的文档"一条。

检查（`npm run docs:check`）：

| 检查 | 守什么 |
| --- | --- |
| 链接 | Markdown 中的相对链接和 `#锚点` 均存在 |
| 路径 | 常设文档中以 `packages/`、`apps/`、`docs/`、`.agents/`、`scripts/` 开头的行内代码路径，以及代码注释中提到的 `docs/`、`.agents/` 文档均存在。设计记录不查，它们可以描述已删除的内容；研究稿等冻结证据按带理由的排除项不查 |
| 不写提交哈希 | 文档引用历史时用 PR 号、tag 或文字说明，行内代码不写提交哈希 |
| 一段一行 | 段落内不硬换行。中文段落中的换行在不少渲染器中会变成字间的空格 |
| 篇幅上限 | 各层 AGENTS.md 有字数上限。超限时先将内容移到所属位置，再压缩，最后才提高上限并写明理由 |
| 停用词 | 一个概念的名称确定后，旧名称列入停用表并写明原因，文档和 src 代码中再次出现即报错 |
| 设计记录格式 | 路径为 `{状态}/{类别}/日期-topic.md`，状态行与所在目录一致，应有的小节齐全，不建索引文件 |
| 包 README 骨架 | 每个包的 README 有固定的几节，见下一节 |
| 持久格式 | `scripts/docs/persistence.json` 声明的持久格式（空间与学习插件的格式标记、学习记录、应用设置等），自首个测试版起 schema 一旦变化，检查即报错，直至在 `docs/persistence/changes/` 写下一条记录，说明本次改动是否升版本及其理由；开发阶段不要求记录 |

### 仓库结构的约定

- 每个包均有 `package.json`、`README.md`、`src/` 和 `test/`。
- README 固定包含以下几节：
  - **概述**：不超过 120 个非空白字符，第一句同时用作包地图中的一行说明；
  - **怎么用**；
  - **对模型的影响**：模型看到的内容、约多少 token、对提示缓存的影响。不向模型注入内容的包，用一句以"无："开头的话说明原因；
  - **已知限制与暂缓**：至少一条，或用"目前没有：……"写明原因。

  "怎么实现"按需编写。
- 仅在边界真实存在时拆包：定义、实现和使用方各自独立演化时方可拆分。仅凭同时具备 Node 和浏览器两个入口，不构成拆包理由。新包须有当前的使用方。Python 运行器据此拆为独立的 `@repa/python-runner`，Web、桌面端和学习插件均依赖它。
- 这些约定写在 `packages/AGENTS.md`。

### 面向编码模型的线索

- **分层的 AGENTS.md。** 各层分工如下：
  - 根目录：常设规则，以及"修改某处之前先读什么"；
  - `packages/AGENTS.md`：编写包的约定；
  - 各包自身的 AGENTS.md：底座和学习插件各一份；
  - `docs/AGENTS.md`：文档的存放位置与写法。
- **由脚本生成、由文档检查逐字节核对的目录。** `npm run docs:gen` 生成，文件开头注明"由脚本生成，不要手改"；内容与重新生成的结果不一致，"生成目录"检查即报错。每份不超过 40 KB，编码模型能整篇读完。具体包括：
  - 包地图 `packages/README.md`：每个包一行，取自其 README 概述的第一句；
  - `docs/generated/` 中的前后端协议的方法和事件、模型看到的工具（名称、说明和参数）、插件的 Host API，以及持久格式。
- **导出的接口均须有说明注释。** 由"导出说明注释"检查核对，只要求有说明，不要求逐个参数写 `@param`；转导出语句不查。
- **新增机制前先查阅这些目录。** 写入根 AGENTS.md，与底座规矩中的"新增机制前，先找已有做法"相衔接。

### 不采纳的部分

以下各项不借鉴，它们或服务于大团队协作，或服务于公开发布，我们目前均用不上：

- 三百多个包的分组和清单检查；
- 中英双语对照；
- 评审归属和 Issue 治理；
- 文档网站；
- 发布与许可证；
- 升级指南；
- 每个文件百分之百的覆盖率；
- 归档记录的封存清单；
- 逐个参数的 `@param` 和 `@returns`。

## 考虑过的其他做法

- **只写规则，不写检查。** 已放弃。dsh 的经验和底座重构第 1 步的漏改均表明，依靠人的记忆会有遗漏。
- **用 git hook 运行检查。** 已放弃。dsh 有意只在 hook 中运行很快的局部检查，文档检查放在测试和 CI 中。我们的 `npm test` 每次都会运行，CI 的 Linux 任务也运行它，检查放在这里即可。
- **照搬 dsh 对接口注释的要求（逐个 `@param`、`@returns`）。** 已放弃。对我们而言负担大、收益小，只要求有说明。
- **检查代码已改而文档未改的情况。** 不做。dsh 也没有此类检查，这一点只能依靠审阅。

## 影响

- 删除或重命名一个被文档引用的文件，或写错锚点时，`npm test` 报错，并指出是哪篇文档的哪一行。
- 根目录 AGENTS.md 指向包地图和 `docs/generated/` 中的目录，编码模型无需在全仓库搜索，即可找到已有的协议方法、事件、工具和 Host API；目录过时即报错。
- 各包 README 均已按骨架改写，只保留现状，底座 README 不再有升级日志；例外名单 `scripts/docs/exceptions.json` 已经清空，此后新增的条目同样须带理由，过时即报错。
- 持久格式的 schema 摘要由 `npm run docs:gen` 记下；`scripts/docs/persistence.json` 的阶段在首个测试版改为 `test` 以后，修改 schema 须先写明是否升版本及其理由。
- 文档检查与目录生成的脚本连同测试约 1,800 行，是新增的维护面。
- 停用词按字面匹配，覆盖检查范围内的文档和 src 代码，可能误报；篇幅上限只查各层 AGENTS.md。
- "在同一提交中更新文档"无法自动检查，仍依靠审阅。
