# 模型调用失败的原因由底座分类

状态：已落地

## 问题

学习者用的是自己注册、充值的模型服务。候选版本验收时，网络不通，做课的对话里连出四条英文的“运行出错 Request timed out.”；学习者看不懂发生了什么，也不知道该做什么。余额用完、key 填错、被限流、服务端出错，在试用者那里迟早会遇到，其中余额不足几乎一定会遇到。

四条来自 Pi 的自动重试：超时、断线、限流和服务端错误，Pi 缺省重试 3 次，每次失败都留下一条出错的助手消息，重试前用一条 `context_edit` 把它移出上下文。底座把每条出错的助手消息都转成一条 `error` 事件，历史里也逐条显示，于是一次失败显示了四遍。原先底座从报错开头取出 HTTP 状态码放进 `errorStatus`，界面只认 401、402、429 三种，网络错误和服务端错误照原文显示英文。

保存 API key 时也不验证：填错了照样显示已连接，要到第一次发消息才失败。

## 决定

### 分类是 Repa 的语义，放在底座

协议新增 `ModelFailureSchema`：`network`（连不上：网络、超时、域名解析）、`auth`（凭据无效或没有权限）、`balance`（余额或额度不足）、`rate_limit`（请求过于频繁）、`server`（提供方服务端出错）、`other`。界面按它说一句话，提供方的原文折叠在下面。

分类在底座的 `agent/model-failure.ts` 里从运行时交回的报错文字认出：只认开头的状态码（Pi 的“状态码: 原文”或“前缀 (状态码): 原文”，OpenAI SDK 的“状态码 原文”），没有状态码时按连接失败的常见写法认出 `network`，不读各家报错的正文。429 而正文提到 quota、billing、balance 的归入余额不足（OpenAI 的 `insufficient_quota`）。

Pi 的错误类型不进协议：Pi 交出的本来就只有一段文字，分类是 Repa 的六个值，以后换掉运行时，只需重写这一处识别。`errorStatus` 随之删去，它只是分类的半成品，留着会有两种表示。

### 一次失败只报一次

- 实时：出错的助手消息不再发 `error` 事件。运行以失败结束时，底座本来就发一条运行一级的 `error` 事件（`code` 为 `model_error`），在它的 `details.failure` 里带上分类，界面显示这一条。
- 历史：被 Pi 自动重试过的那几条出错消息（后面有 replacement 为 null 的 `context_edit` 指向它）标为 `data.retried: true`，界面不显示；最后一次失败照常显示。
- 插件经 `host.models` 调用模型失败时同样以 `model_error` 拒绝，`details.failure` 是分类。

不新建重试或恢复机制。Pi 的自动重试照它的设计保留；失败后学习者重新发送即可，会话停在可以接着发的位置。

### 保存 key 时验证

`auth.setKey` 在 Pi 的登录问到 key 时，先用它向该提供方最便宜的模型经 Pi 发一次只要 1 个 token 的请求，最多等 20 秒：

- 提供方拒绝（`auth`）：以 `key_rejected` 拒绝，Pi 的登录随之中止，凭据不写入，原有的 key 不受影响。
- 其余失败：照样保存，结果 `{ failure }` 写明没能确认的原因。连不上可能只是暂时断网；余额不足说明 key 本身是对的。
- 成功：结果为 `{}`。

### 学习插件自己发起的模型调用

插件用底座的 `modelFailureOf` 从 `model_error` 取出分类，不另起一套。

- 开放题判分：判不出结果的原因本来就只在内存里（重开后显示为 `restart`），分类随它记下，经提交的 `processing.failure` 交给界面，不进学习记录。界面在原有的“没能判出结果，不算错”前面说明原因，并按原因说该做什么；key 无效时给出“去设置模型”。点“再判一次”以后、结果回来之前，界面说“正在判分”，不再显示上一次的原因。辅导读到的当前任务也带上原因。
- 后台展开：分类记进这门课的做课记录（`building/<课的键>.json`）的 `last.failure.failure`，重开应用以后学习页仍能说明原因（持久格式的变更记录见 `docs/persistence/changes/2026-11-17-expansion-failure-reason.md`）。“整门课”下的“未完成：…”后面说一句原因和该做什么，提供方的原文折叠在“原始报错”里；认不出原因的和加入分类之前写下的记录只给折叠的原文。key 无效时“重试”旁边有“去设置模型”。

### 首屏提示先连模型

全新用户的第一屏在没有可用模型时，标题下先显示学习页已有的“还没有可用的模型”和“去设置模型”。建课本身不需要模型，不拦。

## 考虑过的其他做法

- 把 Pi 的错误对象或提供方 SDK 的错误类型直接放进协议：Pi 以后会换掉，协议和界面不能跟着它的类型走。
- 在界面上把连续的几条错误合成一条：重试是运行时的事实，底座看得到（`context_edit`），由底座标出，界面不必猜“连续的错误是不是同一次请求”。
- 关掉 Pi 的自动重试，让每次失败只有一条：断线和限流多半重试就好，关掉会让学习者多发几次；这是 Pi 自然承担的行为。
- 验证 key 用各家“列出模型”的接口：不花钱，但每种接口的地址和鉴权各不相同，Pi 没有统一封装，要在底座里为每种接口写一份；也认不出余额不足。1 个 token 的请求经 Pi 发出，各家差异由 Pi 处理，花费可以忽略（DeepSeek 约十个输入 token）。
- 验证连不上时不保存：学习者可能只是暂时断网，填对了的 key 被拒，他要再填一遍。

## 影响

- 网络不通、key 无效、余额不足、限流、服务端出错，开放题判分与后台展开失败，以及首屏先连模型，由 `npm run verify` 的 `first-run`、`model-failures`、`key-check`、`grading-failures`、`expansion-failure` 五步从界面上走过。

- 分类靠报错的开头和连接失败的常见写法。提供方或 Pi 改了报错格式时，认不出的落进 `other`，界面说“模型调用失败。”并给出原文，不会说错原因。各家的真实报错没有逐一用真实服务核对。
- 保存 key 时多发一次请求，保存最长要等 20 秒；花费极小但不是零。需要第二项信息的 key 在问到第二项之前已经验证过一次。Pi 目录里这类提供方（Cloudflare 要账户 id）缺第二项时，Pi 在发送之前就失败，按 `other` 继续，问到第二项时照旧改走交互登录；若有一家只凭 key 就能发出请求并被拒绝，会误报为 key 无效。交互登录（`auth.login`）不验证。
- 实时事件里不再有逐条的错误。运行中途出错、而排队的消息让运行接着成功的少见情形，实时界面不显示中途那次失败，运行结束后按历史显示。
