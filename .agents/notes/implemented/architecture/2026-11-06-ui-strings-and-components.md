# 界面文字与基础组件的约定

状态：已落地

## 问题

界面文字目前直接写在各个组件里。#101 要求界面上给人看的文字由人书写，可文字散落在几十个文件中，人要改一句话就得找到组件、读懂代码，Agent 修改组件时又会顺手改写或新增文字。#107 的走查中，相当一部分问题出在文字上：解释后台机制的说明句、行话、同一个概念有几种叫法。

另一类问题是同一件事由各个页面各自实现。输入法正在选字时按回车会不会误提交、作答失败后草稿是否保留、减少动态效果的偏好是否生效、关闭弹层后焦点回到哪里，这些都应当全产品一致，现在却取决于每个页面有没有想到。#107 中“刷新后已选的答案丢失”就属于这一类。

第三，设计规则写给人读，界面却主要由 Agent 实现。Agent 照字面执行写得含糊的规则，结果偏离原意：语言文档要求首项“写明缘由”，样稿里就出现了“34 天前学的”这种原始时间。

## 决定

我的决定如下。

**界面文字集中存放，由人编辑。** 界面上给人看的文字放在 `apps/web` 的字符串文件里，组件只引用键，不写字面文字。人直接修改字符串文件，不必阅读组件代码。Agent 新增界面元素时可以新增键，但不填写文字：值留作待人书写的占位，检查报出所有占位，有占位的版本不交给学习者。错误说明、按钮名称、空状态和确认框都属于界面文字；学习内容、辅导回答和后端返回的说明不在此列。文件格式和引用方式由前端决定，以后需要多语言时沿用同一文件结构。

**跨页面的行为由基础组件承担。** 输入法组合输入期间的回车与方向键、Esc 逐层退出、失败时保留输入、减少动态效果、焦点恢复，都在基础组件里实现一次，页面不重复实现。基础组件做不到某件事时，修改基础组件，而不是在页面里绕开它。这条规则延续 `apps/web/AGENTS.md` 中“通用视觉行为修改基础组件”的原则，把范围从视觉扩展到交互。

**设计规则写成 Agent 能照做的契约。** 设计文档中的每条规则写明在什么情形下做什么，并给一个正例；含义依赖判断的规则（例如“写明缘由”）要说明判断的依据，或者交由人来决定。token 和组件的名称按用途命名，使 Agent 能从名称推断用法。

**模型生成的内容使用同一套 token。** 知识卡、图示、题目里的插图等由模型或课程生成的内容，按设计系统的 token 渲染，不自带配色和字号，以免与界面割裂。课程自带的组件（例如某门课特有的题型或图示）将来经插槽接入：在沙箱中运行，只取得设计 token 和已经放出的学习内容，拿不到未放出的答案。第一个插槽在第二门课确实需要自己的题型时再开（#99），现在不建通用的插件机制。

## 考虑过的其他做法

文字留在组件里，用检查拦下新增的说明句。这能减少废话，却没有改变由谁来写：人仍然要在代码里改文字，Agent 仍然会碰到它。

现在就引入完整的多语言方案。目前只有中文，先把文字集中起来，就已经解决了由人书写的问题；多语言等有需要时在同一结构上扩展。

现在就做通用的组件插件机制。没有第二门课的真实需求，插槽的形状只能凭猜测，容易为想象中的插件造出机制。

## 影响

界面文字集中在 `apps/web/src/strings/zh-CN.ts`，`npm run lint` 报出组件里的字面量和待写的键，打桌面包前有占位就失败。输入法选字、Esc 逐层退出、失败时保留输入、减少动效和焦点恢复由基础层实现，测试在 `apps/web/test/base-behaviors.test.tsx`。

课程自带组件的插槽还没有做，等第二门课确实需要时再开。字符串文件变大以后，人靠键名和分组找句子，键名约定见 `apps/web/src/components/ui/README.md`。基础组件承担的行为变多，修改它们的影响面也随之变大。
