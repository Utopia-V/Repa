# 定期备份之间共用历史库中按内容命名的文件

状态：已落地

## 问题

一位试用者的系统盘满了。量下来，安装位置和课程位置都已经可以选，系统盘上唯一还随课程增长的是应用配置目录里的备份。每份备份都是空间 `.repa/` 的完整副本，保留 5 份；`.repa/` 的大头是历史库，课件的每个版本都在里面。一门带 52 MB 课件的课，`.repa/history.git` 有 46.5 MB，5 份备份就是 233 MB，每门带课件的课都是这样。

课程文件夹移到别的盘以后，原位置的那一组备份不再轮换，界面上也删不掉，系统盘上的这几份就一直留着。

## 决定

### 只链接名字由内容决定的文件

历史库里有两类文件写出以后不再改写，名字由内容决定：松散对象 `objects/<2 位>/<其余>` 的名字是解压后内容的哈希，pack 文件 `objects/pack/pack-<哈希>.pack` 的名字是它内容的校验和。Git 写这两类文件都先写临时文件再改名，同名文件已经在时不重写，最多更新修改时间。课件进了历史库，就落在这两类文件里。

定期备份在历史队列里复制历史库，这时没有 Git 进程在写它。复制到这样一个文件时，若最近一份定期备份的同一路径上也有这个文件，且大小与来源此刻相同，就把那个文件硬链接进新备份的临时目录，不再复制。`link` 以任何原因失败，例如文件系统不支持硬链接、那个文件恰好被轮换删掉、链接数到了上限，就照旧复制，不报错。其余文件，包括引用、`HEAD`、`.idx`、`.rev`、`.bitmap`、`.mtimes`、`commit-graph`、会话、学习记录和各个 JSON，每次照旧复制：它们小，而且会被改写，不值得为省它们去信大小或时间戳。

哪些文件属于这两类，由 `@repa/space-history` 的 `isContentAddressed` 判断。它是懂这个仓库布局的一方，底座本来就依赖它，底座里不写 Git 的目录规则。

被链接的文件在清单里照记来源此刻的大小与修改时间，清单格式、复制的先后、`unchanged()` 和轮换都不变。它不进 `syncCopies` 要同步的列表：它属于一份发布前已经整体落盘的备份，不必再同步，也就不会以可写方式打开它。新建的目录和清单照旧落盘，然后发布。

### 不变的前提与边界

整件事的前提是备份发布以后永不原地修改。现在就是这样：写备份只写进组内的临时目录，发布是改名；删除一份是先改名再删目录树，只去掉它自己的目录项；恢复从备份复制出去。因此一个共用的文件，删掉任何一份以后在其余各份里仍完整。

链接只发生在备份与备份之间。空间里的文件会被追加和改写，绝不与备份里的文件链接；恢复仍是复制，不改成链接或移动。

“恢复前”的备份不作为链接的来源，自己也照旧整份复制、不链接别人。它是在恢复之前原样保存当前状态的，当前状态可能正是坏的，比如断电后内容损坏而长度不变的 pack，不能让它流进之后的定期备份。所以新的定期备份只从最近一份定期备份链接；最近的一份是“恢复前”备份时，越过它取它之前的那份定期备份。

### 文件夹已不存在的那一组可以整组删除

选空间页“备份”一节里，标着“文件夹已不存在”的那一组多一个“删除全部备份”，确认一次，页面对这一组的每份调用已有的 `backup.delete`。删到最后一份时，底座把空的组目录一并去掉，组里还有别的内容就留着。不自动删：文件夹可能只是所在的盘没接上，也可能是误删，这时备份正是用来“恢复到新文件夹”的。

## 量了什么

用那门带 52 MB 课件的真实课（34 个文件，课件复制到临时目录里用）模拟一个学习者做课、学习两周：第一天写出 20 个部分的轮廓并展开两部分；之后每天一节约一小时的学习，打开时、30 分钟、60 分钟、关闭时各检查一次备份，每天追加学习记录与会话，后台展开两部分课程（每次约九次写入，与做课试跑里的写入次数相当），直到 20 部分全部展开。历史库与备份都是真实代码，维护按宿主的做法在每批提交以后和关闭时检查门槛。

| 情形 | 两周后 5 份备份的占用 | 峰值 |
| --- | --- | --- |
| 整份复制（改前） | 261.7 MB | 261.7 MB |
| 链接（改后，`du` 实测） | 66.3 MB | 66.3 MB |
| 链接，并在第 5、10 天强制各维护一次 | 65.9 MB | 111.6 MB |

两周里没有自然达到维护门槛：历史库共 607 个松散对象，门槛是 1024 个，按这个速度大约在第四周第一次维护。每次维护把全部对象重新打成一个 48.7 MB 的新 pack，名字随内容变；之后第一份备份整份复制它，旧的松散对象由之前的几份握着，约一天半、轮换掉 5 份以后释放，所以维护之后的一段时间占用接近两份历史库。稳态的占用是一份历史库加上 `.repa/` 其余部分乘以 5；模拟里会话每天增长约 0.24 MB，两周后其余部分合计约 17 MB，这一项随会话多少而定。

Windows 上在 GitHub 的 Windows 机器（NTFS，普通用户权限）上跑同一个模拟，课件换成大小相同的 34 个随机内容文件（课件不能放进公开的仓库；PDF 本身已压缩，随机内容与之相近，在 Linux 上两者相差 2 MB）。两周后 5 份备份按文件身份去重为 68.3 MB；删掉整个备份目录，卷的可用空间增加 69.3 MB，与之一致；`fsutil hardlink list` 对其中一个对象列出 5 个路径，即 5 份备份共用它。逐个文件相加为 271.9 MB，资源管理器的文件夹属性就是这样计算的，所以学习者在那里看到的仍是约 270 MB；选空间页的备份列表里每份的大小同样是所收文件的大小之和。

## 考虑过的其他做法

- **清单里大小和修改时间没变就链接任何文件。** 有三个成立的反例：先写临时文件再改名时，修改时间是写临时文件的时刻，改名被拖延就看不出变化；时钟回拨；内容与修改时间不同时可见。与其逐个补，不如不靠时间戳，只链接名字决定内容的文件。
- **“恢复前”的备份也作为来源。** 它可能保存的正是损坏的状态，见上文。
- **松散对象同名而压缩字节不同。** 只有中途换了压缩级别才会出现，我们不换；即使出现，大小不同就复制，大小相同时解出来仍是同一个对象。不另加检查。
- **把备份挪到别的盘（设置里的备份位置）。** 要加设置项、协议、搬移已有备份并保证中途失败不丢，改动明显更大；它解决的是放在哪里，不解决五倍。这一步不做，做完再看还需不需要。
- **按内容寻址的对象库（备份之间共享一个去重目录）。** 能省下其余文件，但要另建引用计数和垃圾回收；其余文件本来就小，硬链接让文件系统承担引用计数，删除一份仍是删一个目录。

## 影响

- 共用的对象若在盘上损坏，共用它的各份同时损坏；整份复制时，各份是各自独立的副本。备份本来只存在本机，不防硬盘损坏。
- 资源管理器与备份列表显示的大小都比实际占用大，学习者若拿它们看占用，会以为没有变化。
- FAT32、exFAT 等不支持硬链接的盘上照旧整份复制。
- 依赖 Git 对这两类文件“写出以后不再改写”的做法；升级 Git 时随 `@repa/space-history` 的维护测试一起核对。
