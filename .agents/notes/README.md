# 设计记录

这里放一种设计文档：设计记录。它只写代码、测试和模块说明装不下的东西，也就是为什么这样做，考虑过、又放弃了哪些做法。模块现在怎么用、有哪些已知限制，写在模块自己的说明里；要做的事放在 Issue。

这套做法参照 DeepSeek Harness（dsh）的 Agent Notes（仓库 `deepseek-ai/deepseek-harness` 的 `.agents/notes/README.md`，tag `dsh-v0.2.1-alpha.2`），按 Repa 的规模做了简化。

## 目录与命名

每份记录的路径是 `{状态}/{类别}/YYYY-MM-DD-topic.md`，日期取第一次提出的那天，topic 用英文小写和连字符，标题在文件里用中文写。

状态由所在目录决定，状态变了就挪目录：

- `proposed/`：动手前评审的提案。维护者先审设计意图，同意后再开始实现。
- `implemented/`：已经落地的决定。落地的那个 PR 把文件从 `proposed/` 挪过来，改写成已定的说法。以后代码改了其中提到的路径、名称或默认值，同一次改动里一并更新，让它始终和实际一致。
- `rejected/`：考虑过、没有采用的提案。只有当它的理由能拦住一个看起来诱人的错误时才保留，否则删掉。

类别由第二层目录表示：

| 类别 | 记录什么 |
| --- | --- |
| `feature` | 新增的、用户或模型能感知的能力 |
| `simplification` | 删代码、删行为或缩小接口，不增加能力 |
| `architecture` | 包与模块怎样分工、运行时的基本概念 |
| `data` | 盘上数据和交换格式 |
| `process` | 代码之外的工具、流程和规矩 |

这里不建总索引。目录本身就是清单，另写一份索引只会和目录对不上。记录之间用相对链接互相引用。

## 什么时候写

只为长期有用的理由写。判断办法是：以后有人想把它改回去，或者想加一个看起来合理的机制时，是否需要先读到这里的内容。纯机械的改动、局部的界面调整不写。

一个决定已经有记录管着时，更新那份记录，不另写一份。决定本身变了，就写一份新的取代旧的，两份互相链接；不要把旧记录改写成另一个决定。

## 格式

开头两行是标题和状态：

```markdown
# 标题

状态：提案
```

状态写 `提案`、`已落地`，或 `已否决：` 加一句话理由，并且要和所在目录一致。

正文第一节是 `## 问题`，写清动机，不提解法也能读懂。之后的小节按状态不同：

- 提案：`## 做法`、`## 考虑过的其他做法`、`## 验收`、`## 风险与代价`。验收写成从需求上看得到的结果，比如"她能做完一道代码题并在第二天复习到它"，而不是"测试通过"。
- 已落地：`## 决定`、`## 考虑过的其他做法`、`## 影响`。

需要的技术小节（数据格式、接口、迁移步骤）放在这些固定小节之间。每加一个机制，都写清它防的是什么、伤到谁；说不清的就不加。
