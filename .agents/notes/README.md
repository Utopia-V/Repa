# 设计记录

本目录存放一种设计文档：设计记录。它只记录代码、测试和模块说明无法容纳的内容，即为何这样做、考虑过又放弃了哪些做法。模块当前的用法和已知限制写在模块自身的说明中；待办事项放在 Issue。

这套做法参照 DeepSeek Harness（dsh）的 Agent Notes（仓库 `deepseek-ai/deepseek-harness` 的 `.agents/notes/README.md`，tag `dsh-v0.2.1-alpha.2`），并按 Repa 的规模作了简化。

## 目录与命名

每份记录的路径为 `{状态}/{类别}/YYYY-MM-DD-topic.md`，日期取首次提出之日，topic 使用英文小写和连字符，文件内的标题用中文书写。

状态由所在目录决定，状态改变时即移至相应目录：

- `proposed/`：实施前评审的提案。维护者先审阅设计意图，同意后方开始实现。
- `implemented/`：已落地的决定。由落地该决定的 PR 将文件从 `proposed/` 移入，并改写为已定的表述。此后代码若改动其中提到的路径、名称或默认值，须在同一次改动中一并更新，使记录始终与实际一致。
- `rejected/`：考虑过但未采用的提案。仅当其理由能阻止一个看似诱人的错误时才保留，否则删除。

类别由第二层目录表示：

| 类别 | 记录什么 |
| --- | --- |
| `feature` | 新增的、用户或模型能感知的能力 |
| `simplification` | 删除代码、删除行为或缩小接口，不增加能力 |
| `architecture` | 包与模块的分工、运行时的基本概念 |
| `data` | 盘上数据和交换格式 |
| `process` | 代码之外的工具、流程和规矩 |

本目录不建总索引。目录本身即为清单，另写索引只会与目录不一致。记录之间以相对链接互相引用。

## 何时撰写

只为长期有用的理由撰写记录。判断标准是：日后有人想把做法改回去，或想增加一个看似合理的机制时，是否需要先读到这里的内容。纯机械的改动和局部的界面调整不写。

某个决定已由一份记录涵盖时，更新该记录，不另写一份。决定本身改变时，写一份新记录取代旧记录，两者互相链接；不将旧记录改写为另一个决定。

## 格式

开头两行为标题和状态：

```markdown
# 标题

状态：提案
```

状态写作 `提案`、`已落地`，或 `已否决：` 加一句理由，且须与所在目录一致。

正文第一节为 `## 问题`，写清动机，不提解法也能读懂。之后的小节因状态而异：

- 提案：`## 做法`、`## 考虑过的其他做法`、`## 验收`、`## 风险与代价`。验收写成从需求角度可观察的结果，例如"学习者能做完一道代码题并在第二天复习到它"，而非"测试通过"。
- 已落地：`## 决定`、`## 考虑过的其他做法`、`## 影响`。

所需的技术小节（数据格式、接口、迁移步骤）置于这些固定小节之间。每增加一个机制，均须写清它防范什么、伤及谁；说不清则不加。
