# 代价关卡：在昂贵的边界上计数并设上限

状态：提案

## 问题

现有测试只检验结果是否正确，不检验付出的代价，因此浪费的实现照样能通过全部测试。已经出现的情形包括：

- 课程核对在每段候选程序前重启一次 Pyodide 解释器，整门课核对约需 43 分钟；
- 每调用一次插件方法就执行一次 `git log` 并唤醒全部插件；
- space-history 的测试在 Windows 上比 Linux 慢 50 倍，个别测试慢数百倍，主要原因是 Windows 上每启动一次 Git 进程约需 40 至 60 毫秒，而操作中启动 Git 的次数偏多；
- 根目录运行一次测试，底座要构建 5 次；
- 学习记录每一步都存下整个界面画面，体积随使用不断增大；
- 插件工具把整行 JSON 交给模型，首行过长时模型一无所获。

这些问题都有可计数的症状，却没有任何测试去数。以耗时作为关卡又不可行：耗时随机器负载波动，会让测试时过时不过；放宽时限，则把性能问题一并放过。

## 做法

在少数昂贵的边界上计数。次数与机器快慢无关，可以像正确性测试一样严格断言。目前确定的边界如下：

| 边界 | 计数 | 所在位置 |
| --- | --- | --- |
| Git 进程 | 每次操作启动 Git 的次数 | space-history |
| Pyodide 解释器 | 解释器启动次数，应等于超时次数与恢复失败次数之和 | Python 运行器、检查工具 |
| 模型 | 每次调用的请求次数；交给模型的视图、提示段和工具输出的大小 | 底座 |
| 盘上数据 | 每次作答写入的字节数 | 学习插件 |
| 构建 | 每个包在一次全量测试中的编译次数 | 构建脚本 |

每个边界按同一顺序处理：

1. 从原理推算一次操作最少需要的次数，例如快照 N 个改动文件最少需要几次 Git 调用；
2. 统计现状，与推算值对比，差距大的地方即为要改之处；
3. 改好后，把数值写成测试中的上限。此后任何改动使次数增加，测试即失败；确需增加时，修改上限，并在提交信息中写明理由。

耗时本身只在少数端到端基准中记录走势，不作为关卡。报告耗时可附上"次数 × 本机单次耗时"的估算，用来解释慢在何处。

这一做法有成熟的先例：Django 测试中的 `assertNumQueries` 断言一段代码执行的数据库查询次数，Rails 的 Bullet 专门检出 N+1 查询，原理相同。

新增一个昂贵的边界时（新的外部进程、新的模型调用路径、新的持久数据），同时为它设计数与上限。这条规则写入 `packages/AGENTS.md`。

## 考虑过的其他做法

- **以耗时作为关卡。** 放弃。耗时随机器负载波动，CI 机器与本机相差数倍，Windows 与 Linux 相差数十倍，难以设出既不误报、又能拦住问题的阈值。
- **先测本机单次耗时，再按次数推算理想耗时并作为关卡。** 只用于报告，不作为关卡。它依赖单次耗时的测量，仍受负载影响。
- **引入 CodSpeed、Bencher 等持续基准工具。** 暂不做。需要跟踪耗时的长期走势时再评估，届时先核实这些工具的现状。

## 验收

- 把课程核对恢复为"每段程序重启一次解释器"，或在插件方法调用后加回一次 `git log`，测试立即失败，并指出超出上限的计数。
- space-history 的快照、提交、撤销与整理，各有启动 Git 次数的上限；Windows 上的总耗时随之明显下降。
- 新增外部进程或模型调用路径的改动，若没有相应的计数与上限，审查时能被指出。

## 风险与代价

- 每个边界需要一处计数的实现，以及几项断言。
- 上限设得过紧，会让正当的改动也需要修改上限；因此上限取"推算值加少量余量"，并要求在提交信息中写明理由。
