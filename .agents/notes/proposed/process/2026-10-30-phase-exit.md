# 阶段收尾：先定出口清单，新发现的问题分级处置

状态：提案

## 问题

一个阶段中，问题会不断被发现：每次审查都能报出几条，CI 换一个平台就多出一批失败，讨论中又会出现新的想法。2026-10-30 一天之内，Windows 上的 CI 报出 16 项失败，推送前审查报出若干后续修改，维护者提出"内置环境只做基础题"的新方向；每一项都成了任务，却没有规则说明哪些属于本阶段。任务清单因此只增不减，阶段无从结束。

另一面的代价是过度修复。核对器隔离一事中，一个仅用构造的例子说明"可能发生"的问题被当作实际缺陷，做出了每个任务比较约 5.3 万个属性的机制；其后用真实课程核对，课程代码从不产生这类改动。Anthropic 的 Claude Code 文档有同样的观察：被要求找问题的审查者总能找到问题，若每条都修，结果是多出的抽象层和针对不可能情形的测试。

## 做法

### 出口清单

每个阶段开始时写出出口清单：若干条端到端可验证的使用过程，每条只有"通过"和"未通过"两种状态，例如"在 Windows 上上完一节含代码题的课，关闭后重新打开，次日复习到这道题，判分与 Linux 上相同"。清单经维护者批准，此后增删同样须经维护者同意。清单中的每一条都是阶段结束时独立验收的内容，可行时转为回归测试。清单全部通过并经维护者确认后，阶段结束。

### 新发现问题的处置

审查、CI 和开发中发现的每个问题，都在以下三种处置中选一种，并记下理由：

- **现在修**：限于本次改动带入、且违背目标或使出口清单某项不通过的问题，以及会使学习者丢失数据的问题。
- **排期**：原本就存在的问题、不影响出口清单的缺陷和新的想法，记入下一阶段的候选清单。
- **驳回**：不成立或不值得做的问题，写明理由并记录，此后不再作为新问题提出。

风格、命名和措辞不作为问题提出。

### 审查

推送前审查依据目标和已批准的提案判断。每条发现标为"合并前应修""不挡合并"或"原本就有"之一，并写明所防的问题、受影响者和发生的可能性。复审只看上次审查之后的改动。一项工作的"审查—修改"循环，连续两轮没有"合并前应修"的发现即告结束。

### 一项工作的结束

一项工作在以下条件均满足时结束：合入 `dev` 并推送，CI 通过，受影响的文档已在同一提交中更新，对应的设计记录移入 `implemented/`，排到以后的事项写进其"暂缓"一节。

## 依据

- dsh 在代码中以三级标记已知问题：`FIXME` 阻挡发布（审阅者明确同意时例外），`TODO` 在有资源时尽快修复，`XXX` 留待以后、不作承诺。设计记录落地时移入 `implemented/`，未做的部分写入 Deferred 一节。
- Claude Code 的代码审查文档把发现分为 Important（"should be fixed before merging"）、Nit（"not blocking"）和 Pre-existing（"wasn't introduced by this PR"），复审只看新的改动。
- 《The AI-native SDLC playbook》（2026-08-21）对每个发现"Fix now, schedule, or dismiss"，驳回须写明理由，使同一发现下次不再作为新问题出现。
- 《Harness design for long-running application development》（2026-03-24）在写代码之前约定一块工作做完的样子；介绍大规模代码迁移的文章（2026-07-16）指出，没有可靠的评判就没有出口。
- Claude Code 最佳实践文档："A reviewer that's asked to find problems will always find something. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen."

这些材料给出的是单项工作的出口和分级，阶段一级的规则由本记录组合而成。

## 考虑过的其他做法

- **每条发现都修。** 已放弃。审查总能找出问题，阶段因此无法结束；修复不会发生的情形还会留下多余的机制。
- **只按时间收尾。** 已放弃。时间到了不等于可用；"做完"以出口清单界定，时间只用于估计。
- **不分阶段，持续交付。** 暂不采用。首个测试版要固定盘上格式，需要一个明确的节点。

## 验收

- 首个测试版的出口清单经维护者批准，该阶段以清单全部通过结束。
- 推送前审查的每条发现都带有分级和处置，排期与驳回的理由有记录可查。
- 下一阶段开始时，上一阶段排期的事项都在新清单的候选之列。

## 风险与代价

- 排期的问题在下一阶段之前一直存在，处置时须写清它的影响。
- 出口清单写得太粗，会把不该放过的问题排到以后；写得太细，又会回到修不完的状态。清单的粒度以学习者能走通的使用过程为准。
