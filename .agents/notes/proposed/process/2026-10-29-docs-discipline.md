# 文档纪律：规则、检查和给编码模型的线索

状态：提案

## 问题

dsh（DeepSeek Harness，tag `dsh-v0.2.1-alpha.2`）的文档能跟上代码，不靠大家记得改。起作用的是三样东西：

- 每层 AGENTS.md 里一到三行一条的常设规则；
- 二十多个随测试和 CI 运行的文档检查；
- 由脚本生成、再用 `--check` 核对的目录表。

我们这边靠人记，所以一直在漏：

- 第 1 步删掉保温补丁以后，学习插件的 README 和注释还写着运行时的 idle 默认值。
- 底座说明有四成是升级日志，同一个状态抄在好几处，一个概念有四个名字。
- 写代码的模型拿到局部任务就动手，不知道上下层已经有什么，于是确认、提问、代做服务三件事各写了一套"向前端发请求、等回复"。

这些不是一次重构能清干净的，只要还靠人记，下一次改动又会漏。维护者要的是以后每次改动都守的纪律；dsh 为管大团队设的规矩不学。

## 做法

分三块：文档纪律、仓库结构的约定、给编码模型的线索。每一块都分两部分。

- **规则**：写进相应那一层的 AGENTS.md，一条一到三行，链到讲理由的地方。
- **检查**：能机械检查的，写成检查，随根目录的 `npm test` 运行，几秒内跑完。这样 Sol、Aqua 和我每次跑测试都会碰到它。

检查不了的，比如"改代码时同一个提交里更新文档"，dsh 也没有自动检查，靠审阅守住，写进审阅清单。

### 文档纪律

规则：

- 文档随代码一起改：行为变了，同一个提交里更新受影响的 README 和接口注释。
- 一件事只有一个家，别处链过去。为什么这样做、放弃了什么，写进设计记录；包的用法和约定写在包的 README；要做的事放在 Issue；常设规则写在 AGENTS.md。
- 只写现状。历史留在提交、PR 和设计记录里，README 不记升级过程，也不记测试数量和运行结果。
- 能机械检查的规则就写成检查。例外放进带理由的名单，不整条关掉；名单里的条目过时了，检查同样报错。

检查：

| 检查 | 守什么 |
| --- | --- |
| 链接 | Markdown 里的相对链接和 `#锚点` 都存在 |
| 路径 | 常设文档和代码注释里写到的仓库路径（`packages/…`、`apps/…`、`docs/…`、`.agents/…`）都存在。设计记录和研究稿不查，它们可以描述已经删掉的东西 |
| 不写提交哈希 | 常设文档引用历史时用 PR 号或 tag，不用提交哈希 |
| 一段一行 | 段落内不硬换行。中文段落里的换行，在不少渲染器里会变成字间的空格 |
| 篇幅上限 | 各层 AGENTS.md 有字数上限。超了先把内容挪到它该在的地方，再压缩，最后才提上限并写明理由 |
| 停用词 | 一个概念定下名字以后，旧名字进停用表并写明原因，常设文档和代码标识符里再出现就报错 |
| 设计记录格式 | 路径是 `{状态}/{类别}/日期-topic.md`，状态行和所在目录一致，该有的小节都在 |
| README 骨架 | 每个包的 README 有固定的几节，见下一节 |
| 持久格式的改动 | 声明过的持久格式，比如空间 `format.json` 覆盖的文件、插件数据和设置，它的 schema 一变，检查就报错，直到写下一条记录，说明这次改动不升版本还是升版本，以及为什么 |

### 仓库结构的约定

- 每个包都有 `package.json`、`README.md`、`src/` 和 `test/`。现在已经是这样。
- README 固定这几节：
  - **概述**：一百字以内，同时用作包地图里的一行说明；
  - **怎么用**；
  - **对模型的影响**：模型看到什么、大概多少 token、对提示缓存有什么影响。不往模型面前放东西的包，在名单里写明理由；
  - **已知限制与暂缓**：至少一条，或者写明为什么没有。

  "怎么实现"按需要写。
- 只在边界真实存在时拆包：定义、实现和使用方各自独立演化时才拆。只是同时有 Node 和浏览器两个入口，不构成拆的理由。新包要有现在的使用方。眼下要拆的是 Python 运行器，放在学习插件那一步。
- 这些约定写进新的 `packages/AGENTS.md`。

### 给编码模型的线索

- **分层的 AGENTS.md。** 各层分工如下：
  - 根目录：常设规则，以及"改哪里之前先读什么"；
  - `packages/AGENTS.md`：写包的约定；
  - 各包自己的 AGENTS.md：已有底座和学习插件两份；
  - `docs/AGENTS.md`：文档放在哪里、怎么写。
- **由脚本生成、用 `--check` 核对的目录。** 生成的文件开头注明"由脚本生成，不要手改"。具体有：
  - 包地图：每个包一行，取自它 README 的概述；
  - 前后端协议的方法和事件；
  - 模型看到的工具：名称、说明和参数；
  - 插件的 Host API；
  - 持久格式。
- **导出的接口都要有说明注释。** 只要求有说明，不要求逐个参数写 `@param`。
- **加机制之前先查这些目录。** 写进根 AGENTS.md，和底座规矩里的"加机制之前，先找现成的"连在一起。

### 不学的

这些不学，它们要么为大团队协作，要么为公开发布，我们现在都用不上：

- 三百多个包的分组和清单检查；
- 中英双语对照；
- 评审归属和 Issue 治理；
- 文档网站；
- 发布与许可证；
- 升级指南；
- 每个文件百分之百的覆盖率；
- 归档记录的封存清单；
- 逐个参数的 `@param` 和 `@returns`。

### 落地顺序

1. 先写规则和检查，以新文件为主，等底座重构第 2 步（改了根目录的构建和测试脚本）合进来以后再接进 `npm test`。还没改成新骨架的 README，放进带理由的名单，比如"待底座重构第 5 步重写"。
2. 底座重构剩下的几步和学习插件那一步，碰到哪个包，就按新骨架重写它的 README，并从名单里删掉。
3. 重构全部做完时，名单应该是空的。

## 考虑过的其他做法

- **只写规则，不写检查。** 放弃了。dsh 的经验，加上我们第 1 步的漏改，都说明靠人记会漏。
- **用 git hook 跑检查。** 放弃了。dsh 有意只在 hook 里跑很快的局部检查，文档检查放在测试和 CI 里。我们没有 CI，`npm test` 是每次都会跑到的地方。
- **照搬 dsh 对接口注释的要求（逐个 `@param`、`@returns`）。** 放弃了。对我们负担大、收益小，只要求有说明。
- **检查代码改了而文档没改。** 不做。dsh 也没有这样的检查，这一点只能靠审阅。

## 验收

- 删掉或改名一个被文档引用的文件，`npm test` 报错，并指出是哪篇文档的哪一处。
- 新会话里的编码模型从 AGENTS.md 出发，不用全仓库 grep，就能找到已有的协议方法、事件、工具和 Host API。
- 改了某个持久格式的 schema，测试会要求写下升不升版本，以及理由。
- 底座的 README 改写以后只剩现状，没有升级日志。

## 风险与代价

- 检查脚本连同测试大约六七百行，是新的维护面。每个检查都写清它防的是什么。
- 名单不清空，检查就形同虚设。所以名单条目要带理由，过时了检查会报错。
- 停用词和篇幅上限可能误报，先只覆盖常设文档。
