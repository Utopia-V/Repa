# 通用 Agent 接上 MCP 服务器

状态：提案

## 问题

Repa 的通用 Agent 缺一项能力时，现在只有两条路：等底座或某个插件补上，或者用命令行。做课时已经撞上过：DeepSeek 的读网页服务读不回 PDF 讲义和一部分网站；接的不是 DeepSeek 时，Agent 没有搜索。这类能力别人大多写好了，以 MCP 服务器的形式提供（搜索、读网页与 PDF、笔记、日历、文献库），接上就能用，Repa 不必各写一个插件。

内嵌的 Pi 带着两样与 MCP 有关的东西：

- `@earendil-works/pi-mcp`：独立的 MCP 客户端库，支持 stdio 和 Streamable HTTP，负责握手、请求的对应、超时和取消，另有 OAuth 的积木。它不依赖 Pi 的其余部分。
- `pi-coding-agent` 里的 MCP 扩展：在上面那个库之上做了配置文件、工具命名、状态提示和登录命令。它只在 Pi 自己的命令行里加载，Repa 经 SDK 建的会话没有。

把后者接进 Repa 的会话，我在一个草稿分支上实际试过（真实协议后端、离线模型、本机写的测试服务器）。能通，但它是为 Pi 的命令行设计的，放进 Repa 处处要绕：

| 事实 | 后果 |
| --- | --- |
| 服务器进程跟着每个 Pi 会话起：每个对话、每个子 Agent、每次后台运行各起一份，只是打开旧会话看历史也会起 | 有状态的服务器会有好几份，互不相通 |
| Pi 的会话关闭时不通知扩展，服务器不会被关掉 | 不另补一处，后端收到退出信号 8 秒后仍在运行 |
| 配置、凭据、日志默认读写 `~/.pi/agent`；改到 Repa 的目录所需的函数和类没有导出 | 要自己读配置，再把一个形状相同的对象强行当作它的凭据类传进去 |
| 连接失败、需要登录、仍在连接这些提示都发给 Pi 的界面 | 在 Repa 里全部落空，学习者什么也看不到 |
| 一个不回答的服务器让每个新会话的第一条消息等满 10 秒 | 期间没有任何提示 |
| 登录远程服务器的流程挂在 Pi 的 `/mcp` 命令上 | Repa 用不了 |
| Repa 每轮重设启用的工具，会把扩展启用的工具关掉 | 要在 Repa 一侧为它开例外 |
| 超长的结果写进 `/tmp`，不清理；Repa 自己对工具结果的截断不生效 | |

## 做法

Repa 自己管 MCP 服务器的连接，把它们的工具当作 Repa 的工具交给通用 Agent。连接用 `pi-mcp` 这个客户端库，不用 Pi 的 MCP 扩展。这样 MCP 在 Repa 里是底座的一项能力，立在 Repa 自己的接口上：配置的位置与格式、连接的归属、确认、状态都由 Repa 定，客户端库是它现在的实现，以后换成别的 MCP 客户端不动这些。

### 服务器配置在哪里

配置属于这个人，不属于某个空间，放在应用配置目录的 `mcp.json`。格式用各家通行的 `mcpServers` 写法，因为每个服务器的说明给出的都是这一段，粘贴过来就能用：

```json
{
  "mcpServers": {
    "fetch": { "command": "uvx", "args": ["mcp-server-fetch"] },
    "notes": { "url": "https://example.org/mcp", "headers": { "Authorization": "Bearer …" } }
  }
}
```

设置页加一节“MCP 服务器”：列出配置的服务器和各自的状态（已连接、有几个工具；连接失败及原因），可以添加（粘贴上面这样一段）、停用和删除。

空间里的文件不能配置服务器。空间可能是别人给的，stdio 服务器是一条在本机运行的命令；自写插件要经批准才运行，是同一个理由。以后需要“这门课带着它要用的服务器”时，走与自写插件相同的批准。

### 连接归谁

连接归后端，一个服务器一份，所有会话共用。后端启动后在后台连接，不等它；连上以后它的工具才出现在通用 Agent 的工具里，没连上的在设置页显示原因。一个不回答的服务器因此不拖住任何消息。后端正常退出时关闭全部连接和它们的进程。

### 工具怎样交给 Agent

每个工具登记成 Repa 的一项工具，名称按通行的 `mcp__<服务器>__<工具>`，说明和参数取自服务器。它与插件的工具走同一条路，所以 Repa 已有的几样自然生效：结果按 Repa 的上限截断，进会话记录，前端的工具活动里看得到。运行被停止时，进行中的调用要随之取消。

只给通用 Agent 和它的子 Agent。插件声明的 Agent（例如学习辅导）的工具是它定义里列出的那几个，不会多出来。

### 调用之前问不问

MCP 工具可能有副作用（发邮件、改日历），而课件和网页里可能带着诱导模型的文字。沿用命令授权的做法，按服务器设定：

- 每个服务器有一个“调用前询问”的开关，默认打开：每次调用弹出确认，写明哪个服务器的哪个工具和参数。
- 关掉以后这个服务器的调用不再询问。搜索、读网页这类只读的服务器适合关掉。
- 命令授权设为“完全访问”时都不问。

服务器在工具上声明的“只读”不作为依据：它是服务器自己说的。后台运行没有人可问，开着“调用前询问”的服务器在后台调用时被拒绝，与命令行在后台的表现相同。

### 第一版不做的

- 需要 OAuth 登录的远程服务器。用请求头带令牌的可以；登录流程要经前端打开浏览器并接回调，另做。
- 工具很多时的按需加载。服务器的工具全部声明给模型，嫌多就停用这个服务器。
- MCP 的资源和提示。

## 考虑过的其他做法

- **把 Pi 的 MCP 扩展加进 Repa 的会话。** 试过，能通，约二十行加一个小文件。放弃的理由是上表：每个会话一份进程、状态对学习者不可见、登录用不了，补齐这些要在 Repa 一侧为一个扩展写一圈例外，而且它的行为取决于 Pi 没有导出的内部。Pi 的客户端库本身是一个正常的库，直接用它更直接。
- **让 Agent 用命令行调用 MCP 服务器。** 每次调用都起一个进程，握手一次；Windows 上还要有可用的命令行。
- **按空间配置服务器。** 见“服务器配置在哪里”。
- **按服务器声明的只读标记决定问不问。** 标记是服务器自己写的，不同服务器的宽严不一；让使用者按服务器决定，规则只有一条。
- **做成一个插件。** 密钥、连接和确认都在底座，插件拿不到，也不应该拿到；别的领域同样需要它。

## 验收

- 在设置页粘贴一段本机 stdio 服务器的配置：状态显示已连接和工具数；对话里通用 Agent 调用它的工具，先弹出确认，允许后拿到结果，结果在会话记录里。
- 关掉这个服务器的“调用前询问”：调用不再询问；后台展开课程时也能调用它。
- 配置一个不回答的服务器：发消息不受影响，设置页显示它没有连上及原因。
- 关闭应用：服务器进程都结束；打开旧会话看历史不起任何服务器进程。
- 学习辅导的工具里没有 MCP 工具。
- 整个过程不读写 `~/.pi`。
- 配置里的令牌不出现在会话记录、日志和导出的反馈包里。

## 风险与代价

- **本机命令。** stdio 服务器以学习者的身份在本机运行，Repa 不隔离它。这与学习者自己在终端里运行它相同，但 Repa 让这件事变得容易，设置页要写明。
- **服务器写空间里的文件不进 Repa 的写入路径。** 空间历史会把这些改动记为外部程序的改动，可以撤回，但不归到发起它的那次运行名下。
- **学习者的环境。** 多数服务器靠 `npx`、`uvx` 启动，机器上没有 Node 或 uv 时起不来；状态里要把“找不到命令”说清楚。Windows 上启动命令的写法与别的系统不同。
- **工具说明是服务器写的文字，会进模型的上下文。** 学习者装上一个服务器，就是信任它的说明。
- **被强行结束时可能留下进程。** 后端被强杀而服务器不理会输入流关闭时，它会留下来。

## 待定

- 试过的是 Pi 的扩展；直接用客户端库的做法没有试过，实现的第一步是确认它在 Windows 上起进程、工具列表变化的通知、取消和超时都够用。
- stdio 服务器的工作目录，以及传给它的环境变量是全部还是只给配置里写的。
- 设置页上的添加方式：只接受粘贴的一段配置，还是另有逐项填写的表单。
- 远程服务器的 OAuth 何时做。
