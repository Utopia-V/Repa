# 学习插件重做：只记事实、当场判分，检查与判分采用同一套判断

状态：提案

## 问题

在 2026 年 10 月的问题清点中，学习插件的问题大致分为四类，结论均经维护者逐条讨论。

第一类是把派生内容当作记录。学习记录在每一步都存下整个界面画面和学生模型的投影，体积随使用不断增大；前端一改，盘上格式即随之改变；算法改进后，也无法用历史作答重新推断学习状态。快照去重从不生效、写入无人读取的戳和字段、同一事实有多种表示，根源均在于此。

第二类是检查设在所防问题不会发生的位置。代码题的期望值预先算好存入 `expected.json`，并绑定了 `runner.py` 全文的哈希。然而题目、运行器和答案装在同一个安装包中，在学习者一端不会各自变化；这种绑定查不出真问题，Windows 检出时换行一变，代码题反而静默下线。课程核对时每段候选程序都重启一次解释器，整门课串行需四十多分钟，时间几乎全部耗在重启上。

第三类是流程会卡死，或在没有证据时强行判定。判分途中关闭窗口、开放题的模型调用失败、模型表示无法准确判分，均会使任务停滞或被记为失败；复习和测验期间合上笔记本，计时仍继续。

第四类是数值和规则没有出处。流程中的数字、学生模型的常数散落在代码中，未标明出自 Math Academy 公开的内容、Repa 的猜测还是研究结论；FIRe 实现后又被关闭；测验触发、选题和完课估算使用了复杂的规则，理由只写着"Repa 假设"。

另有两项与学习插件的结构有关：Python 运行器连同 `runner.py` 装在学习插件中，Web 为使用它而依赖整个学习包；辅导工具把前端用的 JSON 直接交给模型。

## 做法

### 学习记录只记事实

每次作答只记录对推断学习状态有用的事实：所出题目及其版本，学习者的作答（换回题目原来的选项编号），当时的判分结果，出题和作答的时间，作答前是否看过讲解或询问辅导，以及任务类型（课、复习、测验）。界面、学生模型、进度和 XP 均由这些事实计算得出，可以删除后重算。

题目的版本只由学习者看到的内容和判分方式决定。知识点归属改变时不更换版本，重算学习状态时按新归属计算。

没有证据则既不算对也不算错：中途离开、判分失败、模型表示无法准确判分，均属尚无证据，不阻塞任务，也不记为失败。条件具备时自动补判，学习状态随之重算。

题目的答案改正后，过去的作答按新答案自动重判，对错两个方向均生效；新判分以追加方式取代旧判分。XP 只增不减，不因重判收回。

### 判分：答案存于题目，在同一环境中当场计算

题目中存的是答案本身，即期望表达式和参考解。判分时，在运行学习者程序的同一环境中当场算出期望值，再与学习者程序的结果比较。目前该环境是应用内置的 Pyodide；日后学习者若使用自己安装的 Python，判分也使用它。期望值由期望表达式算出：一次判分请求先求期望表达式，再运行学习者的程序，二者在同一个 Worker 里，程序改不到已经算出的期望值；参考解不发给前端，用来在检查时判对。

因此，`expected.json`、指纹、重新生成以及前后端运行器摘要的比对一并去除。"能否运行 Python"改为前端连接时声明一次。执行请求中不再携带学习插件的编号。

### 检查工具

检查工具用与判分相同的一套判断检查一道题：参考答案须判对，已知的错误作答须判错。它与判分共用同一个入口，入口只认一个运行测试的函数：判分时它经前端运行，检查时它是 Node 里的 Pyodide 沙箱，日后还可以是学习者自己装的 Python。

题目在何处产生，检查即在何处运行：包括我们自己写的、社区贡献的，以及模型在学习者一端写的。因此它是产品中的工具，不只是仓库中的测试。

解释器状态的隔离以题目为单位：互不相干的题目彼此不能影响，同一道题的参考答案、等价写法和已知错误写法之间也不能；多步代码题的各步按顺序运行，后一步继承前一步的变量。判分时每次提交换一个预热好的新 Worker。检查工具为了速度整门课共用一个解释器，每个任务后由 `runner.py` 删去新建的文件、恢复常被改动的全局设置，并用系统熵给随机数重新播种；恢复失败或超时才换新的解释器。恢复失败时这个任务的结果已经算出，照样保留，余下的任务在新的解释器里接着运行，判分时也一样。这依赖一个事实：课程代码不改动库的属性。随包课程全部 2,696 个任务结束时留下的改动只有新建的文件、`builtins._` 和库按需导入的模块（2026-10-30 记录）。整门课核对的耗时应从四十多分钟降至一分钟左右，CI 中"只在定时任务跑整门课核对"的开关随之去除。

无法运行代码的题目，在写题、改题时由模型只看题面独立再解一遍，结论不存档。

一道题中有多个代码作答位且彼此有先后关系，是一种正当的题型，称为多步代码题：作答位按顺序在同一个解释器中运行，题目写明每一步交给下一步的变量名；判第 n 步时，先运行前面各步的参考解，因此一步出错不会连累后续各步。互不相干的代码应出成两道题。多步代码题等模型出题需要时再实现（维护者 2026-10-29 同意）；在那之前，检查工具以 `multiple_code_slots` 拦下有多个按测试判的作答位的题。

### 学生模型与流程

- 启用 FIRe。权重暂用课程中现有的值（多为 0.5），并标明为假设。
- 删除 `uses`，先按 Math Academy 公开的做法以 topic 为单位传递信用；待真实数据证明按题传递信用的预测更准确时再加回。研究需要时从 git 历史找回标注。
- 课程结束时同样按答对比例计算质量，课、复习、测验三种任务使用同一条规则。
- 保留公式本身的常数，为其命名并注明出处，日后调参即调整这些常数；删除研究专用的缩放、指数、capped-sum 和速度开关。
- 测验按累计 XP 触发，XP 只增不减，不使用历史高水位。测验从学过且近期未考过的 topic 中随机选题，每个 topic 一题，答错转入复习，与 Math Academy 一致。
- 完课估算改为"剩余课时 ÷ 最近每天的平均学习时长"，显示为一个日期。
- 复习判定和菜单规则保留，标明为假设，实际使用后再调整。
- 时间一律取自底座的 `host.now()`。时钟回拨时按零间隔继续，不致停滞。
- 中途离开复习或测验时：未作答的 topic 既不算对也不算错；本次测验就此结束，未测到的 topic 之后重新安排；已作答的照常计算。
- 没有可用模型时，不出开放题。
- 先筛除前端无法显示的题目再选题；没有一道题能显示的知识点不进入菜单。

### 辅导

辅导工具向模型提供一份写给模型看的当前任务：题面、学习者的答案、判分结果，写成分行文字。需要更多内容时，由模型自行用工具获取。复习和测验期间不回答，这一条已在底座重构第 5 步改为使用 `beforeRun` 关卡。

### 数值命名与假设清单

流程数字和学生模型常数集中于一处，每个均须命名并注明出处（Math Academy 公开、Repa 猜测、研究结论）。学习插件的说明中另建一份"尚待查证的假设"，每条写明它控制什么、出处是什么、何种证据会使其改变。数值只保留在代码中，文档只引用名称，不抄写数值。首批收入的有：流程中的数字、学生模型常数、Math Academy 未公开的部分（复习判定、衰减形状、质量）、FIRe 权重、测验"速度降 0.2"的幅度，以及研究中仍属假设的各项。

### 拆分 Python 运行器

Python 运行器连同 `runner.py` 拆为一个独立的小包，前端和学习插件均依赖它。同时把 `runner.py` 中那行 `del value` 移入输出收集的范围，修复两处小的时间窗和顺序差异。

### 出题说明

从源头修改出题说明：题目用于区分懂与不懂的人；每个错误选项均应是某种具体误解会选择的；各选项的形式和长短相近。检查工具仍只查对错。日后模型根据维护者的材料出题，也使用这份说明。

### 不在本次范围内

维护者的主要用法是提供自己的材料（讲义、教材），由模型拆出 topic、知识点和题目，题目经检查工具核对后进入练习和复习的循环。这条路径在产品中尚不存在，包括将知识作为普通文件放在空间中、在对话中新建 topic 和修改题目的工具、把预制课程复制一份作为自己的课程修改。它是下一项功能，另行提案；本次先完成它所需的两部分：检查工具和出题说明。

## 分步

1. 拆出 Python 运行器；检查工具复用解释器。（已落地）此后各步的测试都会快很多，CI 中整门课核对的开关也已随之去除。
2. 判分当场计算，去除 `expected.json`、指纹和运行器摘要比对；检查工具改为与判分共用同一入口。（已落地）这个入口要与当场判分一起设计，所以放在这一步。
3. 学习记录只记事实，状态重算；没有证据的规则、答案改正后的重判。
4. 学生模型与流程的各项改动，以及假设清单。
5. 辅导工具改为写给模型看的分行文字。
6. 出题说明。

每一步对应一个分支、一次审阅、一次合并。

## 考虑过的其他做法

- **预先算好期望值，加指纹防止其过时。** 已放弃。答案本就随课程装在学习者一端，在同一环境中当场计算，期望值与判分天然一致；存储期望值反而需要始终保证计算环境与判分环境相同。
- **检查时每段程序换一个新的解释器。** 已放弃。隔离最彻底，判分也是每次提交换一个新的 Worker，但每次启动约 2.7 秒，整门课串行需四十多分钟。从内存快照启动也省不下多少：Pyodide 314.0.7 的快照接口未公开，只能在加载包之前做快照，加载并导入 NumPy 和 pandas 的约 2 秒仍然要花。
- **每个任务后与基线比较全部模块和类的属性并改回。** 已放弃。它能拦下课程代码改动库属性（如 `math.pi = 3`）的情形，但每个任务要比较约 5.3 万个属性，多花 3 至 8 毫秒，整门课核对从约 7 秒增至约 21 秒，这段代码还要在判分时运行；随包课程没有这类改动，原地修改它也查不出。
- **随机数在任务之间恢复成基线时的状态。** 已放弃。这样每个任务抽到的随机数都相同，算期望值的任务和运行候选程序的任务也抽到同样的数，依赖未设种子的随机数的题因此能通过检查，判分时新的 Worker 却抽到别的数。改为每个任务后用系统熵重新播种，与新的解释器相同。
- **记录中存储界面画面，重放时直接读回，不重新运行教学逻辑。** 已放弃。这相当于把缓存当作记录，新算法无法依据历史重新推断。
- **按题传递信用（`uses`）。** 暂不实施。现有研究不支持依靠未经验证的隐式信用压缩复习，待真实数据证明其预测更准确后再加回。
- **一题最多一个代码作答位。** 已放弃。有先后关系的几步代码放在同一题中继承解释器是合理的。

## 验收

- 在 Windows 上按 CRLF 检出后，学习者能做完一道代码题并在第二天复习到它，判分结果与 Linux 上相同。
- 整门课核对在一分钟左右完成，只启动一个解释器；对同一道题，检查与判分给出相同的结论。
- 改正一道题的答案后，过去的作答自动重判，学习状态随之变化，XP 不减少。
- 复习或测验中途关闭应用，再次打开时不会停滞，未作答的 topic 不记为错误。
- 未配置模型时，不出开放题。
- 更换一组学生模型参数后，能用历史作答重放，比较两组参数的预测。

## 风险与代价

- 开发阶段的旧学习记录直接丢弃，不写转换。
- 删除 `uses` 和研究专用的开关后，研究重启时需从 git 历史取回。
- 拆包会影响 Web 和桌面端对运行器的引用，前端部分由 Aqua 跟进。
