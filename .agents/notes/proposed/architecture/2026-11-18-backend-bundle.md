# 安装包里的后端打成少数几个文件

状态：提案

## 问题

第一个测试版的 Windows 安装包在学习者的笔记本上安装约 4 分钟，装好后第一次打开要等 50 到 80 秒，之后每次只要几秒。没有自动更新，每个修复版都要重装一遍，这两段时间也就每次重付。

在 GitHub 的 Windows runner 上（windows-2025，dev `08c6d770c`）把时间拆开量了一遍。runner 缺省关掉了 Defender 的实时扫描，测量时分别在打开和关掉的状态下各装一份：

| 项目 | Defender 开 | 关 |
| --- | --- | --- |
| 静默安装（12545 个文件、576 MB，其中 `node_modules` 11976 个） | 101 至 113 秒 | 62 至 64 秒 |
| 第一次打开应用到显示选空间页 | 19.5 至 23.0 秒 | 2.1 秒 |
| 其中后端第一次启动到交出连接 | 14.6 至 18.3 秒 | 0.7 秒 |
| 之后再打开 | 1.3 至 1.6 秒 | 1.4 秒 |

再用合成文件看扫描的代价怎样计算：新写的 1600 个 100 B 的 .js 和 1600 个 6 KB 的 .js 一样慢，第一次读都要 3.6 到 6.7 秒，写入也要多花 3.7 到 7.5 秒；一个 9.6 MB 的文件第一次读只多 13 ms，扩展名换成 .dat 也一样。也就是说，Defender 的代价按文件个数计，每个新文件写入和第一次读取各约 2 到 4 毫秒，与大小几乎无关。

后端是一个按 npm 包布局装着的 Node 程序。它启动时要读约 1800 个文件（typebox 一家 669 个、Pi 的几个包约 550 个），首次打开多出的十几秒全在这里；安装时写的一万两千个文件，多出的约 40 秒也在这里。学习者笔记本上的数字大约是 runner 的两到三倍，构成相同。

## 做法

打包时把后端和随包的两个插件用 esbuild 打成一个整体，平铺在 `node_modules/@repa/base/dist` 下的几十个文件里（ESM，按动态导入拆块）。准备应用目录的步骤照旧按锁文件装好运行依赖，之后由 `apps/desktop/scripts/bundle-backend.mjs` 换成打包后的布局。

难处不在打包本身，而在依赖自身位置的代码：Repa 和 Pi 都有按 `import.meta.url` 找资源的地方（课程、写课说明、插件 Skill、CMap、Python 沙箱的脚本、Pi 的 `package.json`、文档、主题和 wasm），代码搬进别的文件后，这些路径就指错了。做法是让打包后的代码看到的位置仍是原来的布局：

- **入口与 base 原来的文件同名同位置。** base 的每个导出（`index`、`client`、`protocol`、`plugin`、`process`、`testing`）和 `cli` 都输出到 `@repa/base/dist` 下原来的文件名，所以 `package.json` 的 `exports`、`process.js` 按相对路径找 `./cli.js`、`folder-imports.js` 找 `../plugin.js` 都照旧，主进程也照旧按包名导入 `@repa/base/process`，源码不用改。
- **模块的位置换成原来的位置。** 每个被打包的模块里，`import.meta.url`、`import.meta.resolve` 和 CommonJS 的 `__dirname`、`__filename` 换成这个模块在安装布局里原来的位置。替换由 esbuild 的 `define` 做，只换真正的表达式，字符串和注释里的同名文字不动。
- **资源留在原处。** 被打包的第三方包只留非代码文件（`package.json`、许可证、wasm、数据），Repa 自己的包留下 `dist` 之外的全部内容。Pi 导出 HTML 时按路径读的三个脚本另列保留。
- **按路径启动的 worker 单独打。** Pi 的 codemode 与缩图两个 worker 各打成一个自足的文件，放回 Pi 计算出的位置；codemode 的那个 Pi 会读进内存以 `data:` URL 启动，构建时核对它不依赖自己的位置。Pi 按它自己支持的打包方式运行（`PI_BUNDLED_NODE`）。
- **不打包的。** `pyodide` 和 `ws` 原样留在 `node_modules`：Linux 课程核对的沙箱用另一个 Node 进程按路径加载它们，Landlock 也按路径放行。
- **插件文件夹。** 学习、课件插件的文件夹仍在原处，`repa-plugin.json` 的入口 `dist/plugin.js` 是一行转出，指向这次构建里的插件入口；两个包的 `package.json` 只导出这个入口，其余 Repa 包不再导出模块。
- **报错的堆栈。** `cli` 的入口先打开 source map 再加载服务，后端报错的堆栈指向原来的源文件。source map 只在生成堆栈时才读，不增加启动时读的文件。

### 不能出错的几件事

**用户插件里的 `@repa/base/plugin` 是进程里唯一的那一份。** 运行上下文和 `RepaFault` 的 `instanceof` 都靠它。解析错到另一份副本时插件照样能加载，只是错误码和运行上下文悄悄失效，所以这是最要防的一处。打包后 `@repa/base/plugin` 只有一个输出文件，宿主、随包插件和用户插件都从同一次构建的同一个文件取得它。安装包核对（`verify-application.mjs`）在装好的应用上放一个自写插件，导入 `@repa/base/plugin` 并抛出带错误码的 `RepaFault`，要求后端原样交回这个错误码；把解析目标改指另一份副本时，这项核对失败。

**按路径找的资源都还在。** 安装包核对照旧覆盖：用安装包的 Electron 拉起后端、两个插件运行、页面里运行 Python、经假模型走一遍 `course_use`。依赖升级后出现新的 worker，构建停下，要求在脚本里说明怎样处理。

**许可证清单不少。** 许可证仍按 `node_modules` 收集，被打包的包都留着 `package.json` 和许可证文件；打包前后清单逐项相同。

## 考虑过的其他做法

- **只裁剪 `node_modules`**（生产依赖去重、删文档和类型声明）：能减少安装时写的文件，但后端启动要读的约 1800 个文件都是真正被导入的模块，一个也少不了，首次打开的十几秒不变。
- **asar**：一个归档文件，扫描只一次。但后端由 Electron 当 Node 拉起，ESM 从 asar 里加载、Python 沙箱里的另一个 Node 按路径读 pyodide、Landlock 按路径放行，处处要解包或绕开，代价和风险都比打包大。
- **直接用 Pi 自己发布的 bundle**：它里面带着自己的一份 pi-ai 和 typebox，Repa 另外导入的 pi-ai 和 typebox 就成了第二份，提供方注册表和 schema 都会分成两份。
- **把资源路径改成显式配置**：要改 Repa 的多处源码，Pi 里的改不了；保持原来的布局只在打包这一步做，源码和开发时的工作区布局都不受影响。

## 验收

- 在 Windows 上，新装的应用第一次打开到显示选空间页，与之后再打开相差不超过几秒；安装时间明显缩短。数字见下一节。
- 三个平台的安装包核对照常通过，其中包括用户插件导入的 `@repa/base/plugin` 是唯一的一份。

## 风险与代价

- **依赖自身位置的写法有漏网的。** 例如某个第三方包按拼出来的路径读一个 `.js` 文件当数据，打包后它被删掉，只在运行到那一处时报错。已查过 Pi 与其余被打包的包，只有 Pi 导出 HTML 的三个脚本属于这一类，已保留；Repa 不调用 Pi 的 HTML 导出。依赖升级时要再查一次。
- **打包步骤多了一个要维护的脚本**，Pi 升级后 worker 的位置、`PI_BUNDLED_NODE` 的含义可能变，构建时的检查只能抓到新出现的 worker。
- **`import.meta.resolve` 改由 `createRequire` 解析**，用的是 require 的条件；现有用法只解析 `package.json` 和普通文件，结果相同。
