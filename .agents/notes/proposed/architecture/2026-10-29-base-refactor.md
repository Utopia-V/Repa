# 底座重构：去掉防御性机制，按约定和 Pi 的设计重整

状态：提案

## 问题

2026 年 10 月对仓库做了一次问题清点，逐条和维护者讨论过。底座这一层的问题大致有三类。

第一类，是为不会发生的问题设的机制：每调用一次插件方法，都跑一次 git log 并唤醒所有插件；为一个在实际组合里从不运行的缓存保温功能，给 Pi 打了补丁；压缩对话前，直接修改 Pi 传进来的内部对象。

第二类，是同一件事写了几套，或者写在了不该写的地方：确认、提问、前端代做服务各有一套"向前端发请求、等回复"；渲染视图时抛错，被当成"不许运行"的关卡；用户改提示词，是整段替换插件的文字。

第三类，是格式和版本只认"相等才打开"：一个插件的数据版本不符，整个空间打不开；没有版本标记的 `.repa/` 会被直接当成当前版本；应用配置放在 `~/.repa`，主目录因此被当成空间。

学习者还没开始用，没有需要保护的真实数据，所以这一轮可以直接改格式，不写迁移。

## 做法

### 空间格式与版本

现状：`.repa/format.json` 和 `plugin-versions/<id>.json` 只做相等检查（`src/space/format.ts`），缺标记时直接写入当前版本（`format.ts:16-17`）。插件的版本检查放在同一个 try 里逐个做，任何一个不符，整个空间都打不开（`src/plugins/host.ts:210`）。应用设置 `<home>/settings.json` 用严格 schema 读取。

做法：

- 旧数据永远能读。新版本负责认得旧格式；需要改写盘上数据时，先备份，成功以后再改标记。
- 遇到比自己新的数据，拒绝打开，不往盘上写任何东西。
- 只有旧版本会读错的改动才升版本。增加一个旧版本可以忽略的字段，不算。读取时忽略不认识的可选字段，设置文件也一样；写入时严格。
- 一个插件的数据打不开，只停这个插件，空间其余部分照常。插件的数据版本由插件自己管理，底座不再维护 `plugin-versions/`。学习插件的数据目录由它独占，无标记的旧数据认作原来的版本 1，只补标记，不改写已有记录，也不需要备份。
- 没有 `format.json` 的 `.repa/` 不是 Repa 写的，比如 repa-writing 的书稿。把它当作认不得的数据：给出提示，不补版本，也不写入。以后写作搬进来时，再专门做导入。
- 写明 `format.json` 的版本 1 覆盖哪些文件和格式，以后才判断得了一次改动该不该升版本。
- 应用配置从 `~/.repa` 搬到系统的配置目录：Linux 用 `~/.config/repa`，Windows 用 `%APPDATA%\Repa`，macOS 用 `~/Library/Application Support/Repa`，`REPA_HOME` 照旧可以覆盖（`src/protocol/server.ts:109`）。这样目录浏览不会再因为有 `.repa/` 就把主目录标成空间（`src/space/browse.ts:59`），应用配置也不会和空间数据混在一起。
- 空间里的 skill 从 `.repa/skills/` 改到 Agent Skills 的通用位置 `.agents/skills/`，Pi 本来就支持这个位置。skill 是用户写的内容，放在这里就是普通文件：Agent 能改，空间历史会记录。
- 删掉前端连接时上报的 `capabilities.interaction.vocabulary` 整数。没有任何地方读它，真正决定前端能显示什么的是能力清单。插件清单里插件自己的 `version` 保留，它是常规的版本标注。

### 删掉没有好处的机制

- 插件方法调用之后的 `history.list(1)`、`wake` 和 `flush`（`src/plugins/host.ts:363-366`）。文件改动本来就经 `space.onRevision` 通知所有插件；插件自己的数据不进历史，拿最新版本号去唤醒别的插件，什么也没告诉它们，还多起一个 git 子进程，历史队列一忙，连读一下学习状态都要排队。删掉。插件自己的状态变了，用插件自己的事件告诉前端。
- 缓存保温的补丁和整套保温设置（`patches/@earendil-works+pi-coding-agent+1.1.0.patch` 及 `src/agent/runtime.ts` 里的保温配置）。底座说明里自己写着：锁定的 Codex 目录没有声明缓存寿命，保温从不触发，真实效果"仍待单独核实"。学习者用的 DeepSeek，缓存本来就能保留几个小时。补丁却锁死了 Pi 的版本，打包时还得单独复现。删掉，一律用 Pi 的默认行为。以后真遇到需要保温的服务商，先实测，再找 Pi 上游解决。
- 压缩前原地过滤 `event.preparation.messagesToSummarize` 里的视图（`src/agent/runtime.ts:706-712`）。Pi 文档里这个钩子只能取消压缩或自己提供摘要，原地修改能生效，靠的是 Pi 当前的内部写法。摘要里提到"之前在做什么"本来就是事实，最新视图会在压缩后立刻补回（`:713-721`），模型以后面的为准。删掉过滤，保留补回。

### 插件和模型之间

- **请求前的关卡。** 现状：辅导 Agent 在渲染视图时检查是否在复习或测验中，靠抛错拦下运行（学习插件 `tutor.ts:256`）；接口说明（`src/plugin.ts:127`）只说视图是"本 Agent 的运行时状态"。视图因为普通的 bug 抛错时，运行也会被拦下，报的错看不出原因。做法：底座给插件 Agent 一个明确的关卡，在每次真正发出模型请求之前调用，可以返回"拒绝，以及拒绝的原因"。视图只负责渲染，出错就按错误报出。dsh 的对应做法是 `agent/pre-step`、`agent/request` 这类请求前钩子。
- **插件调模型。** 现状：`complete` 调用 Pi 的 `completeSimple`，只取回文本，用量被丢掉，也不进任何会话；`completeStructured` 把 JSON Schema 写进提示，请模型只返回 JSON，解析失败就整段重发，最多三次（`src/agent/runtime.ts:335-370`）。做法：插件发起的模型调用，当作一个子任务记进会话的 jsonl，用量随之记下，和其他会话的用量算在一起。结构化结果改用模型原生的机制来取，比如带 schema 的工具调用；失败就返回失败和一句简短诊断，不靠重发碰运气。dsh 的子 Agent 用 `outputSchema` 请求结构化结果（`docs/subsystems/subagent.md`）。
- **超长的工具输出。** 现状：`src/agent/output.ts` 用 Pi 的 `truncateHead` 截断，如果第一行就超过约 50 KB，Pi 返回空内容，模型只看到一句"已省略多少字节"。插件工具常把结果写成一整行 JSON，正好撞上。做法：超过上限时，保留开头和结尾，把全文存进一个文件，告诉模型文件路径，模型用读文件工具接着读。这样插件工具不必各自做分页。dsh 的 spill-policy 也是这样做的。至于给模型看的内容本身只放它需要的、写成分行的文字，由各插件负责。

### 提示词画板

现状：用户在设置页改提示词，存的是按段的编号整段替换的文字（`src/agent/prompts.ts:16-20`、`src/settings.ts:56-69`），不记录它是基于哪一版默认文字改的。插件更新默认文字后，改过这一段的用户收不到更新；插件改了段的编号，用户的修改会悄悄失效。两种情况都没有任何提示。

做法：提示词由一块块画板拼成，统一在一处注册。插件把自己的板放进去，并声明放在什么位置。位置是固定的，用户不调整顺序，这样提示的前缀稳定，缓存也能命中。用户写在自己的板上：空间根目录的 AGENTS.md 已经是一块，如果需要，再给每个 Agent 加一块用户板。插件的板对用户只读，可以关掉。插件更新时只改自己的板，用户写的东西不会被覆盖，也不会失效。

设置页随之改成三件事：看每块板的来源、位置、是否启用和最终拼成的样子；开关插件的板；编辑用户自己的板。现有的整段覆盖不保留，因为还没有真实用户。#41 由维护者按这个做法改写。dsh 的 `ctx.systemPrompt` 是同样的结构（`packages/core/system-prompt/README.md`）：片段按序号拼接，部署方的定制是单独的前后两块板，不改插件片段的文字。

### 前后端之间

- **三套反向请求合成一套。** 现状：确认、提问、前端代做服务各有一张待回复的表、一份取消逻辑和一种连接绑定（`src/protocol/server.ts:114-116`），连接断开时还要分别清理（`:159-175`）。做法：底座只保留一套"向前端发请求、等回复"的通用机制，请求带编号、可以取消、连接一断就作废，三者都建在它上面，只是请求的内容不同。
- **重连以后的运行状态。** 现状：前端重连后，把运行状态直接设成空闲，排队的消息有没有送到也不知道（Web 的 `src/lib/store.ts:486`），因为协议里查不到当前的运行状态。做法：连上以后，后端先挂好事件订阅，再把当前状态作为基线发给前端，包括哪些会话正在运行、排队的消息去了哪里；前端收到基线后才开始显示。dsh 的连接层就是先订阅、再发"就绪"、前端再读基线（`packages/client/connection/README.md`）。前端那边的逐级退避重连和连接状态显示，由 Aqua 来做。

### 会话按 Pi 的方式建立

现状：新会话先用 `openSync(<随机 uuid>.jsonl)` 建一个空文件，再用 `SessionManager.open` 打开（`src/agent/runtime.ts:504-516`），文件名和会话编号毫无关系，按编号找会话只能把文件逐个打开、读会话头（`:536-548`）。#66 的几次修复补的都是这个绕路。代码注释说，这样做是为了让会话一建立就有文件、在第一条回复之前也不丢消息。可 Pi 1.1.0 的 `SessionManager.create(cwd, dir, { id })` 允许调用方传入编号，文件名是 `<时间戳>_<id>.jsonl`；文件在出现第一条用户或助手消息时写入，此前缓冲的条目会一起写进去（`session-manager.js` 的 `_persist`）。在那之前进程崩溃，丢掉的只是一个还没说过话的空会话。

做法：新会话改用 Pi 的 `create`，编号由我们传入，按文件名查找。已有的旧会话文件，打开时按会话头改一次名，之后就不再需要逐个读头。

### 时钟

底座给插件提供时钟，测试里可以拨动，插件不再各自直接取 `Date.now()`。学习插件会用它判断到期、限时和"距上次学习多久"。

### 保留的东西

- 精确编辑工具（`src/agent/edit.ts`）保留，在代码里写清为什么不用 Pi 的那一步：Pi 的编辑在精确匹配失败时会做模糊匹配，并把被改到的那一行整行换成规范化后的文字，包括 NFKC、去掉行尾空白、把弯引号和破折号换成 ASCII。中文段落常常就是一整行，全角的，：；（）！？会被改成半角，“”会变成英文引号。
- 文件、改动通知、历史、模型调用、`runAgent`、工具里向用户提问、`createModelScope`，这些接口都保留。学习插件把知识放进空间文件以后，会用到前三样；写作很快会用到 `runAgent` 和提问；`createModelScope` 服务于嵌套插件。

### 构建

第 2 步已落地：根目录以 `tsc -b` 和 project references 统一准备库包，包内独立入口也使用同一引用关系。构建命令与配套产物见[开发指南](../../../../docs/development/README.md#增量构建)。原有 `ensure-base.ts` 的时间戳扫描与构建锁随之删除；增量判断交给 TypeScript，同一 worktree 的构建命令串行运行。

改用 TypeScript 的增量构建：在根目录统一构建一次，每个包只编译一遍，没改过的直接跳过；各个包的 pretest、predev 等脚本不再自己去构建依赖。现在根目录跑一次全量测试，底座要构建 5 次，学习模型库 3 次，学习插件 2 次。

## 分步

一次做完不现实，所以按依赖拆成七步。每一步一个分支、一次审阅、一次合并，验收取下面"验收"里对应的几条。前面的步骤不依赖后面的。

1. **删掉没有好处的机制。**（已落地）方法调用后的 git log、保温补丁和保温设置、压缩前的过滤、词汇版本整数；顺带给精确编辑工具补上说明。这一步全是删除和注释，风险最小，先做。
2. **增量构建。**（已落地）放在前面，是因为之后每一步跑测试都会快很多。
3. **会话与时钟。**（已落地）会话改用 Pi 的 `create`，旧会话文件改一次名；底座提供时钟。学习插件重写时要用到这个时钟。
4. **空间格式与版本。**（已落地）三条规则、插件失败隔离、读宽写严、没有标记的目录、应用配置的位置、skill 的位置。这一步要在学习记录改成"只记事实"之前做完，因为插件的数据版本将改由插件自己管理。
5. **插件和模型之间。**（已落地）请求前的关卡、插件调模型记进会话并记用量、结构化结果改用原生机制、超长输出存文件。学习插件的辅导关卡和开放题判分都要用到。
6. **前后端之间。**（后端已落地，前端由 Aqua 跟进）反向请求合成一套；重连时先订阅，再发基线。前端那一半由 Aqua 跟进。
7. **提示词画板。** 后端的注册方式和设置页一起改，设置页由 Aqua 来做，#41 由维护者改写。

第 1 到第 5 步做完，学习插件那一大步就可以开始；第 6、7 步可以和学习插件的工作同时进行。

## 考虑过的其他做法

- **提示词：给用户的修改记下基于哪一版默认文字，默认变了就提醒。** 放弃了。画板做法让用户的字和插件的字从根上分开，既不需要记版本，也不需要提醒。
- **插件调模型：只记用量，不存对话，因为输入随时能从事实重新拼出来。** 放弃了。统一成"所有模型调用都在 jsonl 里"，更简单，也更一致。
- **压缩：向 Pi 上游要一个正式的过滤钩子。** 暂时不做。等真用起来，发现模型确实被摘要里的旧状态带偏了，再考虑。
- **保温：保留补丁，补做真实服务上的核实。** 放弃了。学习者用的服务不需要保温，而补丁的代价是确定的。
- **删掉暂时没人用的接口，比如 `createModelScope`。** 放弃了。它独立、不牵连别处，删掉换不来任何好处，而且嵌套插件本来就是既定设计。

## 验收

- 新版本能打开旧版本写的空间；遇到更新版本写的空间，给出提示，不写任何东西；一个插件的数据坏了，只有这个插件停用，对话和历史照常可用。
- 主目录不会再被当成空间，应用配置不在任何空间的 `.repa/` 里。
- 插件能在模型请求发出之前拒绝，并给出原因；视图出错时，看到的就是那个错误本身。
- 每一次模型调用，包括插件发起的，都能在会话的 jsonl 里找到，并且带着用量。
- 工具输出再长，模型也能看到开头、结尾和全文所在的位置，并能接着读完。
- 用户写在自己板上的提示，在插件更新之后原样保留；插件的新文字也照样生效。
- 确认、提问、代做服务在连接断开时一起作废，背后只有一套代码。
- 前端重连以后显示的运行状态，和后端的实际状态一致。
- 按编号打开一个会话，只读一个文件。
- `patches/` 是空的，升级 Pi 不会被补丁挡住。
- 全量测试时，每个包只构建一次。

## 风险与代价

- 插件接口有不兼容的改动：视图的语义、新增的请求前关卡、提示词的注册方式。用到这些接口的只有本仓库的学习插件和示例插件，在同一轮里一起改。
- 维护者和 Aqua 本机已有的 `~/.repa` 配置、提示词覆盖和旧会话文件：配置搬一次，提示词覆盖不保留，旧会话文件改一次名。没有学习者的数据，不写其他迁移。
- 删掉保温以后，如果换成缓存寿命很短的服务商，空闲之后的第一次请求会贵一些。真遇到时，先实测再说。
