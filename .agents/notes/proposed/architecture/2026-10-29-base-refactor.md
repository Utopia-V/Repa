# 底座重构：移除防御性机制，按约定与 Pi 的设计重整

状态：提案

## 问题

2026 年 10 月对仓库进行了一次问题清点，所列问题均经维护者逐条讨论。底座层的问题大致分为三类。

第一类是为不会发生的问题设置的机制：每次调用插件方法都运行一次 git log 并唤醒所有插件；为一个在实际组合中从不运行的缓存保温功能给 Pi 打了补丁；压缩对话前直接修改 Pi 传入的内部对象。

第二类是同一件事写了几套，或写在了不应写的位置：确认、提问、前端代做服务各有一套"向前端发请求、等回复"；渲染视图时抛错被当作"不许运行"的关卡；用户修改提示词的方式是整段替换插件的文字。

第三类是格式和版本只认"相等才打开"：一个插件的数据版本不符，整个空间便无法打开；没有版本标记的 `.repa/` 会被直接当作当前版本；应用配置放在 `~/.repa`，主目录因此被当作空间。

学习者尚未开始使用，没有需要保护的真实数据，因此本轮可直接修改格式，不写迁移。

## 做法

### 空间格式与版本

现状：`.repa/format.json` 和 `plugin-versions/<id>.json` 只做相等检查（`src/space/format.ts`），缺少标记时直接写入当前版本（`format.ts:16-17`）。插件的版本检查放在同一个 try 中逐个进行，任何一个不符，整个空间均无法打开（`src/plugins/host.ts:210`）。应用设置 `<home>/settings.json` 用严格 schema 读取。

做法：

- 旧数据始终可读。新版本负责识别旧格式；需要改写盘上数据时，先备份，成功后再修改标记。
- 遇到版本高于自身的数据时，拒绝打开，不向盘上写入任何内容。
- 只有旧版本会读错的改动才升版本。增加一个旧版本可以忽略的字段不在此列。读取时忽略不认识的可选字段，设置文件亦然；写入时严格。
- 某个插件的数据无法打开时，只停用该插件，空间其余部分照常。插件的数据版本由插件自行管理，底座不再维护 `plugin-versions/`。学习插件独占其数据目录，无标记的旧数据视为原来的版本 1，只补标记，不改写已有记录，也无需备份。
- 没有 `format.json` 的 `.repa/` 并非 Repa 所写，例如 repa-writing 的书稿。将其视为无法识别的数据：给出提示，不补版本，也不写入。日后写作迁入时，再专门实现导入。
- 写明 `format.json` 的版本 1 覆盖哪些文件和格式，日后才能判断一次改动是否应升版本。
- 应用配置从 `~/.repa` 迁至系统的配置目录：Linux 用 `~/.config/repa`，Windows 用 `%APPDATA%\Repa`，macOS 用 `~/Library/Application Support/Repa`，`REPA_HOME` 仍可覆盖（`src/protocol/server.ts:109`）。由此，目录浏览不会再因存在 `.repa/` 而把主目录标为空间（`src/space/browse.ts:59`），应用配置也不会与空间数据混杂。
- 空间中的 skill 从 `.repa/skills/` 移至 Agent Skills 的通用位置 `.agents/skills/`，Pi 原本即支持该位置。skill 是用户编写的内容，放在此处即为普通文件：Agent 可以修改，空间历史会记录。
- 删除前端连接时上报的 `capabilities.interaction.vocabulary` 整数。没有任何地方读取它，前端能显示什么实际由能力清单决定。插件清单中插件自身的 `version` 保留，它是常规的版本标注。

### 移除无收益的机制

- 插件方法调用之后的 `history.list(1)`、`wake` 和 `flush`（`src/plugins/host.ts:363-366`）。文件改动原本即经由 `space.onRevision` 通知所有插件；插件自身的数据不进入历史，用最新版本号唤醒其他插件，并未向它们传递任何信息，还多启动一个 git 子进程；历史队列繁忙时，连读取学习状态也须排队。删除。插件自身的状态变化时，用插件自己的事件通知前端。
- 缓存保温的补丁和整套保温设置（`patches/@earendil-works+pi-coding-agent+1.1.0.patch` 及 `src/agent/runtime.ts` 中的保温配置）。底座说明自己写明：锁定的 Codex 目录没有声明缓存寿命，保温从不触发，真实效果"仍待单独核实"。学习者使用的 DeepSeek，缓存本就能保留数小时。补丁却锁死了 Pi 的版本，打包时还须单独复现。删除，一律采用 Pi 的默认行为。日后若确实遇到需要保温的服务商，先实测，再寻求 Pi 上游解决。
- 压缩前原地过滤 `event.preparation.messagesToSummarize` 中的视图（`src/agent/runtime.ts:706-712`）。按 Pi 文档，该钩子只能取消压缩或自行提供摘要；原地修改之所以生效，依赖的是 Pi 当前的内部写法。摘要中提到"之前在做什么"本属事实，最新视图会在压缩后立即补回（`:713-721`），模型以后者为准。删除过滤，保留补回。

### 插件与模型之间

- **请求前的关卡。** 现状：辅导 Agent 在渲染视图时检查是否处于复习或测验中，靠抛错拦下运行（学习插件 `tutor.ts:256`）；接口说明（`src/plugin.ts:127`）只说视图是"本 Agent 的运行时状态"。视图因普通 bug 抛错时，运行同样会被拦下，且报错看不出原因。做法：底座为插件 Agent 提供一个明确的关卡，在每次实际发出模型请求之前调用，可返回"拒绝，以及拒绝的原因"。视图只负责渲染，出错即按错误报出。dsh 的对应做法是 `agent/pre-step`、`agent/request` 这类请求前钩子。
- **插件调模型。** 现状：`complete` 调用 Pi 的 `completeSimple`，只取回文本，用量被丢弃，也不进入任何会话；`completeStructured` 把 JSON Schema 写进提示，要求模型只返回 JSON，解析失败即整段重发，最多三次（`src/agent/runtime.ts:335-370`）。做法：插件发起的模型调用作为一个子任务记入会话的 jsonl，用量随之记录，并与其他会话的用量合并计算。结构化结果改用模型原生的机制获取，例如带 schema 的工具调用；需要防范的是旧做法那种盲目重发：模型不知错在何处，整段请求原样再发。模型写错工具名或参数不合格时，Pi 会把具体错误告知模型，在同一会话中给它一次更正机会，这是带有信息的更正，保留；整次调用最多两个请求，仍不正确则返回失败和一句简短诊断。dsh 的子 Agent 用 `outputSchema` 请求结构化结果（`docs/subsystems/subagent.md`）。
- **超长的工具输出。** 现状：`src/agent/output.ts` 用 Pi 的 `truncateHead` 截断；若第一行即超过约 50 KB，Pi 返回空内容，模型只看到一句"已省略多少字节"。插件工具常把结果写成一整行 JSON，恰好落入这种情况。做法：超过上限时，保留开头和结尾，将全文存入一个文件并告知模型文件路径，模型用读文件工具继续读取。由此插件工具不必各自实现分页。dsh 的 spill-policy 亦采用此做法。至于给模型看的内容本身只含其所需、写成分行文字，由各插件负责。

### 提示词画板

现状：用户在设置页修改提示词时，保存的是按段编号整段替换的文字（`src/agent/prompts.ts:16-20`、`src/settings.ts:56-69`），不记录修改基于哪一版默认文字。插件更新默认文字后，改过该段的用户收不到更新；插件修改段的编号后，用户的修改会悄然失效。两种情况均无任何提示。

做法：提示词由若干块画板拼成，统一在一处注册。插件放入自己的板，并声明其位置。位置固定，用户不调整顺序，由此提示的前缀保持稳定，缓存得以命中。用户在自己的板上书写：空间根目录的 AGENTS.md 已是一块；如有需要，再为每个 Agent 增加一块用户板。插件的板对用户只读，可以关闭。插件更新时只修改自己的板，用户所写内容不会被覆盖，也不会失效。

设置页随之改为三项功能：查看每块板的来源、位置、是否启用和最终拼接结果；开关插件的板；编辑用户自己的板。现有的整段覆盖不保留，因为尚无真实用户。#41 由维护者按此做法改写。dsh 的 `ctx.systemPrompt` 采用相同结构（`packages/core/system-prompt/README.md`）：片段按序号拼接，部署方的定制是单独的前后两块板，不修改插件片段的文字。

### 前后端之间

- **三套反向请求合成一套。** 现状：确认、提问、前端代做服务各有一张待回复的表、一份取消逻辑和一种连接绑定（`src/protocol/server.ts:114-116`），连接断开时还须分别清理（`:159-175`）。做法：底座只保留一套"向前端发请求、等回复"的通用机制，请求带编号、可以取消、连接一断即作废；三者均建于其上，仅请求内容不同。
- **重连以后的运行状态。** 现状：前端重连后直接把运行状态设为空闲，也无从得知排队的消息是否已送达（Web 的 `src/lib/store.ts:486`），因为协议中查不到当前的运行状态。做法：连接建立后，后端先挂好事件订阅，再把当前状态作为基线发给前端，包括哪些会话正在运行、排队的消息去向；前端收到基线后才开始显示。dsh 的连接层即为先订阅、再发"就绪"、前端再读基线（`packages/client/connection/README.md`）。前端的逐级退避重连和连接状态显示由 Aqua 实现。

### 会话按 Pi 的方式建立

现状：新会话先用 `openSync(<随机 uuid>.jsonl)` 建一个空文件，再用 `SessionManager.open` 打开（`src/agent/runtime.ts:504-516`）；文件名与会话编号毫无关系，按编号查找会话只能逐个打开文件、读取会话头（`:536-548`）。#66 的几次修复均在弥补这一绕路。代码注释称，此举是为了让会话一建立即有文件，在第一条回复之前也不丢失消息。然而 Pi 1.1.0 的 `SessionManager.create(cwd, dir, { id })` 允许调用方传入编号，文件名为 `<时间戳>_<id>.jsonl`；文件在出现第一条用户或助手消息时写入，此前缓冲的条目会一并写入（`session-manager.js` 的 `_persist`）。若进程在此之前崩溃，丢失的只是一个尚未产生对话的空会话。

做法：新会话改用 Pi 的 `create`，编号由我们传入，按文件名查找。已有的旧会话文件在打开时按会话头重命名一次，此后不再需要逐个读取会话头。

### 时钟

底座为插件提供时钟，测试中可以拨动，插件不再各自直接调用 `Date.now()`。学习插件将用它判断到期、限时和"距上次学习多久"。

### 保留的部分

- 精确编辑工具（`src/agent/edit.ts`）保留，并在代码中写明不用 Pi 那一步的原因：Pi 的编辑在精确匹配失败时会做模糊匹配，并把被改动的那一行整行替换为规范化后的文字，包括 NFKC、去除行尾空白、把弯引号和破折号换成 ASCII。中文段落常为一整行，其中全角的，：；（）！？会被改为半角，“”会变为英文引号。
- 文件、改动通知、历史、模型调用、`runAgent`、工具中向用户提问、`createModelScope`，这些接口均保留。学习插件把知识放入空间文件后将用到前三项；写作很快会用到 `runAgent` 和提问；`createModelScope` 服务于嵌套插件。

### 构建

第 2 步已落地：根目录以 `tsc -b` 和 project references 统一准备库包，包内独立入口也使用同一引用关系。构建命令与配套产物见[开发指南](../../../../docs/development/README.md#增量构建)。原有 `ensure-base.ts` 的时间戳扫描与构建锁随之删除；增量判断交给 TypeScript，同一 worktree 的构建命令串行运行。

改用 TypeScript 的增量构建：在根目录统一构建一次，每个包只编译一遍，未改动的直接跳过；各包的 pretest、predev 等脚本不再自行构建依赖。目前在根目录运行一次全量测试，底座需构建 5 次，学习模型库 3 次，学习插件 2 次。

## 分步

一次完成并不现实，因此按依赖拆为七步。每一步对应一个分支、一次审阅、一次合并，验收取下文"验收"中对应的几条。前面的步骤不依赖后面的步骤。

1. **移除无收益的机制。**（已落地）方法调用后的 git log、保温补丁和保温设置、压缩前的过滤、词汇版本整数；同时为精确编辑工具补上说明。这一步仅涉及删除和注释，风险最小，因此最先进行。
2. **增量构建。**（已落地）排在前面，是因为此后每一步运行测试都会快很多。
3. **会话与时钟。**（已落地）会话改用 Pi 的 `create`，旧会话文件重命名一次；底座提供时钟。学习插件重写时需用到该时钟。
4. **空间格式与版本。**（已落地）三条规则、插件失败隔离、读宽写严、没有标记的目录、应用配置的位置、skill 的位置。这一步须在学习记录改为"只记事实"之前完成，因为插件的数据版本将改由插件自行管理。
5. **插件与模型之间。**（已落地）请求前的关卡、插件调模型记入会话并记录用量、结构化结果改用原生机制、超长输出存入文件。学习插件的辅导关卡和开放题判分均需用到。
6. **前后端之间。**（后端已落地，前端由 Aqua 跟进）反向请求合成一套；重连时先订阅，再发基线。前端部分由 Aqua 跟进。
7. **提示词画板。** 后端的注册方式与设置页一并修改，设置页由 Aqua 实现，#41 由维护者改写。

第 1 至第 5 步完成后，学习插件这一大步即可开始；第 6、7 步可与学习插件的工作同时进行。

## 考虑过的其他做法

- **提示词：为用户的修改记下所基于的默认文字版本，默认文字变化时提醒用户。** 已放弃。画板做法从根本上分开了用户的文字和插件的文字，既无需记录版本，也无需提醒。
- **插件调模型：只记录用量，不保存对话，因为输入随时可从事实重新拼出。** 已放弃。统一为"所有模型调用均在 jsonl 中"更简单，也更一致。
- **压缩：向 Pi 上游请求一个正式的过滤钩子。** 暂不实施。待实际使用中确认模型确实被摘要中的旧状态带偏后，再作考虑。
- **保温：保留补丁，补做在真实服务上的核实。** 已放弃。学习者使用的服务不需要保温，而补丁的代价是确定的。
- **结构化结果一律不重试，首次不合格即失败。** 已放弃。这把"不盲目重发"用过了头：Pi 的更正带有具体错误，几乎都能一次改对；直接失败则判分没有证据，日后补判还须再发一次完整的请求。
- **删除暂时无人使用的接口，例如 `createModelScope`。** 已放弃。它独立、不牵连别处，删除不会带来任何好处，而且嵌套插件本就是既定设计。

## 验收

- 新版本能打开旧版本写的空间；遇到更高版本写的空间时给出提示，不写入任何内容；某个插件的数据损坏时，只有该插件停用，对话和历史照常可用。
- 主目录不再被当作空间，应用配置不在任何空间的 `.repa/` 中。
- 插件能在模型请求发出之前拒绝并给出原因；视图出错时，所见即为该错误本身。
- 每一次模型调用，包括插件发起的调用，均能在会话的 jsonl 中找到，并附有用量。
- 无论工具输出多长，模型均能看到开头、结尾和全文所在的位置，并能继续读完。
- 用户写在自己板上的提示在插件更新后原样保留；插件的新文字也照常生效。
- 确认、提问、代做服务在连接断开时一并作废，背后只有一套代码。
- 前端重连后显示的运行状态与后端的实际状态一致。
- 按编号打开一个会话，只读一个文件。
- `patches/` 为空，升级 Pi 不会受补丁阻碍。
- 全量测试时，每个包只构建一次。

## 风险与代价

- 插件接口有不兼容的改动：视图的语义、新增的请求前关卡、提示词的注册方式。使用这些接口的只有本仓库的学习插件和示例插件，在同一轮中一并修改。
- 维护者和 Aqua 本机已有的 `~/.repa` 配置、提示词覆盖和旧会话文件：配置迁移一次，提示词覆盖不保留，旧会话文件重命名一次。尚无学习者的数据，因此不写其他迁移。
- 删除保温后，若换用缓存寿命很短的服务商，空闲之后的第一次请求费用会高一些。届时先实测再作处理。
