# Repa 给自己写插件：运行中装卸，插件带自己的页面

状态：提案

## 问题

使用者想让 Repa 做一件它原本不会的事，例如把课件转成文字，或者每天看一遍某个论坛板块的新帖。现在只有两条路，都不合适。

其一是让通用 Agent 当场想办法。它会摸索一番，写一段临时脚本，把事情办成；下一次再提同样的要求，它又从头摸索一遍。办法没有留下来，做得好坏每次都看运气，结果也只出现在对话里，软件里没有一处地方可以回头查看。

其二是写一个插件。插件能留下来，也能把状态存在模型之外，可是现在的插件只能由开发者来写：它是构建好的 TypeScript 目录，进程启动时导入一次，运行中不能添加、卸载或替换（[`@repa/base` 说明](../../../../packages/base/README.md#停用插件)写明“不提供自动重启或在线启停”）；插件也没有自己的界面，学习的界面写在 `apps/web` 里，换一个领域就得改前端。

于是“Repa 是领域状态的底座，领域由插件承担”这句话，目前只对我们自己写的学习插件成立。别的领域能不能用这个底座，要等有人坐下来写一个包、改一遍前端、重新发布才知道。

## 做法

### 已定的要求

以下各项是我的决定，设计以此为前提。

- **Repa 能给自己写插件并使用。** 反复出现的需求由 Agent 写成插件留下来，以后直接使用，不再每次临时摸索。
- **常用的插件随产品附带。** 随包插件与自写插件用同一个接口和同一种文件夹形式，区别只在于谁写的、放在哪里。
- **插件在软件里有自己的界面，装上就生效。** 写完不需要重新构建、重新安装或重启。参照是 DeepSeek Harness（下称 dsh）的做法。
- **界面先只给插件自己的一块地方。** 插件暂时不能改动应用别处的界面；对话旁的面板、工具结果的卡片这类位置，等需求出现再逐个开放。
- **定时任务可以是代码，也可以是提示词。** 确定的部分写成代码，需要判断的部分交给 Agent，两者可以并用。
- **界面文字由人书写的规则（[#101](https://github.com/Utopia-V/repa/issues/101)）管的是随产品发布的界面。** 随包插件的页面照此办理；使用者自己的 Repa 为他写的插件，页面文字出自模型，不在这条规则之内。

### dsh 的做法与 Repa 的现状

dsh 的现状取自仓库 `deepseek-ai/deepseek-harness` 主分支 2026-11-13 的内容，当时最新的 tag 是 `dsh-v0.2.2-rc.3`；下面的路径均相对该仓库。

在 dsh 里，Agent 用普通的文件工具写一个 npm 包：后端的一半是 `index.js`，页面的一半是 `client.js`，可以是纯 JavaScript，不经构建（`packages/preset/agent-preset/skills/dsh-doc/references/host-plugin.md`、`templates/decoration/`）。写好以后调用 `plugin_manager` 工具的 `install_bundle`，这一步需要用户批准或会话处于完全访问模式（`packages/boot/plugin-manager/src/tools.ts`）。启用了热更新的组合里，插件当场生效，页面不刷新（`packages/boot/hmr/README.md`、`packages/client/hmr/README.md`）。

这套做法有四处值得留意。

- 页面的一半是主页面里的一段普通脚本，向预留的位置注册 React 组件，与应用共用同一个全局环境，没有隔离（`packages/client/modules/src/client/main-realm.ts`）。预留位置的目录现有 122 项，其中 54 项标明会替换自带界面（`packages/extensions/cordis-client-runner/src/client/slot-catalog.ts`）。官方给外部作者的指引要求不要引用应用的公共组件，因为它们“会无通知地改变”（`skills/dsh-doc/references/practices.md`）。
- 页面与后端那一半之间的类型化调用，文档要求经构建期生成的描述符，客户端不在运行时发现后端的方法（`docs/api-gateway.md`）。给 Agent 的写法说明因此让手写插件借用已有的通道；手写描述符能否工作，没有查证。
- Agent 走的安装路径在替换已加载的代码时，靠 Node 的内部接口从模块缓存里删除记录（`packages/boot/hmr/src/index.ts`、`package-manifest.ts`），文档自述依赖内部实现。在这条路径上，新版本加载失败时旧插件已经停下，不会恢复。
- 插件在启动函数之外抛出未处理的异常，整个进程退出（`packages/boot/app-boot/src/index.ts` 的 `installFailLoud`）。

Repa 与它的距离比表面上近。插件的贡献本来就是声明式的：工具、Agent、协议方法、说明、view 都是实例返回的值，由宿主持有，宿主也已有停用单个插件的路径（`packages/base/src/plugins/host.ts` 的 `disable`）。界面调用插件有一条不需要生成代码的通用通道，即协议的 `plugin.call` 与 `plugin.event`，参数和结果在运行时按 schema 校验，学习界面用的就是它。缺的是下面五样：

- 运行中加载和替换插件的入口。插件现在只在 CLI 启动时导入（`packages/base/src/cli.ts`）。
- 会话对插件集合变化的响应。会话创建时把工具清单交给 Pi，此后不变（`packages/base/src/agent/runtime.ts`）。
- 协议里表示“插件集合变了”的通知，以及前端对它的响应。前端每个空间只读一次插件列表，而且只用来判断学习插件在不在。
- 插件提供界面的途径。页面的内容安全策略与桌面端的 `repa://` 协议只放行安装包内的内容。
- 给 Agent 用的安装入口和写法说明。

### 插件文件夹

插件的单位是一个文件夹，下称插件文件夹。它包含清单、入口模块，以及可选的页面：

```text
reddit-digest/
  repa-plugin.json
  index.ts
  page/
    index.html
```

清单仍是 `repa-plugin.json`，在现有四个字段之外增加两个可选字段，标题和页面声明：

```json
{
  "id": "reddit-digest",
  "version": "0.1.0",
  "baseVersion": "^0.1.0",
  "entry": "index.ts",
  "title": "板块摘要",
  "pages": [{ "id": "main", "title": "板块摘要", "entry": "page/index.html" }]
}
```

入口模块导出的仍是现在的 `Plugin`：`open(host)` 返回实例，实例声明工具、Agent、方法、说明和 view。自写插件与学习插件用同一个接口，不另设一套较弱的接口，否则“别的领域能不能用这个底座”就没有得到检验。

对入口模块有一条新的要求：模块顶层只定义代码，打开文件、启动定时器、联网这类事放在 `open` 里做，并在 `close` 里收回。宿主要先导入新版本才知道它能不能用，顶层有副作用的模块在导入失败时会留下收不回的东西。

入口可以是 `.js`、`.mjs` 或 `.ts`。桌面端后端运行在 Electron 44.3.0 自带的 Node 24.20.0 上，它默认剥离类型，`.ts` 文件不经构建即可导入；在该版本上试过，入口、它静态导入的文件、JSON 导入和动态 `import()` 都能加载。限制有三条，写进给 Agent 的说明：导入要写真实的扩展名；不能用 `enum` 等需要转换的语法；只用 ES 模块。类型剥离不处理 `node_modules` 下的文件，随包插件装在那里，所以仍以构建产物发布，依赖也照常由包管理器安装。

自写插件的代码可以导入三类东西：Node 的内置模块、文件夹内自己的文件、宿主提供的 `@repa/base/plugin`。这个入口现在只导出类型和少量常量，要补上插件作者实际用得到的运行时导出：声明参数用的 `Type`（取自 `typebox`）和错误类 `RepaFault`。宿主把这个名字解析到自己的那一份，插件与宿主因此共用同一个 `RepaFault`，错误码不会退化。导入文件夹之外的文件或别的包会被拒绝。这不是安全边界，代码仍可以用 `node:fs` 读写任何文件、用 `node:child_process` 运行别的程序；它保证的是模块的依赖都在快照之内，批准覆盖的就是这份快照和受这条规则约束的导入，其余的运行行为属于“批准一个本机程序”所承担的信任。第三方包暂不支持，见[待定](#待定)。

自写插件放在空间里的 `.agents/plugins/<id>/`，与空间 Skill 的目录并列。Agent 在这里写文件不需要确认，写入进空间历史，写坏了可以撤回，也随空间一起备份和迁移。随包插件在安装包内，由产品装配。一个空间里插件 id 不能重复，自写插件不能与随包插件同名。

### 批准与快照

插件的入口模块是本机代码，在后端进程里运行，权限与使用者本人相同。这一点对随包插件早已如此；自写插件的不同在于代码出自模型，而且运行时不再逐条确认。通用 Agent 执行命令默认要逐次确认，插件一旦运行，它的工具和方法不再询问。

批准要防的是一件事：代码在使用者不知情时开始运行。具体有两种情形，一是 Agent 改了插件的代码，改动未经同意就生效；二是打开别人给的空间或从别处复制来的空间，其中的代码自行运行。批准防不了已经批准的代码做错事，它能做使用者本人能做的任何事。

为此，编辑的地方与运行的版本分开。空间里的插件文件夹只是编辑的地方；运行的是宿主保管的一份只读快照，入口模块从快照导入，页面的文件也从快照提供。空间里的文件夹此后怎样改动，都不影响正在运行的版本，改动要生效就得再批准一次。

批准一次的顺序是固定的：

1. 宿主把插件文件夹当时的内容复制到一个暂存位置。只收普通文件，遇到符号链接就拒绝，总大小有上限。
2. 对复制好的这一份计算摘要、读清单，并与当前运行的版本比较。请求批准时，界面展示的是这一份：插件的标题、声明的页面、改动了哪些文件。此后不再读源文件夹来决定这次运行什么。
3. 使用者同意以后，宿主把这一份整体移入已批准快照的目录，以摘要命名。移入是原子的。
4. 使用者拒绝、取消，或复制中途出错，暂存的这一份丢弃，不参与加载。

已批准快照的目录在应用配置目录中，由宿主管理。一份完整的快照在那里存在，就是它在本机被批准过的记录，不另设批准清单。加载时核对快照内容与目录名中的摘要一致。Agent 的文件工具不能写这个目录和暂存位置，这一限制按规范路径判断，不依赖它们恰好在空间之外。

这样安排有三个后果。

- 批准的对象是确定的。使用者看到什么，运行的就是什么，中间没有可以被改写的间隙。
- 快照不随空间走。空间被复制到另一台机器，那里没有对应的快照，插件不运行。
- 每个版本是不同的目录，Node 把它们当作不同的模块，替换不需要清除模块缓存。每个插件保留两份快照：当前选定的版本和上一次选定的版本，更早的由宿主清理。使用者可以让上一次选定的版本重新生效；它是上一次选定的，不保证是最后一个能运行的。

完全访问模式下，Agent 在运行中明确提出的加载不再询问；打开空间时发现的未批准插件，任何模式下都不自动运行。这一条只对文件工具成立：完全访问模式下 Agent 的命令工具能写任何地方，包括快照目录，那时的保证与命令工具本身相同。

快照按空间文件夹的路径分组存放，与备份的做法相同。空间文件夹移动或改名以后，原来的快照对不上，插件转为待批准，要再批准一次。

### 启用状态

每个空间记着它启用了哪些自写插件，以及各自选定的版本的摘要和上一次选定的版本的摘要。这是使用者的意图，持久保存，在打开插件之前写入：一个版本打不开时，记录仍然指向它，插件显示为失败，重新打开空间也不会悄悄换回旧的版本。实际运行的，是这份记录经过摘要核对、导入、打开和声明核对以后的结果，没能运行的带着失败或待批准的状态。

插件列表取启用记录与空间里发现的插件文件夹的并集，每个插件有两项互不相干的状态。

运行状态：

| 状态 | 含义 |
| --- | --- |
| 未启用 | 空间里有这个插件文件夹，但没有启用。不运行 |
| 运行中 | 已启用，实例已打开 |
| 待批准 | 已启用，但本机没有记下的那个版本的快照 |
| 失败 | 已启用，但打开失败、声明与别的插件冲突，或它引用的插件不在，附原因 |
| 暂停 | 已启用，但宿主有意不运行它：后端异常退出以后，使用者选择了暂停自写插件再启动 |

源文件夹的状态，相对于记下的版本：相同、有改动、缺失、无法读取。它在读取列表或文件变化时刷新，本身不引起任何装卸。

“待批准”时能做什么，取决于源文件夹。内容与记下的摘要相同，批准的就是那个版本；内容不同，批准的是文件夹现在的内容，界面要说明这是换了一个版本；源文件夹缺失，就没有可批准的内容，只能卸载。

卸载就是取消启用，重新打开空间以后它不会自己回来。文件夹、快照和数据目录都保留。运行的既然是快照，删掉空间里的文件夹并不会让插件停下，要停就卸载。

一个插件的 Agent 声明可以引用另一个插件的工具或 Agent。被引用的插件不在时，引用方转为失败。插件集合每变化一次，全部插件都重新打开，声明按整个集合重新核对，所以被引用的插件回来以后，引用方随之恢复，不必另行加载。

插件自己的数据格式由插件负责，沿用现有做法：新版本遇到不认识的数据，在改动数据之前拒绝打开。

### 装卸只在没有运行的时候进行

插件集合只在空间里没有 Agent 运行的时候变化。这条规则来自两个现状。

其一，通用 Agent 带着命令工具，它的每次运行整段持有空间的写锁，其间不允许读取空间历史（`packages/base/src/space/space.ts`）；而插件打开以后要追赶已有的历史。在 Agent 的一次运行中途加载插件，两边会互相等待。

其二，会话的工具清单在一次运行里本来就是固定的。在运行中途换掉插件，模型手里的工具声明、系统提示里的工具段与实际可调用的东西会对不上。

所以 Agent 调用工具提出加载或卸载时，宿主只把请求记下，告诉它“本次运行结束后处理”。此后分三段。

**准备与批准。** 运行结束以后，宿主为加载请求准备候选并询问使用者。这一段不占用空间的打开与关闭队列，其间空间照常使用，也可以关闭；批准回来以后，宿主重新核对空间还是那一次打开、请求没有被撤销，否则作废。

**等待空闲。** 批准以后，宿主等空间空闲：没有 Agent 在运行，没有正在处理的插件方法调用，插件经宿主进行的模型请求、文件读写和历史记录也都已结束。等待期间不挡住任何工作，别的会话照常可以发消息；运行一个接一个时，装卸就一直等，列表里显示它在等待，使用者可以停止那些运行，也可以撤回这次装卸。

**执行。** 空闲以后，宿主进行一次重组，见下一节。重组与空间的打开、关闭排在同一条队列里。

执行了的装卸，结果在重组结束时写进提出请求的会话。一次运行里提出的几个请求按顺序一起处理，结果合成一条。若提出请求的那次运行是正常结束的，此后使用者没有在这个会话里发消息、按停止、换模型、压缩或分支，也没有关闭或切换空间，发起它的连接也还在，宿主就用这条结果开始下一次运行，Agent 接着做下去；这时新插件的工具已经在它的清单里，可以直接调用来验证。否则只写结果，不启动运行。

没有执行的装卸同样要让提出它的 Agent 知道。准备失败或导入失败时，宿主等到空间空闲，把结果写进会话，条件与上一段相同时用它开始下一次运行，Agent 拿到错误就能接着改；这一步不关闭也不重开插件。使用者拒绝批准或撤回时只写结果，不启动运行。空间已经关闭或切换时不写。往会话里写入要避开它正在进行的运行和压缩，所以无论执行与否，写入都放在空间空闲、暂停受理请求的时刻。这些结局也记在插件列表里。后端在交回结果之前异常退出时，结果不保证送达，重新启动以后也不会自己接着运行。

`plugin` 工具的装卸动作只在使用者直接对话的会话里可用。子 Agent 和后台运行提出的装卸会被拒绝：它们结束以后没有人接着处理结果，父运行也已经拿到了它们的输出。

对使用者来说，过程是：让 Repa 写一个插件，它写完，界面请求批准，同意以后它接着试用并报告。其间没有重启，也没有构建。使用者在插件列表里直接启用、批准或卸载时，走的是同样的三段。

### 重组

插件集合只经一种动作改变：关闭这个空间的全部插件和 Agent 运行时，再按启用记录把它们打开。这个动作叫重组。空间本身不关闭，它的锁、历史和备份都不动；后端也不重启。

选择重组，而不是在运行着的空间里单独换掉一个插件，理由有两条。其一，这条路径是现成的：切换空间时，后端做的就是关闭再打开，单个插件打不开时宿主也已经会把它停用、让其余的照常工作。其二，它不要求插件做任何新的事：每个插件打开时本来就从空间历史和自己的数据重建状态，这是底座的前提，重新打开一次只是把这个前提再用一遍。实测，带着随包 Python 课程的学习插件重新打开一次约 0.4 秒，积累一年密集使用的学习记录以后约 0.9 秒。

一次重组的顺序是：

1. 空闲成立的那一刻，后端不再受理与 Agent 和插件有关的新请求，让它们稍等；同时通知旧的插件宿主和 Agent 运行时开始关闭，它们从此拒绝新的工作，并取消各自还在进行的模型请求。两边一起开始关闭，再一起等它们结束，不存在一方等另一方先停的次序。
2. 写启用记录，并读回核对盘上实际的内容。
3. 按盘上的启用记录打开：随包插件，加上已启用、快照核对通过、导入成功的自写插件。打开的次序与打开空间时相同，先调用各插件的 `open`，核对声明，再让它们追赶空间历史。
4. 清理不再被记录引用的快照。关闭时有插件报错，或者记录是否已经持久写入不能确认，这一次就不清理。
5. 把结果交回提出请求的会话，通知前端重组完成，恢复受理请求。

第 2 步的记录没有写成时，第 3 步打开的就是原来的集合，这次装卸报告为失败。任何情况下，打开的依据都是盘上的记录。

**替换**一个正在运行的插件，在重组之前多一步：批准以后，宿主先导入新版本的入口模块。导入失败时到此为止，不重组，原来的版本照常运行，错误交回请求方。这一步之所以可靠，靠的是“模块顶层只定义代码”这条要求；不遵守它的插件，导入失败时可能已经留下副作用。

新版本导入成功但打不开时，插件转为失败，宿主不自动退回旧版本。使用者或 Agent 可以改好再加载，也可以让上一次选定的版本重新生效，后者是一次普通的加载。退回的只是代码：新版本若已经改过数据，旧版本可能不认识，这时它按上面的规矩拒绝打开，数据原样保留。

插件的 `close` 抛错时，重组照常继续，报错连同结果一起交回，写插件的 Agent 可以据此修正。旧实例如果还留着没有收回的定时器，它经宿主进行的读写在关闭以后一律被拒绝；它绕过宿主直接写自己数据目录的，宿主收不回。所以对插件的要求是：`close` 里收回定时器和打开的文件，并等自己的后台工作结束。`close` 执行期间，这个插件经宿主的读写照常进行，后台工作的结果可以在这时写下；`close` 返回以后才一律拒绝。

插件自己在后台做的事，宿主看不见，重组不会等它，只会在 `close` 里给它收尾的机会；它此时发起的模型请求会被取消，与关闭空间时相同。插件要能在重新打开以后接着做，或者把没做完的当作没做。

导入时，宿主用 Node 的 `module.registerHooks` 注册一个解析钩子，在第一次导入插件之前注册即可。它做两件事：把 `@repa/base/plugin` 解析到宿主自己的那一份；拒绝快照内的模块导入快照之外的文件和别的包。这是 Node 的公开接口。每个头一次导入的版本会在进程里留下一份模块，公开接口无法把它卸掉；同一个版本再次打开时复用已经导入的模块，顶层代码不再执行，实例的状态因此必须在 `open` 里建立。对偶尔发生的修改，这点内存可以接受，要真正卸掉只能把插件放进单独的进程，见[考虑过的其他做法](#考虑过的其他做法)。

### 会话

会话的工具清单在建立 Pi 的会话对象时固定。重组时，这个空间在内存里的会话对象随 Agent 运行时一起释放；会话的内容在会话文件里，下次用到时从文件重新打开，按当时的插件集合建立工具清单、子 Agent 列表、提示段和 view 的来源。历史和父子关联都从文件恢复。

重组发生时没有运行在进行，会话的队列是空的，所以不存在“正在运行的会话用哪一套工具”的问题。内存里的读取基线不保留：Agent 要整份覆盖一个此前读过的文件，得先再读一次。还没有发过第一条消息的会话尚无会话文件，宿主要保证它在重组以后照常可用。

插件 Agent 的会话在插件卸载后只读；插件回来以后，同一个会话恢复可用。

在同一份会话文件上重新建立 Pi 的会话对象，已在 Pi 1.1.0 上试过：按新的工具清单重建以后，历史完整，系统提示不变，会话文件只多一行工具变化的记录。Pi 也提供运行中登记工具的入口，但要改变 Repa 创建会话的方式，而插件集合本来就只在没有运行的时候变化，用不上它。

### 协议

协议直接改动，不保留旧接口。按[现有的版本规则](../../../../packages/base/README.md#版本规则)，前后端可以分别更新之前协议版本不变：前端与后端出自同一个仓库，没有需要拒绝的旧客户端。初始化基线加入插件列表，每项有 id、标题、版本、来源、运行状态及原因、源文件夹的状态、页面声明。列表变化时发一条通知，前端据此增删入口。`plugin.list` 与 `plugin.disabled` 并入这份列表。启用、批准、卸载各有一个方法，供界面上的插件列表使用，与 Agent 的工具走同一套宿主操作。

`plugin.call` 现在按“当前活动的空间”取插件，空间切换时在途的调用可能落到另一个空间里同名的插件上。后端因此维护一个只增的重组序号，空间每打开一次、每重组一次加一；调用带上发出时的序号，早于这一次打开空间的调用被拒绝。插件发出的事件也带序号，前端只接受与自己当前序号相同的事件。

### 崩溃

插件在调用之外抛出未处理的异常，会让后端进程退出，这一点与 dsh 相同，进程内运行无法避免；其他插件的在途工作和所有连接随之中断。数据是否完好，取决于各模块自己的写入方式，学习记录是逐行追加的，备份的说明里已经写明每种写法在进程意外退出时留下什么。

崩溃的原因无法可靠地归到某个插件头上，宿主不去猜。后端异常退出以后，桌面端用系统的对话框询问使用者：退出，重新启动，或者暂停自写插件以后重新启动。选了后者，这一次启动时所有自写插件都处于暂停，列表里标出退出前最近生效的那些供参考，由使用者逐个恢复；启用记录不因此改动。这是 dsh 桌面端的做法。桌面端现在没有重启后端并重新打开空间的路径，要补上。

插件代码卡住不返回时，进程不会退出，重组也不会结束。解脱的办法与崩溃相同：结束后端进程，再按上面的询问重新启动。现在后端在关闭中卡住时，桌面端连退出都等不到，这一点要一并修正。同步的死循环同样只有结束进程才能解除。

### 插件页面

插件的界面是它自带的页面，下称插件页面：一个 HTML 文档，脚本和样式写在文档里，图片等静态文件可以放在同一目录下。清单的 `pages` 声明每个页面的 id、标题和入口文档。应用在侧栏为运行中的插件的每个页面列一个入口，点开以后页面显示在主区域。以后开放别的位置时，再决定它们怎样声明。为此只预留一点：应用里放插件入口和页面的地方按具名的位置组织，由一张登记表驱动，学习的入口和插件页面都是表里的项。以后开放对话旁的面板、工具结果的卡片，或者允许插件改动自带界面，是往表里加位置和登记方式，不必重排应用的外壳。

页面放在沙箱 iframe 中，由后端的 HTTP 服务从快照提供。在无界面的 Chromium 里按 Repa 现行的页面策略试过，结果如下：

- 页面能加载，脚本能运行。iframe 只给 `allow-scripts`，页面的源因此是不透明的，读应用页面的文档、全局变量、`localStorage` 和 cookie 都被拒绝，拿不到后端的连接令牌。
- 应用与页面之间的 `postMessage` 往返正常。应用一侧看到的来源是 `null`，所以按窗口对象识别页面。
- 页面的响应若不带内容安全策略，它可以向任意地址发请求，也能连上本机后端的端口。带上严格的策略以后，这些都被拦住。
- `srcdoc`、`blob:` 和 `data:` 形式在现行策略下不能用或只能部分使用，页面必须有一个地址。

页面由后端提供而不是由桌面端的 `repa://` 协议提供，是因为界面有两种宿主（桌面端和浏览器里的开发页面），后端只有一个。后端的 HTTP 入口现在一律回 404，令牌只在 WebSocket 握手时核对，页面的提供要自己定边界：

- 应用要显示一个页面时，向后端开一个页面会话。后端记下它属于哪个连接、空间的哪一次打开、哪一次重组、哪个插件、哪个页面，并交回一个页面凭据：一段猜不到的地址前缀，只能用来读取这一版快照里页面目录下的文件，与连接令牌无关。
- 只提供页面目录下的文件。入口模块、清单、数据目录都不在其内。
- 每个响应带内容安全策略：默认全部禁止，允许文档内和同目录的脚本与样式、同目录和 `data:` 形式的图片与媒体，不允许任何连接；另声明只允许应用的页面嵌入它。响应不缓存。
- 应用页面的策略相应放行嵌入本机后端的地址，别的来源嵌不进来。
- 一个页面会话只对应 iframe 里加载的第一个文档，只接受一次握手。页面关闭、插件替换、空间切换，或者 iframe 里又加载了别的文档，会话即作废，应用移除这个 iframe；要刷新页面，就开一个新的会话。调用发出时记下它所属的会话，结果回来时会话已经作废的，不再交给页面。

不让页面联网，是为了让它碰不到本机后端的端口，也让插件对外的往来集中在入口模块一处；它不是针对插件作者的防线，入口模块本来就能联网。页面要取外部数据，就调用自己插件的方法，由入口模块去取。

#### 页面与应用之间的消息

页面与应用之间的消息下称页面桥。它是交到插件作者手里的约定，这里不另造一套消息，取 MCP Apps 扩展（Model Context Protocol 的界面扩展，规范在仓库 `modelcontextprotocol/ext-apps` 的 `specification/2026-01-26/apps.mdx`，状态为稳定）的一个子集，加上必要的适配。它定义的正是“沙箱 iframe 里的 HTML 页面经 `postMessage` 上的 JSON-RPC 2.0 与宿主往来”，握手、调用、主题、链接和收尾都有现成的消息，模型也熟悉这套写法。

Repa 实现下面这些消息，协议版本取 `2026-01-26`：

| 方向 | 消息 | 在 Repa 里的含义 |
| --- | --- | --- |
| 页面到应用 | `ui/initialize` | 握手。应用在结果里交回协议版本、自己的能力，以及界面语言、时区、明暗主题、容器尺寸和样式变量 |
| 页面到应用 | `ui/notifications/initialized` | 页面就绪。在此之前，应用除了答复握手，不主动向页面发请求或通知 |
| 页面到应用 | `tools/call` | 调用本插件的一个协议方法：`name` 是方法名，`arguments` 是它的输入。调用归到这个页面会话名下，后端按会话核对空间、重组序号和插件，页面不能指定别的插件 |
| 页面到应用 | `ui/open-link` | 请求用系统浏览器打开一个链接。应用向使用者显示完整地址，同意后才打开 |
| 应用到页面 | `ui/notifications/host-context-changed` | 主题、语言或样式变量变了 |
| 应用到页面 | `ui/resource-teardown` | 页面即将被移除，页面答复后应用再移除它，等待有时限 |
| 双向 | `ping` | 探活 |

`tools/call` 的结果总是一个合乎规范的 `CallToolResult`：`content` 为空数组，方法的返回值放在 `structuredContent` 的 `result` 字段里，因为方法可以返回数组或空值，而 `structuredContent` 必须是对象。方法执行出错时，结果的 `isError` 为真，错误码和说明放在 `structuredContent` 的 `error` 字段里；消息本身不合协议、调用了没有实现的请求，则以 JSON-RPC 的错误立即答复。应用在握手结果里只公布它实现了的能力。

规范之外加一条通知，`repa/notifications/event`，由应用发给页面，携带本插件用 `host.emit` 发出的事件。事件不重放，页面需要完整状态时调用自己的方法去取。

页面被移除以后，已经交给后端的方法照常执行完，结果不再交回。页面重新打开时应当先读状态，不要假定上一次的调用没有发生。

这是对规范的借用，不是完整实现，按它写的页面不能原样拿到别的宿主里，别处的页面也不能原样放进来。可以通用的是握手、样式和调用这部分写法。与规范不同的地方有这些：

- 规范假定页面由一次工具调用产生，初始数据经 `ui/notifications/tool-input`、`tool-result` 送达。主区域的页面不是这样来的，这些消息以及把内容交回对话的 `ui/message`、`ui/update-model-context` 都不实现。页面在握手完成后主动调用自己的方法取初始状态，模板照此写。以后开放“工具结果的卡片”这个位置时，用的正是这些消息。
- `tools/call` 调到的是插件的协议方法，不是 MCP 服务器的工具。
- 规范的这一版要求网页宿主经一个中间的沙箱代理页与页面通信；Repa 只用一层 iframe，页面由自己的后端提供并带上策略头，这也是规范后来的草案允许的做法。
- 规范要求 iframe 带 `allow-same-origin` 并与宿主处于不同的源；Repa 不给 `allow-same-origin`。后端的端口每次启动都变，按源保存的存储本来就留不住，给了它只会让同一后端下的不同页面互相够得着。
- 规范让页面以单个资源经 `resources/read` 取得；Repa 的页面是快照里的文件，由后端直接提供。
- 多出一条 `repa/notifications/event`。

实现以后要用规范的官方客户端库和手写的客户端各验证一条路径，握手和调用都要走通。

样式用规范里标准化的变量名，例如 `--color-background-primary`、`--color-text-secondary`、`--font-sans`、`--border-radius-md`，全表见规范的 Theming 一节。应用在握手结果里给出它们的值，值来自应用的设计系统；规范没有间距和组件，页面自己的基础样式（正文、标题、表格、按钮、输入框）写在随 Skill 附带的模板里，由 Agent 复制进页面，变量都带回退值。页面因此是自足的，不依赖应用的 React、组件库、构建产物，也不依赖后端另外提供的脚本或样式表；应用内部换框架、换组件，插件页面不受影响。

对话中的表单仍用已有的 Item：插件工具通过 `context.ask` 提问，由应用渲染。Item 与插件页面各管一处，前者是对话里的一次询问，后者是插件自己的一块地方。

学习的界面暂不改动，仍在 `apps/web` 里。它是否迁到插件页面，等这套机制有了实际使用者再定。

### 定时任务

“每天看一遍新帖”需要到点运行。dsh 的定时任务是到点给一个会话发一句提示词（`docs/subsystems/schedule.md`），事情全由 Agent 临场去办。按已定的要求，Repa 的定时任务可以是插件里确定的代码，也可以是交给 Agent 的提示词：以取新帖为例，抓取、去重、存档是代码，从当天的新帖里挑出值得看的并写成摘要是提示词。

定时任务排在最后一步，它的设计另写一份提案，本提案的清单里不为它预留字段。那份提案要回答的问题已经清楚：一个发生时刻怎样确定（时区、间隔从哪里起算）；调度推进到哪里与某一次执行的结果要分开记；空间没有打开时错过的怎样补；提示词任务由哪个 Agent 运行、带哪些工具；无人在场时的花费怎样看得见。

### Agent 怎样写插件

通用 Agent 得到一个 `plugin` 工具，动作有三个：

| 动作 | 作用 |
| --- | --- |
| `list` | 列出插件及其状态 |
| `load` | 请求启用一个或几个插件文件夹，或让它们当前的内容生效；也可以指定让某个插件的上一次选定的版本重新生效 |
| `unload` | 请求卸载 |

`load` 与 `unload` 只提出请求，本次运行结束后处理。结果交回会话：生效或失败时，条件允许就由 Agent 接着运行；使用者拒绝或撤回时只记结果。每个插件最近一次请求的结局也在列表里，`list` 能读到。登记由程序完成，Agent 只写插件文件夹里的文件。

随产品附带一份简短的 Skill 和一个模板文件夹，说明插件文件夹的结构、入口模块的写法要求，附一个带握手和基础样式的页面模板，以及“写完请求加载，下一轮验证”的顺序。

学习者版本目前关闭了通用 Agent，那是此前测试版的产品组合。自写插件以通用 Agent 为前提，学习者版本要先打开它。

### 分步落地

1. **形式。** 清单接受新字段和 `.ts` 入口，`@repa/base/plugin` 补上运行时导出，并用真实的入口验证一个最小的自写插件。第一个随包插件“材料转文字”按插件文件夹的形式写成，仍在启动时加载。
2. **运行中装卸。** 快照与批准、启用状态、装卸的三段、重组、协议、`plugin` 工具与 Skill、崩溃与卡住以后的恢复。到这一步，Agent 已能写出只有工具的插件并在下一轮使用。
3. **插件页面。** 后端提供页面、应用里的页面宿主与侧栏入口、页面桥的上述消息。
4. **定时任务。** 另写提案。

| 页面会话 | 应用为显示一个页面在后端开的一次会话，绑定连接、空间、重组序号、插件和页面 |
| 页面凭据 | 页面会话的地址前缀，只能读取该页面的文件 |
| 页面桥 | 应用与插件页面之间的消息，取 MCP Apps 的一个子集并作适配 |

## 考虑过的其他做法

**带脚本的 Skill 文件夹。** 一份说明加一个脚本，由 Agent 用命令调用。它不用改底座，但脚本没有界面，没有生命周期，也没有任何东西按时运行它；每次用不用、怎么用，仍由模型临场决定。它是一份说明书，不是软件里的一项功能。Skill 仍然保留，用于只需要告诉模型怎么做的场合。

**照搬 dsh 的同页脚本与预留位置。** 这样插件可以细致地改动应用的任何一处界面。代价是约定的面很大：预留位置的目录、React 的版本、页面里的模块表，任何一项变化都可能使已有的插件失效，dsh 自己也要求外部作者不要依赖公共组件。页面脚本与应用同权限，能读到连接令牌。按已定的要求，位置以后逐个开放。

**由应用渲染的声明式界面。** 插件只交出一份描述，由应用画出来，Item 和 dsh 兼容层的 `Box`、`Text`、`Button` 都是这一类。它最安全，外观也最一致，但表达能力由词汇决定，一个列表加筛选的页面就要扩充词汇。Item 继续用于对话里的询问。

**按摘要批准，仍从空间里的文件夹运行。** 这是本提案最初的写法，少一次复制。但批准以后文件还能改：页面的脚本改了，刷新即运行新的；已加载的模块稍后动态导入的文件，读到的也是改过的内容；确认与导入之间还有间隙。要逐一堵上这些口子，不如让运行的版本根本不可改。

**在 Agent 的运行中途装卸。** 装上以后下一步就能用。但通用 Agent 的运行持有空间写锁，加载要读历史，两者互相等待；为绕开它，要么设计一种能在运行中途安全收束历史再继续的边界，要么另设一个不经正常工具路径的转调动作。把装卸放在没有运行的时候，两个问题都不出现，Agent 也只晚一轮用上新工具。

**在照常运行的空间里只替换一个插件。** 这样别的插件不受打扰，一个插件卡住也只影响它自己。本提案原先是这样写的，实现设计做了两版。为了让一个实例在别的工作进行时安全地停下和换上，要给每次打开编号，让交出去的工具和回调认得自己属于哪一次；要有一道准入的闸，分清哪些新工作该等、哪些该放行；会话要在保留自身的同时换掉内部的 Pi 对象并转交排队的消息；停不下来的实例还要设时限并登记在案。这些机制单独看都说得通，放在一起就在彼此等待的地方反复出错。重组把这一切换成一条已有的路径，代价是每次装卸多花不到一秒，以及一个插件的问题会波及整个空间。以后若真有插件重开一次很贵，或者要容纳不可信的插件，出路是把插件放进单独的进程，而不是回到进程内的单个替换。

**新版本打不开时自动退回上一个版本。** 这样一次失败的修改不会让插件停掉。但退回要重新打开旧版本，又是一个新的实例；失败的那个版本若收尾不清，或者已经改过数据，退回本身也会失败，状态的组合成倍增加。写插件时 Agent 就在场，把错误交给它改，比宿主替它猜要稳妥；上一次选定的版本的快照留着，要退随时可以明说。

**自写插件与随包插件同名时覆盖后者。** 使用者可以借此改造随包的插件。但它带出一串问题：自写的版本待批准或打不开时，随包的版本还运行不运行；卸载以后是否退回随包的版本；两个版本共用一个数据目录，退回去的版本能否读新版本写过的数据。想改造随包插件，复制一份另取 id 即可。

**在应用配置目录再设一处插件文件夹，对所有空间可用。** Skill 有这样一处。但插件带着定时任务和数据，“对所有空间可用”的批准究竟允许了什么，要另行定义；眼下没有非它不可的用法，需要在别的空间用同一个插件时，把文件夹复制过去。

**把自写插件放进单独的进程。** 这样才能真正卸载、释放内存、终止死循环，并把崩溃隔离在外。可是 `Host` 接口里有同步成员（`now`、`models.defaultModel`、`currentRun`）和回调参数（`history.record` 的动作、`ask` 的 `onSubmit`），跨进程要逐个设计转接；学习插件又留在进程内，底座就得同时维护两条路径。本提案先在进程内做，新增的接口都取异步、参数可序列化的形式，不给以后迁出进程增加障碍。

**用 Node 内部接口清除模块缓存。** dsh 的做法，依赖 Node 的内部实现，升级 Node 时可能失效；删掉缓存记录也不保证旧模块被回收。每个版本各有一份快照，本来就不需要清缓存。

**以 MCP 服务器作为插件形式。** MCP 是现成的标准，也在进程之外。但 Repa 的插件要承担空间里的长期状态：数据目录、空间历史的接入、每次运行前投影进上下文的 view、随空间打开和关闭的实例。这些不在 MCP 的范围内。本提案只在页面桥上采用它的界面扩展。Repa 的插件工具仍可以另包一层 MCP 提供给外部的 Agent，那是另一件事。

**自己定一套页面桥。** 本提案最初列了六条自定的消息和十五个自定的样式变量。它们都得自己补全握手、版本和错误的语义，名字一旦发布就要一直维护，写页面的模型也要从头学。MCP Apps 的消息和变量名已经有多个宿主在用；借用它仍要自己定适配的细节，但名字和形状不必再发明。

## 验收

- 在一个打开着的空间里，让 Repa 写一个插件：每天取一个论坛板块的新帖，并有一个页面列出它们。它写完以后界面请求批准；同意以后它接着试用，侧栏出现入口，页面显示取到的内容。其间没有重启，也没有运行任何构建命令。
- 让 Repa 修改这个插件。批准之前，运行的仍是原来的版本，页面刷新也不变；批准以后改动出现，原有对话的历史完整。
- 把插件改成有语法错误的样子再请求加载：错误交回给 Agent，原来的版本继续工作；改正后再次加载成功。把 `open` 改成必然抛错再加载：插件转为失败并报告错误，重新打开空间仍是失败；让上一次选定的版本重新生效以后，它恢复工作。
- 卸载这个插件：侧栏入口消失，它的工具从下一条消息起不再出现；重新打开空间，它没有自己回来；它的数据目录和文件夹还在。
- 把含有这个插件的空间文件夹复制到另一台机器上打开：插件不运行，界面把它列为待批准。
- 在插件页面的脚本里尝试读取应用页面的内容、向外部地址发请求、连接本机后端端口，均失败；另一个本机网页拿到页面地址也无法嵌入它。桌面端和浏览器里的开发页面都要验证，其中桌面端的 `repa://` 页面嵌入后端地址这一点目前尚未试过。
- 插件集合变化以后，一个此前打开过的会话继续对话：历史和子 Agent 的关联都在，用的是新的工具清单。一个刚建好、还没有发过消息的会话，在插件集合变化以后照常可以发第一条消息。
- 使用者在 Agent 提出加载以后按了停止：批准照常可以进行，但 Agent 不会因此自己再运行起来。
- 界面请求批准时去改插件文件夹里的文件，再点同意：运行的是请求时展示的内容。
- 一个自写插件在后台抛出未处理的异常：桌面端询问怎样处理；选择暂停自写插件再启动以后，应用重新可用，自写插件全部停着，逐个启用后恢复。
- 一个自写插件的 `open` 永不返回：应用可以退出；重新打开并选择暂停自写插件以后，空间可用。
- 装卸等待空闲期间，另一个会话照常可以发消息；使用者撤回这次装卸以后，插件集合不变。
- “材料转文字”以插件文件夹的形式随产品附带。

## 风险与代价

- **进程内的代码没有隔离。** 批准防的是代码在使用者不知情时开始运行，防不了已批准的代码做错事、拖垮后端或陷入死循环。
- **内存只增不减。** 每个导入过的版本在进程里留一份模块。长时间反复修改插件以后，重启后端才能收回。
- **新工具晚一轮才能用。** Agent 写完插件不能在同一次运行里试它。
- **每次装卸都重新打开全部插件。** 学习插件打开一次约 0.4 秒，学习记录很多时接近 1 秒；其间与 Agent 和插件有关的请求稍等，插件的页面要重新读取状态。别的插件正在自己做的后台工作会被打断，由它在重新打开以后接着做。
- **装卸要等空间空闲。** 等待期间不挡住任何工作，所以运行一个接一个时，装卸会一直等下去；使用者可以停止那些运行，或撤回这次装卸。
- **一个插件的问题会波及整个空间。** 任何一个插件的 `open` 或 `close` 不返回，重组就不结束，整个空间与 Agent 和插件有关的请求都停住，只能结束后端再打开。把影响限制在一个插件之内的做法见[考虑过的其他做法](#考虑过的其他做法)。
- **批准的次数。** 每次让改动生效都要批准，写插件的过程中会被问若干次。实际嫌多时再考虑“本次对话内不再询问”。
- **插件页面的外观靠约定。** 基础样式表保证字体、颜色、间距的底子一致，页面仍可能做得粗糙。页面里的快捷键和焦点与应用互不相通。
- **页面不能直接显示外部图片。** 帖子的缩略图之类要由入口模块取回，再以数据的形式交给页面。规范里有声明可访问域名的字段，需要时可以照它开放，并在批准时列出。
- **约定一旦发布就难改。** 清单字段、`@repa/base/plugin` 的导出、插件文件夹的位置，使用者的插件都依赖它们。页面桥跟随外部的规范：它的草案仍在变动，Repa 固定在 `2026-01-26` 这一版，日后升级要保留对旧版页面的支持。
- **前端要增加通用的部分。** 页面宿主、侧栏入口和插件列表落在 `apps/web`，分工另行商定。
- **与 Pi 的耦合。** 重组以后会话要在同一份会话文件上重新建立 Pi 的会话对象，升级 Pi 时要重新核对。

## 待定

- **第三方依赖。** 自写插件暂时只能用 Node 内置模块和 `@repa/base/plugin`。要用别的 npm 包，得随产品带一个包管理器，或让 Agent 把依赖放进插件文件夹；两者都未设计。
- **Agent 怎样看到自己写的页面。** 现在它只能验证方法的返回值，页面画成什么样要使用者来看。前端可以提供一项服务，把页面的文字内容交回后端，尚未设计。
- **插件的分享。** 把插件文件夹交给别人即可使用，对方打开时要批准。目录、版本与升级不在本提案之内。
- **与提示词画板（[#41](https://github.com/Utopia-V/repa/issues/41)）的关系。** 该 Issue 里“启用或停用插件”的部分由本提案承担，画板只管提示段。
