# Repa 文档规范

本规范适用于 Repa 的项目文档和 Issue／PR 技术说明。它规定落笔的位置与写法；产品行为以已接受的领域约定和接口为准。

## 文档归属

| 内容 | 保存位置与写法 |
| --- | --- |
| 产品概览、阅读顺序、当前实现范围、运行入口 | 根目录 `README.md`；先提供入口，再链接详细说明 |
| 已接受的领域概念、关系与不变量 | 根目录 `CONTEXT.md`；格式沿用 [领域文档格式](../domain-modeling/CONTEXT-FORMAT.md) |
| 架构选择及其原因、代价 | `docs/adr/NNNN-slug.md`；按下节维护当前有效决定 |
| 当前模块责任、调用方式、持久格式、验证入口 | `docs/development/`，由其中的 `README.md` 索引；新增模块说明同时补入口 |
| 上游调查与比较证据 | `docs/research/`；写清核验的版本、提交或发布包，以及源码核对和实际运行各覆盖什么 |
| 待讨论方案、开发任务、跨任务协调 | `Utopia-V/repa` 的 GitHub Issues；已定结论回到所属文档，不把 Issue 时间线复制进设计正文 |

同一项约定由一处详细解释，概览和其他指南用链接引用。当前可调用字段以所属协议 schema 为准；接口草案不能写成现有能力。

## 架构决策

- 文件使用顺序编号与英文小写连字符短名，标题用简体中文描述决定。修改已有决定时更新原记录及其引用；新增具有独立取舍的决定才另建 ADR。
- 说明四件事：触发选择的具体需求、当前决定、决定性原因与代价、哪些实现策略仍可替换。按内容组织段落或表格，不强制固定小节数量。
- 使用一个能区分方案的具体例子解释容易忘记的理由。例如局部编辑为何保留范围外的字符，应说明对数学符号或代码的影响，而不只写“保证一致性”。
- 区分已接受的产品行为、当前工程策略和特定 SDK 的限制。记录本次选择的理由，不把工程推导写成用户原话，不把上游缺口写成永久产品需求。
- 待重新讨论的部分明确标为讨论项，并写出改变判断所需的使用反馈或证据；它们不自动修改当前契约。

## 正文与状态

- 项目自有 Markdown 使用简体中文。代码标识符、命令、包名、协议字段和上游专名保持原文；术语与 `CONTEXT.md` 一致。
- 面向开发者和希望理解内部行为的用户，先说明行为、原因与使用后果，再给接口、路径和实现细节。文件名、模块名或抽象术语不能代替因果说明。
- 独立说明文档保留一个一级标题；小节按读者要查找的对象命名。并列映射用表格，操作顺序用有序列表，正文解释用段落；不为整齐而复制固定栏目。
- 在影响阅读的位置区分“目标设计”“当前已实现”“待实现”。版本调查保留固定基准；升级后更新当前结论和开发指南，不改写旧版本的核验结果。
- 验证或兼容性结论写明实际范围，例如 Linux、真实 Pi SDK、本地 faux provider。运行命令不是已通过的证明；不把设计上的轻量性写成实测性能。

## 示例、图与链接

- 仓库文件使用相对于当前文档的 Markdown 链接；代码路径与字段用行内代码。文档不依赖本机 `/home/...` 目录。
- 命令示例说明执行目录，沿用所属 `package.json` 的脚本。API 示例包含必要的输入与结果处理；占位值能看出需要替换什么，不省略关键版本基准或目标归属。
- 上游行为依据优先链接固定 tag／commit 的源码或对应版本文档。链接附近写明它支持的判断；GitHub 任务链接使用实际 Issue／PR 地址。
- 静态架构图使用 Mermaid。图标题或相邻正文说明画的是当前实现还是目标设计；箭头标明调用、传输、引用或保留等含义，涉及进程和权限时画出边界。
- 修改行为、版本或文档位置时，同步所属说明、README 摘要及受影响链接。纯文档修改检查差异、字段与链接，不因此要求运行完整代码测试。
