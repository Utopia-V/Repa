# Repa 文档规范

本规范适用于 Repa 的项目文档、供维护者审阅的技术工作稿和 Issue／PR 技术说明。它规定落笔的位置与写法；产品行为以已接受的领域约定和接口为准。

提交作者要求见[贡献规范](../../../CONTRIBUTING.md#文档与协作说明由人类书写)，实现期工作稿遵循根目录 [AGENTS.md](../../../AGENTS.md)。维护者授权的未提交工作稿随实现记录事实与取舍，最终提交正文由人类书写；不把工作稿直接作为提交或公开说明。

## 文档归属

| 内容 | 保存位置与写法 |
| --- | --- |
| 产品概览、阅读顺序、当前实现范围、运行入口 | 根目录 `README.md`；先提供入口，再链接详细说明 |
| 已接受的领域概念、关系与不变量 | 根目录 `CONTEXT.md`；格式沿用 [领域文档格式](../domain-modeling/CONTEXT-FORMAT.md) |
| 架构选择及其原因、代价 | `docs/adr/NNNN-slug.md`；按下节维护当前有效决定 |
| 当前模块责任、调用方式、持久格式、验证入口 | `docs/development/`，由其中的 `README.md` 索引；新增模块说明同时补入口 |
| 上游调查与比较证据 | `docs/research/`；写清核验的版本、提交或发布包，以及源码核对和实际运行各覆盖什么 |
| 待讨论方案、开发任务、跨任务协调 | `Utopia-V/repa` 的 GitHub Issues；已定结论回到所属文档，不把 Issue 时间线复制进设计正文 |

同一项约定由一处详细解释，概览和其他指南用链接引用。当前可调用字段以所属协议 schema 为准；接口草案不能写成现有能力。

## 模块文档的固定格式

模块开发说明及其对应的技术工作稿统一使用以下结构，章节名称与顺序固定。工作稿用于审阅同一份模块说明，也沿用这个格式。

```markdown
# 模块名称

简短概述：这一部分做什么、当前可以怎样使用。

## 设计思路

## 实现细节

### 按具体对象命名的小节

## 未完成项与待验证项

## 验证入口
```

- 概述直接放在标题下面，不另立章节。
- “设计思路”解释需求怎样引出实现选择、复用了什么，以及具体收益和代价。
- “实现细节”按查阅需要组织接口、配置、持久格式、调用和生命周期。三级小节的名称与数量由模块内容决定。
- “未完成项与待验证项”记录缺口、使用影响和接续归属；没有未完成项时写明“无”，不保留空表。
- “验证入口”集中放检查命令、测试位置、验证结果与覆盖范围；本轮运行过程和测试结果不穿插进设计解释。

上述格式适用于模块开发说明及对应工作稿。README、领域 context、ADR 和 Issue 使用各自文种的格式。

## 行文

- 从读者能理解的具体事情或已有认识说起，让后面的概念、机制和判断有来处。例如说明共同能力入口时，先让读者看见 Agent 和界面都需要保存复习结果，再解释为什么共用处理函数。例子、操作、对照按内容选择，不固定以某种开场写每篇文档。
- 后一句接住前一句已经引入的对象，再展开新的意思。解释一个选择后，可以接着说明它怎样工作、给使用者带来什么，或它还留下什么问题。条件、因果、顺序和转折尽量用相应的衔接词说出来，让读者顺着判断往下读，不为压缩字数省去这些提示。如果几段只是轮流介绍同主题的事实，先理顺关系，再用句子和衔接词把它们连起来。
- 句法应当显出判断和动作的次序。需要较长列举时，先交代要区分什么；连续操作按实际顺序展开，让读者知道每一步面对什么、接着发生什么。讲解用法和选择时自然使用“你”引导观察与操作。精确的术语和完整的事实仍需组成能顺着读下去的句子，不把多个动作压进一串短语。
- 保留作者字词中表达的判断、次序和适用范围，也保留有助于讲解的语气和自然情绪。编辑前读最新原文，理解这些词的作用再改；“继续”“则”等词要有相应的前文关系，不能因此一概删去。
- 完稿后从头连读正文，核对下一句为什么接在这里、指代能否落到前文、判断是否被保留。只核对技术事实、换掉几个词或把条目改成段落，不能代替这次检查。删改时保留事实、接口条件和技术示例；读者应当能够跟着说明形成理解，而不必自己把分散的事实重新拼起来。

## 架构决策

- 文件使用顺序编号与英文小写连字符短名，标题用简体中文描述决定。修改已有决定时更新原记录及其引用；新增具有独立取舍的决定才另建 ADR。
- 说明四件事：触发选择的具体需求、当前决定、决定性原因与代价、哪些实现策略仍可替换。按内容组织段落或表格，不强制固定小节数量。
- 使用一个能区分方案的具体例子解释容易忘记的理由。例如局部编辑为何保留范围外的字符，应说明对数学符号或代码的影响，而不只写“保证一致性”。
- 区分已接受的产品行为、当前工程策略和特定 SDK 的限制。记录本次选择的理由，不把工程推导写成用户原话，不把上游缺口写成永久产品需求。
- 待重新讨论的部分明确标为讨论项，并写出改变判断所需的使用反馈或证据；它们不自动修改当前契约。

## 正文与状态

- 项目自有 Markdown 使用简体中文。代码标识符、命令、包名、协议字段和上游专名保持原文；术语与 `CONTEXT.md` 一致。
- 上游适配的维护要求写在对应实现旁边：当前依赖什么行为，升级时核对哪里，上游补足能力后哪些适配可以删除或收缩。保留原因，使后续维护者能够重新判断取舍。
- 独立说明文档保留一个一级标题；固定章节内部的小节按读者要查找的对象命名。并列映射用表格，操作顺序用有序列表，正文解释用段落。
- Issue 和 PR 先交代具体问题、目标或结果，再写影响实现与协作的条件。共享开发约定链接到所属文档，本题只保留必要分工和依赖。标题概括对象与任务，删除重复的职责宣告、模板过渡和泛泛评价。
- 在影响阅读的位置区分“目标设计”“当前已实现”“待实现”。版本调查保留固定基准；升级后更新当前结论和开发指南，不改写旧版本的核验结果。
- 验证或兼容性结论直接写出实际结果，将版本、环境和范围放在相应事实旁边。长篇解释后又以“不能说明”“不代表”等泛泛否定收尾时，核对前文：判断过大就收窄原句，范围清楚就删除重复保留话；实际缺口写明所缺条件和使用影响。性能结论依据测量结果。

## 中文编校参考

技术文档的标题、段落、数值、标点和中英混排参考本地保存的阮一峰《[中文技术文档的写作规范](references/ruanyifeng/README.md)》。原文按固定提交完整保存，授权与版本见[来源说明](references/ruanyifeng/SOURCE.md)，按当前问题选择章节阅读。

项目正文统一在中文与英文、阿拉伯数字之间留空格，数值与英文单位符号之间留空格；代码、命令、路径、URL 和原样引用保留自身格式。篇幅按信息需要安排，长句拆分以语义关系为准。

正式标准的名称、版本和用途见[中文编校标准索引](references/chinese-standards.md)。本地参考已覆盖的写法直接使用；需要核对具体标准条文或新增语言问题时再查原始资料。

## 未完成项的记录

按 Issue 已接受的交付与验收要求核对实现。发现缺口后，在授权范围内完成，或记入所属模块开发说明的固定小节 `## 未完成项与待验证项`，放在正文末尾、验证入口之前。

每项写清尚缺什么、当前可用到哪里、对使用的影响及下一步由谁或哪个任务接续。区分未实现、待前后端接入和已经实现但尚待验证；跨任务部分链接所属 Issue。影响维护的已知 SDK 限制继续在对应实现处解释，需要后续行动时从此节引用。

阶段交付按这些记录说明完成范围。缺口补齐后更新对应实现说明，并移除已经完成的条目；该节仍按固定格式保留。聊天中发现的问题当轮落到所属位置，不只留在交接消息中。

## 示例、图与链接

- 仓库文件使用相对于当前文档的 Markdown 链接；代码路径与字段用行内代码。文档不依赖本机 `/home/...` 目录。
- 命令示例说明执行目录，沿用所属 `package.json` 的脚本。API 示例包含必要的输入与结果处理；占位值能看出需要替换什么，不省略关键版本基准或目标归属。
- 上游行为依据优先链接固定 tag／commit 的源码或对应版本文档。链接附近写明它支持的判断；GitHub 任务链接使用实际 Issue／PR 地址。
- 静态架构图使用 Mermaid。图标题或相邻正文说明画的是当前实现还是目标设计；箭头标明调用、传输、引用或保留等含义，涉及进程和权限时画出边界。
- 修改行为、版本或文档位置时，同步所属说明、README 摘要及受影响链接。纯文档修改检查差异、字段与链接，不因此要求运行完整代码测试。
